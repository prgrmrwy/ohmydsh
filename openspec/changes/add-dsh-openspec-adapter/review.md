## Findings

Bottom line: the redesign is coherent in direction, and the three probe-driven shrinkages are mostly sound, but the artifacts still contain one premise that is false against the runtime (C3), one internal contradiction that makes two scenarios unsatisfiable (C2), one unspecified trust boundary (C1), and one wrong probe claim (M1). All are fixable with narrow, specified edits.

### 🔴 Critical (blocking; each has a specified fix in Required Changes 1-3)

**C1. The appended adapter block has no normative format, escaping or content-trust rule, yet it carries a shell command the model will run and registry-derived text.**
- Artifacts: session spec L17 and L22 say only "clearly delimited block ... provenance" and "one delimited adapter block". Shell quoting of the invocation is stated only in design D2 (L36); the spec requires quoting only for `/openspec-init` (L53). Scenario L40 leaves open whether the session cwd is embedded. The notice inside the block is built from registry data (updates spec L4, L22).
- Runtime: `renderSkillContent` (dsh-skill/lib/index.js:57-70) embeds `content` verbatim between `<skill_instructions>` and `</skill_instructions></skill_content>`; only the name attribute and resource-hint prose are escaped, and its comment says "skills are trusted local content". The block therefore lives inside the loader's own frame, and an early `</skill_instructions>` or `</skill_content>` in the body or block terminates it. None of the 12 bodies in the installed 1.11.0 templates contains either closer, and a line scan of the whole pinned 1.13.2 `dist` found no occurrence of `<skill_content` or `<skill_instructions` or their closers, so rejecting a collision at preparation time is feasible and cheap.
- Two carriers hand `content` to the model: the model `skill` tool result (dsh-tool-skill/lib/index.js:138-156) and the user `/name` gesture injection (:168-201, regex :373), which wraps the same output in a USER-role message (source kind `skill-invocation`). The spec names neither carrier, so on the gesture path any registry-derived or path-derived string in the block reaches the model at user-message trust.
- `DSH_HOME` is user-configurable (sync resolves env and `~`), so generation paths may contain spaces, quotes, `$()`, backticks or newlines.
- Missing: a fixed marker pair and closed field set; a rule forbidding cwd, slash arguments, project text and raw registry strings in the block; one named quoting function; the behavior when a value cannot be rendered safely; a preparation-time check that the official body contains neither the markers nor the loader's frame closers; a statement that both carriers use one builder. "Exactly one delimited block" is not mechanically assertable without a parseable format.

**C2. The upgrade/rollback transaction and the manifest-record pin check cannot both hold, and the record has no machine-checkable home.**
- Session spec L71 and scenario L78-81: the `dsh.yaml` record carries the exact version, and sync exits non-zero with `dsh-openspec-pin-mismatch` when it differs from `packages/dsh-openspec/package.json`. Updates spec L48 and design D5: the transaction writes only the package.json dependency entry and the root lockfile ("MUST NOT" touch anything else). After a successful compare-and-swap from B to C the record still says B while the pin says C, so the sync that D5's own step list runs to materialize the new generation aborts with the mismatch. "Approved upgrade survives sync" (updates L50-53) and "Rollback is source-owned and sticky" (L55-58) cannot pass as written; rollback has the same defect.
- There is no structured record to compare. Design D2 puts the record in the free-text `note`; sync validates no such field (`scripts/sync.mjs` entry validation reads only id, type, source, spec, name, version, deps, buildInputs, compatDependencies, npmScopes, enabled, enabledEnv), and `thirdPartyResources` uses strict per-type field whitelists (`scripts/lib/third-party-resources.mjs:29-33`, `noUnknown` at :43-47) for `npm-workflow`, `npm-mcp-server` and `openspec-schema`, none of which models a CLI dependency of a local bundle. So `dsh-openspec-pin-mismatch` is a new sync feature plus a new manifest contract, while proposal.md declares "Modified Capabilities: none" and `repo-layout` L501 only requires that the record exists.

**C3. "Register the Skill provider in the global layer only, so Pet executors are unaffected" is false against the runtime; as written the Pet scenario can never pass and the adapter would bypass the Pet allowlist.**
- Premise appears in: session spec L35 (last sentence) and scenario L42-45, test-plan row for "Pet-isolated sessions", tasks 9.6a/9.6b, design D1/D7, and the design Non-Goal "不让全局 bundle 绕过 Pet allowlist".
- Runtime: `SkillRegistry.collectFresh` builds every view as `[this.layers.global, ...this.layers.chainLayers(options.scope)]` (dsh-skill/lib/index.js:299) and merges them (:305). The global layer is part of EVERY scope's view; a preset or agent layer can add or shadow, never subtract, and the registry has no restrict or filter API (grep of the file finds none). Pet's own preset comment says the same ("a scoped registration is ADDITIVE", presets/dsh-pet-executor/agent.cordis.yml:87-93). Reproduced in memory with the real packages: a provider registered on the root context serving `openspec-propose`, plus a Pet-style scoped provider on a parent-linked child scope; `list({scope})` returned BOTH `openspec-propose <- adapter-global` and the scoped skill, and `get('openspec-propose', {scope})` returned the body. Registration scope decides who may ADD skills, not who may SEE them.
- Pet's tested isolation mechanism is "the preset omits `skill-filesystem`" (a preset-layer registration); it does not reach host-level providers. Dedicated Pet executors and Locus children compose from `dsh-pet-executor` (pitfalls note section 12, rule 2), so they would list and load the adapter's Skills, and the managed invocation then runs through Pet's own Bash. This contradicts the dsh-pet requirement that globally visible, non-enabled Skills fail closed.
- Side observation, outside this change but same mechanism: the existing host-level provider `third-party-spec-superflow-skills` (generated cordis.patch.yml, unscoped) is by the same source merged into every Pet executor's catalog. No dedicated-Pet-executor session newer than 2026-09-25 exists locally to confirm. Worth a separate check against the dsh-pet spec.

### 🟡 Moderate

**M1. Probe 0.6 is factually wrong as worded: a non-waking write seam into a live session exists.** `Agent.inject(message)` is public (dsh-agent/lib/types/runtime-types.d.ts:202-209, which also documents the `agent/session-start` hook as the place to "seed model-facing context" with it; dsh-agent-loop/lib/index.js:795-797 `send(input, "next-step", false)`): "Queue model-facing context for the next pre-step without waking the driver ... may miss a request whose pre-step already claimed its batch. Cancellation or disposal may discard pending context." Official packages use it (dsh-user-approval, dsh-plan-mode, dsh-hooks-claude-code, dsh-hooks-codex, dsh-cordis-host-runner). The false sentence appears in design D4, updates spec L22 ("the DSH runtime exposes no non-waking write seam"), tasks 0.6 and 0.8. The decision (attachment-only) can still stand, but for different reasons: `inject` persists an extra user-role message, so it rewrites the conversation; delivery is best-effort; and it needs an agent handle the provider does not have. Correct the rationale in all four places.

**M2. No session identity is established for the notice's per-session dedup.** The provider contract carries only `SkillLookupOptions {cwd?, signal?}`. `scope` belongs to `SkillViewOptions` and reaches the provider only because the registry passes its whole borrowed options object through (dsh-skill/lib/index.js:256 for `get`, :350 for `list`). Both runtime callers pass it (`scope: exec.agent` at dsh-tool-skill:143, `scope: agent` at :177), but `exec.agent` can be undefined (:141 uses optional chaining). Updates spec L22 ("at most once per session"), tasks 5.11 ("per session x version dedup, liveness check") and the routing token ("bound to session id") all need an identity the contract does not declare. An implementer may silently weaken this to per-process or per-cwd. Define the key (for example a WeakMap keyed by the `scope` object identity: process-local, no id exposed, dies with the agent, resets on restart, resume and fork) and pin the undeclared-field dependency with a test at both call sites.

**M3. Two oracles for "official body", and the official bodies reference slash names DSH cannot express.** Session spec L9 allows "documented DSH invocation-reference adaptation"; L17 and L22 demand the body equal "the official renderer output" byte-for-byte. The loader strips frontmatter and trims (`content = parsed.body.trim()`, dsh-skill-filesystem/lib/index.js:702), so loaded content can never equal `generateSkillContent` output; the comparable oracle is the instructions part (on 1.11.0, `trimmed body == template.instructions` holds for all 12). Also 10 of 12 bodies contain `/opsx:*` references, and DSH command names must match `/^[a-z][a-z0-9_-]*$/` (dsh-commands/lib/index.js:71), so `/opsx:propose` is not a valid DSH command or skill gesture. The official renderer takes a `transformInstructions` hook for exactly this, so "official renderer output" has no DSH-specific oracle until the transform is named. Define `renderOfficialBody(selection)` = instructions of `generateSkillContent` with one documented DSH transform, and say whether it applies to Skills, commands, or both.

**M4. The plugin options `updateCheck` and `telemetry` have no channel.** Updates spec L4, design D4, proposal L10/L30 and tasks 1.2/10.1 place them in "the `dsh.yaml` entry's configuration". Sync passes no per-entry config to a bundle (fields it reads are listed under C2; no existing dsh.yaml entry carries `config` or `options`); local packages get configuration from their static `cordis.patch.yml` (dsh-pet, worktree-session) or from the DSH settings service (`ctx.settings.register('dsh-memex', ...)` backed by `~/.dsh/settings.yaml`). Adding an entry-level options field is a sync change plus a repo-layout delta, contradicting "Modified Capabilities: none". Pick an existing channel or declare the repo-layout change.

**M5. `OPENSPEC_TELEMETRY=0` also disables the official CLI's own update check, and `telemetry: official` re-enables it.** In 1.11.0 `isCheckEnabled()` returns false when `OPENSPEC_TELEMETRY === '0'` (version-check.js:34); 1.13.2 does the same through `isTelemetryOptedOutByEnv()`. With `telemetry: official` (and no CI, `DO_NOT_TRACK` or global-config opt-out) and `updateCheck: disabled`, the official `openspec update` still performs its own registry request (`getAvailableCliUpdate`, cli/index.js:243) and prints "A newer OpenSpec CLI is available ... npm install -g ..." advice; the interactive self-upgrade offer is gated on a TTY and an npm-global install (`shouldOfferUpgrade`, version-check.js:517-522), which a generation directory under `$DSH_HOME` is not, so the realistic effect is a network request plus advice that tells the model to upgrade outside the managed flow. This contradicts "disabled stops all automatic and explicit network checks" and the managed-upgrade model. `OPENSPEC_NO_UPDATE_CHECK` (honored when defined, in both versions) is the independent switch. The managed invocation should always set it, and a scenario should assert the official CLI makes no request through the managed invocation.

**M6. The registry request is under-specified, and the obvious request fails the stated limit.** Measured against the real registry today: full packument 157,363 bytes (over the 64 KiB limit, so every automatic check would fail as "oversized"), abbreviated packument 57,308 bytes (under the limit by about 8 KB and growing with each release), `/latest` document 3,164 bytes, dist-tags endpoint 56 bytes. The official CLI itself reads `/<package>/latest` with a 256 KiB cap, 1.5 s timeout and up to 3 redirects. Name the exact URL and field in the updates spec, and add a fixture shaped like the real response so a limit/endpoint mismatch fails a test.

**M7. Catalog staleness: official profile or delivery edits are not reflected.** Design D2 re-reads the official global config "at every get/load", but the registry caches `list` results per (cwd, scope chain, revision) until a provider calls its registration-scoped `invalidate()` (dsh-skill/lib/index.js:265-275, README "no TTL"). A user switching `openspec config profile` sees a stale catalog until restart, while `get` may then find the skill gone. Specify an invalidation trigger (watch or stat the global config on a bounded cadence and call `invalidate()`), plus one scenario.

**M8. The command carrier is unspecified.** A command handler result is `{kind, text, sourceEventSeq?}` (dsh-commands/lib/index.js:175-194); `text` goes to the human UI and the persisted `command/done` event (:333-336) and is NOT shown to the model. Official commands feed the model by submitting a message (`agent.followup`/`agent.steer`, dsh-command-goal:97-105, dsh-plan-mode:215-221; both wake the driver). The spec never says what is submitted to the model, with which message source, that raw arguments are not placed in the plugin-sourced message, or that the block is attached in the same message as the body. `command/run` also persists the raw argument string unless `recordInput: false`. The DSH command names for the 12 workflows are not stated anywhere (valid names exclude `:`), and which path handles a typed `/openspec-propose` (command registry or skill gesture) is unspecified; the two use different carriers.

**M9. Missing failure scenarios for the appended block and the attachment-only notice.**
