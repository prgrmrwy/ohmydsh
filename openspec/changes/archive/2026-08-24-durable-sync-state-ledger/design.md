## Context

sync 通过一份 `$DSH_HOME` 下的 JSON 账本记录"哪些产物是我部署的、部署时内容哈希是多少"。这份记录是所有 fail-closed 判定的唯一依据:`agentInstructions` 用它区分「我部署的文件」与「用户自己写的文件」,并据此决定能否覆盖或删除。

历史上该文件名一直带仓库名,随仓库更名被"顺手统一":

| 提交 | 更名 | 账本处理 |
|---|---|---|
| `41109c1` | zydsh → mydsh | 改常量,未迁移 |
| `fdd1a65` | mydsh → ohmydsh | 改常量,未迁移 |

两次都产生孤儿账本。症状不对称是它长期未被发现的原因:package / skill / preset 的判定是"内容 hash 对得上即认领",账本丢失后静默恢复;只有 `agentInstructions` 是 fail-closed 的,才把问题暴露成硬失败。2026-08-24 的实际故障链是:账本丢失 → 目标被判为未托管 → sync 失败 → launcher 回滚 `dsh.yaml` → DSH 自动升级被阻断。

关键约束:**fail-closed 判定本身是正确的**,不能为了消除报错而放宽它。`openspec/specs/repo-layout/spec.md` 的「未托管目标冲突」场景明确要求"目标已存在、内容不同且没有本仓库的部署状态"时报错。问题不在判定,在于账本本不该丢。

## Goals / Non-Goals

**Goals:**

- 消除"仓库更名 → 账本孤儿"这一缺陷类别的成因,而不仅修复本次实例。
- 让既有安装无需人工干预即可恢复所有权。
- 把账本持久性写成规范不变量,使其不能被下一次无害的更名再次破坏。

**Non-Goals:**

- 不放宽任何 fail-closed 判定,不改变「未托管冲突」「托管漂移」「安全撤销」的既有语义。
- 不改变账本的内容结构与哈希算法。
- 不做跨 `$DSH_HOME` 的账本合并或冲突消解(多世代只取其一,不合并)。
- 不自动清理用户目录下的历史文件。

## Decisions

**1. 账本文件名与仓库名解耦,而不是仅补一次性迁移。**

只补迁移能修好本次,但下一次更名仍会重演——因为"改名时顺手统一所有带仓库名的标识"是完全合理的直觉,缺陷会被反复重新引入。把标识改成与仓库名无关(`.dsh-sync-state.json`),该直觉就不再触发这个后果。
*备选*:保留带仓库名的文件名 + 每次更名时手动加迁移项。否决——依赖人每次都记得,而历史证明两次都没记得。

**2. 迁移用 rename 而非 copy。**

移动后历史文件自然消失,迁移天然只发生一次,幂等无需额外标记;复制则会留下两份看起来都有效的账本,下次读取时需要额外规则判断谁是权威。
*备选*:copy + 写入 migratedFrom 标记。否决——引入需要维护的元数据,收益为零。

**3. 多世代取最新,更旧世代只报告不删除。**

按已知命名的新旧顺序取第一个存在者,语义明确且无需读内容做启发式判断。不删除更旧世代:删除是不可逆的,而这些文件是惰性的,留下它们的代价只是一行提示;由用户决定何时清理。
*备选*:迁移后自动删除全部历史文件。否决——为了目录整洁让工具默认执行不可逆操作,与仓库"安全相关路径 fail closed"的一贯取向相悖。

**4. 迁移发生在 `main()` 最早、任何状态读取之前。**

账本被多个 action 各自 `loadState()` 读取,迁移必须先于全部读取完成,否则第一个 action 会看到空账本并做出错误判断。放在 `main()` 入口是唯一能保证该顺序的位置。

**5. 不把"账本缺失"当作放宽 fail-closed 的理由。**

规范显式写明这一点。否则未来容易出现"账本没了就当作首次部署"的便利实现,那正是本次故障想要覆盖掉用户文件的那条路径。

## Risks / Trade-offs

- **历史命名列表会随时间增长** → 缓解:列表是有限且封闭的(仓库更名是罕见事件),且新命名已与仓库名解耦,预期不再新增条目。
- **本次又发生了一次文件名变更,理论上是同类操作** → 缓解:这次变更**自带**迁移逻辑,且新名不含仓库名,是该序列的终点而非又一环;已在真实 `$DSH_HOME` 上验证迁移成功并保持幂等。
- **rename 跨文件系统会失败** → 影响可忽略:源与目标同在 `$DSH_HOME` 目录下,不跨设备。
- **更旧世代文件长期滞留用户目录** → 接受:每次 sync 一行提示告知可安全删除;以可逆性换整洁性是刻意选择。
