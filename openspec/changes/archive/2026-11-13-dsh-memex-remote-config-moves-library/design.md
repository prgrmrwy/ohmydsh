# Design — dsh-memex-remote-config-moves-library

## D1 为什么必须搬目录而不是只改配置

配置里的 `home` 只说明库在哪，真正让它可同步的是目录里的 `.git` 与 `.sync.json`，这两样都归内核所有。
所以「改路径」必须等于「搬目录」：复制卡片与仓库状态到新路径，主机在新路径执行内核动作，最后才让配置
指过去。反过来（先改配置）会让旧目录里的仓库变成孤儿，新目录则是一个没有历史的空库。

被否掉的方案：**先改配置，再在内核里 clone**。内核没有 clone，`--init` 只会 init+push；在已有历史的远端
上从空目录 init 会推入第二条互不相关的历史，比不动更糟。

## D2 顺序：搬家 → 内核在新目录跑 → 落配置 → 删旧目录

四步不可交换，理由各自独立：

1. 先搬家：新目录必须先有卡片与仓库，内核动作才有意义。
2. 芯核在新目录跑：`sync --init <url>` 或用现有远端 `sync`（拉齐远端已有内容），失败就在此结束，
   旧目录原封不动。
3. 落配置（页面 `persistScopes`）：配置仍是唯一真相源，`scopes[].home` 指到新目录。
4. 删旧目录（宿主 `retire`）：只有配置已经解析到新目录，宿主才允许删除；删除前再校验该路径确实是本次
   搬过的来源、且不包含任何在用的库。

任何一步失败的状态都是可解释的：1/2 失败 = 完全没变；3 失败 = 新目录已就绪、旧目录保留、配置未变
（重试即可）；4 失败 = 配置已指向新目录，旧目录残留（页面提示手动清理）。

## D3 目标目录非空：按「目标优先」合并

目标目录已有卡片时，沿用切换主入口的合并规则：同名 slug 保留目标副本，来源记为跳过。这样把库搬进一个
已存在的目录（例如另一台机器上的同名库）不会静默覆盖任何一侧。`.git` / `.sync.json` / `.gitignore` 只在
目标没有自己的那一份时带过去，避免半覆盖一个已有仓库。

## D4 删除的安全性

宿主只在内存里记住「本次搬过、尚未退休」的路径（`pendingRetire`），并要求：

- 该 scope 现在解析到的 home 必须等于这次搬家的目标；
- 被删路径不得是 `/`、home 目录，或包含任何在用库目录；
- 每条记录只能退休一次。

页面无法指定任意路径去删——它只能说「退休这个 scope 的旧目录」，具体路径来自宿主自己的记录。

## D5 幂等与重试

搬家是「复制 + 跳过已存在」，因此重试只会补缺。若第 3 步被拒绝，用户再点一次即可：搬家庭已就绪
（跳过），内核动作重复执行是安全的（`--init` 对已存在仓库只更新 remote），随后配置与退休继续。

## 风险

- 目标目录与旧库在同一块盘上时复制很快；跨盘搬大库会同步阻塞 Host 一次，页面用忙态提示。
- 若用户把新目录选到另一个远端仓库的检出里，`assertLibraryTarget` 只挡「相同/嵌套/非目录」，不判断内容
  归属；`D3` 的合并规则保证不丢卡片，但库里可能出现两套来源的卡，属用户显式选择。
