## Findings

What this change does: It makes the pinned Jev MCP transport selectable between TypeSafe and OpenRouter and restores the shadow observation path. It also adds provider attribution and error normalization to the recorder; these remain observational and do not authorize workflow changes.

### 🔴 Critical (blocking)

None. The round-1 package-pin collision is resolved in the current plan.

### 🟡 Moderate

**R2-M1 — The error-normalization rule accepts non-HTTP numbers and misses the pinned transport's deadline error.**

- **Evidence:** The [routing requirement:4](<specs/jev-workflow-routing/spec.md#L4>) treats the first standalone `[45]\d\d` anywhere in the text as an HTTP status, then recognizes only `timeout`, `timed out`, or `aborted` as timeout text. Actual supported HTTP formats are emitted at [OpenRouter:302–304] (`node_modules/@jkudish/jev-mcp/dist/provider.js#L302-L304`) and [shared provider:86–93] (`node_modules/@jkudish/jev-agent-tools/dist/provider.js#L86-L93`). The OpenRouter deadline instead says `Jev request exceeded the 60000ms deadline.` at [205] (`node_modules/@jkudish/jev-mcp/dist/provider.js#L203-L207`), with another variant for response-body reading at [129–131] (`node_modules/@jkudish/jev-mcp/dist/provider.js#L129-L131`).
- **Why:** `socket hang up on port 451` becomes `region-blocked`; `network failed after 503 ms` becomes `provider-5xx`. Neither number is an HTTP status. Conversely, the actual deadline text becomes `unknown`. Both stipulated 451 examples, `OpenRouter decisions API 451` and `Jev provider typesafe: request failed (HTTP 451)`, do normalize correctly; the defect is the unrestricted search and missing deadline form, not those examples. Offline in-memory checks reproduced all three wrong classifications, and an upstream fetch mock reproduced its deadline text without network access.
- **Concrete fix:** Extract status only from the supported, anchored HTTP-message grammars, including the OpenRouter numeric slot and the shared provider's `(HTTP NNN)` suffix. Do not scan arbitrary text for a number. Add the pinned deadline wording to timeout recognition. Specify precedence and case handling, and add positive fixtures for both 451 messages plus negative-number and deadline fixtures.

**R2-M2 — Overwriting `errorCategory` from transport success/error alone can erase semantic response failures.**

- **Evidence:** [Design D5:51–54](<design.md#L51-L54>) and the [routing requirement:4](<specs/jev-workflow-routing/spec.md#L4>) make the calculated category override the supplied category whenever `jevCalls` is present. The [realistic-outcome scenario:37–40](<specs/jev-workflow-routing/spec.md#L37-L40>) specifies `none` for successful calls but contains no malformed-success case. The pinned MCP returns a successful JSON envelope with classify `results[].status: invalid_response` at [527–536] (`node_modules/@jkudish/jev-mcp/dist/server.js#L527-L536`) and decide `recommendation.status: invalid_response` at [678–689] (`node_modules/@jkudish/jev-mcp/dist/server.js#L678-L689`). The bridge does not reject those envelopes: it rejects only MCP `isError` at [231–253] (`node_modules/@deepseek-ai/dsh-mcp-client/lib/index.js#L231-L253`).
- **Why:** A caller can correctly supply `errorCategory: malformed-response`, then provide the mandatory successful `jevCalls` carrying that invalid-response envelope. The new contract supplies no way to retain or deterministically recover this category; an implementation following the successful examples can overwrite it with `none`. Existing [recorder aggregation:564–572](<../../../skills/jev-workflow-router/recorder.mjs#L564-L572>) counts failures by `errorCategory !== none`, so this changes the meaning of the failure gate even if its arithmetic is untouched. Missing-credential and cancellation categories also need explicit treatment rather than becoming unreachable through the new raw-text-only mapping.
- **Concrete fix:** Keep provider attribution separate from final observation error/status validation. Explicitly preserve bounded semantic categories when no transport call failed, or define a small bounded outcome field/response validation rule that deterministically produces them. Require `invalid_response` and invalid/truncated success payloads to remain failures, never overwrite a proven failure with `none`, and retain the existing conservative `needs-review` policy. Add classify-invalid, decide-invalid, cancellation, and missing-credential fixtures with expected persisted categories and report failure counts.

**R2-M3 — Passing raw output into recorder creates an unaddressed diagnostic and shell-data boundary.**

- **Evidence:** [Design D5:52](<design.md#L51-L54>) and the [routing requirement:4](<specs/jev-workflow-routing/spec.md#L4>) newly require up to two 2-KiB raw texts, potentially containing echoed secrets. Existing [skill:60,73](<../../../skills/jev-workflow-router/SKILL.md#L60-L73>) forbids raw provider errors in arguments, while its [recorder instructions:83–86](<../../../skills/jev-workflow-router/SKILL.md#L83-L86>) previously accepted only bounded observations on stdin. The recorder parses stdin with unguarded `JSON.parse` at [431–440](<../../../skills/jev-workflow-router/recorder.mjs#L431-L440>) and prints `error.message` at [905–907](<../../../skills/jev-workflow-router/recorder.mjs#L905-L907>).
- **Why:** Valid input can be projected safely without persisting `jevCalls`, but malformed JSON takes a different path: Node's parser error includes input snippets. A read-only probe supplying malformed JSON containing the invented `SECRET-ECHO-ONLY-FIXTURE` produced stderr containing `SECRET-ECH`. Thus “discard the field before record serialization” does not cover failure diagnostics. Additionally, copying untrusted tool text into a shell here-document or quoted command is not made safe by the 2-KiB bound; quote delimiters, `$()` and backticks must remain inert data. This is a new exposure from expanding a formerly bounded-enum input channel, not evidence that an existing tool result actually executed instructions.
- **Concrete fix:** Document the narrowly scoped local-only exception to the existing no-raw-error rule, require safe JSON serialization and stdin transport without interpolating raw tool text into shell syntax or argv, and emit a fixed diagnostic for malformed JSON/invalid `jevCalls` rather than input-dependent parser messages. Add valid and malformed sentinel fixtures, including quote/heredoc delimiters and shell-substitution-shaped text, asserting no execution and no raw/sentinel text in persisted records, stdout, or stderr. Keep all provider/error computation as data-only parsing, with bounded fallback on invalid input.

### 📌 Suggestions

**R2-S1 — Reduce the raw-success payload contract instead of adding a new output-processing subsystem.**

- **Evidence:** [Design D5:51–54](<design.md#L51-L54>) passes entire truncated result texts to derive two small values, while [the scenario:38](<specs/jev-workflow-routing/spec.md#L38>) already uses the much smaller success projection `{"provider":"openrouter"}`. Real [decide output:674–695] (`node_modules/@jkudish/jev-mcp/dist/server.js#L674-L695`) includes distributions and requirement checks. Truncating a complete JSON document before parsing can make a valid, long response unparsable even though its provider was near the beginning.
- **Why:** Deterministic attribution and a visible unknown group are justified; forwarding all successful text is not necessary for them. Supporting full outputs, byte truncation, parsing failures and semantic errors broadens the recorder's privacy surface and tests beyond the transport change's core need.
- **Concrete fix:** Prefer a closed, bounded success projection plus a bounded semantic outcome, and retain bounded error text only where fixed upstream error parsing is genuinely needed. Validate everything in the existing normalizer. If full success JSON is retained, specify extraction before truncation or an explicit conservative truncation outcome and test it. Do not introduce a wrapper service, persistent provenance channel, provider fallback, or general-purpose error framework.
