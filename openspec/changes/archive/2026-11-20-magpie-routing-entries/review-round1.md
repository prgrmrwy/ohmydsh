## Findings

### 🔴 Critical (blocking)

**C1. The reserved-route degradation (D2 / 「保留 route 不可用时的降级」) contradicts the first-registration rule of `magpie-owner-routes`, and its only scenario cannot occur as written.**
- `magpie-owner-routes/design.md` D6 and its spec 「归属 route 持久」 (注册 bullet 2) make *any* throw from the **first** `registerAdapter` a fatal start-up state: no retry, no further `register`/`replace`, `knownOwners` untouched. The code does exactly that (`registrar.ts:34-47`, `runtime.ts:162-167`, `commitOwners` `if (this.registrationError) return` at `runtime.ts:362`).
- This change's D2 says the reserved route is part of the set "只要本插件有任一 route 要注册" (`design.md` L33). Whenever `knownOwners` is non-empty, `start()` (`runtime.ts:198`) registers `[...owners, routing]` as the **initial** set. If `dsh-magpie-connector-routing` is held by another adapter at that moment, the initial call throws `DUPLICATE_ADAPTER` ⇒ plugin-wide fatal state ⇒ **every** owner route is gone until a Host restart. That is strictly worse than the degradation the new requirement promises, and the opposite of "路由入口始终至少出现在一个本插件 route 上" (spec 「保留 route 不可用时的降级」, last sentence; design Goals bullet 3).
- Scenario 「保留 route 被占用时路由入口不消失」 (spec L36-38) GIVEN "另一个 adapter 已注册 route …-routing; `knownOwners` 为 `["opencode-go"]`" then WHEN "目录同步" then "第一次后本插件 route 集合不含 routing, `Magpie (Opencode-go)` 含 `group/ds`". For that to be true the plugin must already hold a handle *without* routing, i.e. the startup set did not contain routing — which D2 forbids, and which would also break the `NO_ADAPTER`-before-first-sync guarantee (owner-routes D9) for saved selections on the routing route. The only reachable path (other adapter registers the name after the plugin's initial registration) means the plugin's `replace` fails, which is the *other* case. The scenario is therefore either unreachable or tests a different rule than the one specified.
- The `replace`-failure branch is also unspecified against the existing rollback: `commitOwners` (`runtime.ts:371-380`) rolls back the **newly admitted owner** on any `replace` failure and reports `lastSyncErrorKind: registration`. A failure caused by the routing route would wrongly evict a healthy new owner. The spec does not say how to attribute the failure (the registrar only parses the first conflicting route from the error text, `registrar.ts:19`).
- "下一次目录同步 SHALL 重新尝试" means every sync issues two `replace` calls (with routing → fail → without) and flips routing entries between `Magpie (Routing)` and their vendor group. A DSH route is a saved identity (product-positioning "Design principles" bullet 5; owner-routes D3/D4): a session that selects `group/ds` while degraded is saved on `-opencode-go`, then becomes `session/model-unavailable` the moment routing recovers (Q1-A explicitly accepts this *once*, not as a recurring flap). No requirement bounds this.
- **Required decision (design + spec):** (a) state whether the startup set includes routing; (b) state that a failure of the *initial* registration is fatal exactly as for owner routes (and drop the claim that it degrades), or persist a marker so routing is only ever added through `replace`; (c) define failure attribution and rollback for a routing-caused `replace` failure; (d) define memoization (e.g. stop retrying within the process after a `DUPLICATE_ADAPTER` on routing, retry only on restart) so entries do not flap; (e) rewrite the scenario so its GIVEN is reachable.

**C2. The invariant "路由入口始终至少出现在一个本插件 route 上" is not achievable with the specified owner handling, and owner admission for routing entries is undefined.**
- The fallback lists a routing entry on the route of its `owned_by`. That route exists only if the owner key is in `knownOwners`. Nothing says whether routing entries still contribute their `owned_by` to owner admission (`runtime.ts:359` today collects `m.owner` for *all* catalog entries). Either answer breaks something:
  - If they **do** contribute: a gateway whose only entry for owner `commandcode` is `group/x` consumes one of the 32 slots (an empty hidden route) — silently burning quota for a route that never lists anything in the normal path, and re-creating the agent-bebop "full registry" problem for ordinary models.
  - If they **do not**: when routing registration fails (C1) and the entry's `owned_by` owner is not otherwise in `knownOwners` (first install with only groups; cap full at 32 — exactly agent-bebop's PR #11 P2 reproduction, "ordinary provider model remains listed, `auto/flash` absent from every route"), the entry is on **no** route. The change's headline claim (proposal 3rd bullet, design D2 last bullet "否决 … 满额时路由入口被搬走却无处可去") is then false in the very case it cites.
- The "first install, routing entries only, `knownOwners` empty" case also yields an empty route set ⇒ no `registerAdapter` ⇒ the routing group is invisible although the plugin has a perfectly good reserved route. 「路由入口单独分组」 says routing is added when "有任一 route 需要注册", which is circular for this case.
- **Required decision:** define the exact route set as a function of (`knownOwners`, catalog routing entries, routing-registration state), including whether routing entries admit owners, the empty/first-install case, and the cap-full + routing-unavailable case; add one scenario for each (cap full + routing held; first install groups-only).

### 🟡 Moderate

**M1. The guard/AUTO "联动" claim is factually wrong or unproven, and the change carries no delta for the capability it says it must touch.**
- Proposal Impact "联动" (L33) and design Risks L65: "新 route 未补列会被 fail-closed 拦截". `packages/home-network-model-guard/src/rules.ts` `isClaudeFamily(provider, model)` is true only for provider `claude`/`anthropic` (or `claude/`, `anthropic/` prefixes) or a model id that *starts with* `claude`/`anthropic`. For `dsh-magpie-connector-routing` + `group/…` or `auto/…` neither holds, so the guard never classifies these requests as Claude and nothing is blocked. The stated failure mode does not exist; the converse risk is the real one (see M5: a group can reach a Claude member while the guard sees a non-Claude id), and it is not discussed.
- `openspec/specs/auto-model-routing/spec.md` (「AUTO 的双 Magpie 精确 transport 兼容」, L393) says Magpie providers "无需任何登记"; grep of `packages/dsh-auto-model-routing/src` finds no Magpie route list. Only `patches/home-network-model-guard-config.yml` lists routes. The AUTO half of the "联动" is unsupported.
- If the exemption is nevertheless wanted, `magpie-owner-routes/specs/home-network-model-guard/spec.md` (「豁免配置校验持久化与两端同步」) says the repo SHALL configure *exactly* the five owner routes and "MUST NOT 以前缀或通配符代替". Adding `-routing` needs a MODIFIED delta there (and the "未列出的 Magpie 归属不被隐式豁免" scenario), plus a task for `patches/home-network-model-guard-config.yml` and the `dsh.yaml` note (L437-438). Without it the change's own deployment step violates a SHALL in a sibling spec.
- AUTO interaction not analysed: AUTO "只设定每一步的 reasoning effort" and may raise it on an unregistered-family Magpie model (`auto-model-routing` L393). On a group whose member depends on effort (design Context L8: `effort ≥ high → claude-fable-5-2`), AUTO silently switches the serving member and its cost. Design Risks (L68) only mentions a settings-page hint.

**M2. Visibility key `routing` collides with ordinary models (D3 / 「路由组只受 routing 键控制」).** `catalog.ts:46` sets the visibility key to raw `owned_by`, else the first id segment. An ordinary model `{id:"routing/foo", owned_by:"routing"}` — or `{id:"routing/foo"}` with no `owned_by` — gets visibility key `routing`, the same key the new partition reads/writes (`visibility.ts:7`) and the "恢复跟随" button deletes. The spec handles the *route* collision (→ `other`) but not the *key* collision: saving the routing partition would hide `routing/foo`, and restoring would un-hide it. The settings `groups` list (built from `m.provider` at `routes.ts:46` and `runtime.ts:563`) would also merge both into one partition. Fix by namespacing the reserved key (or the ordinary models' key) and add a scenario.

**M3. Persisted `knownOwners` that already contain `routing` are not handled.** PR #11 puts `routing` into `knownOwners` (PR #11 comment by WuW0 shows exactly that on a live profile), and owner-routes' `ownerKey` accepts `routing` as an ordinary owner today. After upgrade `routeSet()` (`runtime.ts:161`) would emit `dsh-magpie-connector-routing` twice, or `validateKnownOwners` (`settings.ts:120-126`) accepts it and the "not in `knownOwners`" invariant (spec 「保留 route 不占归属名额」) is already violated. Specify: strip/ignore `routing` on load (without being a `knownOwnersReset`), de-duplicate the set, and add a scenario.

**M4. Sidebar multi-account segmentation (D6 / 「多账号分段」) is under-specified exactly where defaults land, and has a latent key collision.**
- Default `sidebarWindows` is `["weekly"]` (spec 「默认档位只显示周窗口」), i.e. one window per account. `compactRow` (`SidebarUsage.ts:259-267`) renders a single-window card as one line `name (window) · reset · %`, the *name being part of the label*. The new text says the provider name is shown once with "N 个账号" and each account's window rows follow "与单账号时的渲染规则相同". With one window per account those two statements conflict (name repeated per account, or single-line layout replaced?). The only scenario uses two windows per account with `["fiveHour","weekly"]`. Add the default-config scenario.
- Order: spec says cards follow gateway order (existing 「侧边栏常驻额度卡」 "顺序 SHALL 按网关返回顺序") yet the provider heading appears once. If the gateway interleaves `claude`, `codex`, `claude`, either order is violated or the heading repeats. State the rule (group at first occurrence?) and test it.
- Scenario 「多账号缺少 user」: `cardIdentity` is `provider + user` (`sidebar-view.ts:145`) and is used as React `key` (`SidebarUsage.ts:242,326`) and in `unchangedReads`. Two `claude` cards without `user` have the same identity ⇒ duplicate keys and a wrong "not re-read" decision. The spec requires 「账号 1/2」 but does not require a unique identity.
- The expanded detail (`detail()`, `SidebarUsage.ts:323-354`) is a separate layout (`section` per card with `plan` in `providerMeta`); the requirement says it shows the provider once too but gives no scenario. English strings for 「N 个账号」「账号 N」 are not specified although `locales.ts` carries both languages.
- Privacy: the scenario puts `user` (an account e-mail) into a permanently visible sidebar card, in `title` tooltips and, per spec, in full. The settings page already shows `user`, but the sidebar is the surface that ends up in screenshots/screen shares. At minimum record the decision and consider masking by default (`a***@example.com`) with the full value only in the tooltip/settings. `user`/`plan` are gateway text: the existing "渲染为文本" rule applies, but say so for the new rows.

**M5. Group semantics that break assumptions elsewhere are not analysed.**
- Replay: the plugin's replay envelope binds only to `response.model === source.model` (`adapter.ts:43`), here `group/…`. Since effort changes the serving member (design Context L8), a multi-turn session whose effort changes mid-conversation will replay encrypted reasoning/thought signatures produced by member A to member B. The spec's 「原生回放身份跨 route 稳定」 treats the id as "同一模型". Either state that groups opt out of native replay (always fall back to plain history) or add a scenario/risk acknowledging the behaviour.
- The wire API for group entries (`native_endpoints` ⇒ responses vs completions, `adapter.ts:176`) and their `max_output_tokens`/`context_window` are not in the author's measured facts; 「路由入口原样透传」 only asserts `model` and "effort 为 high" without naming the request field (`reasoning_effort` vs `reasoning.effort`) — not mechanically assertable as written.

**M6. D4 display-name suffix rests on an unmeasured precondition.** The scenario assumes an `auto/` entry and its concrete twin have **identical** `display_name`. The author measured only custom groups. PR #11's own gateway output (description, "Problem") shows `auto/…` and `opencode-go/…` with *different* label strings (`… · routing group` vs `… · OpenCode Go`), and the maintainer's PR #11 comment says `display_name`, `name` and `magpie_label` are "populated differently" and that the mapper reading `display_name` "does not automatically" fix naming. If auto entries on a real gateway never have an equal `display_name`, the suffix never fires and the picker ambiguity stays; if they do, the suffix depends on the *whole* catalog (not the visible set), so a name can change when an unrelated model appears. Verify against a gateway that actually has `auto/*` entries and state which field wins; or drop the suffix (entries already sit under a distinct `Magpie (Routing)` heading — cheaper) and handle name collisions among routing entries themselves (two `group/*` with equal names are indistinguishable and not covered).

**M7. The new ADDED requirements contradict the owner-routes requirements they sit on, and the delta structure will not merge cleanly.** `magpie-owner-routes` 「按网关归属注册 route」 says an owner route lists *all* models whose owner key equals the route and defines the owner key purely from `owned_by`; 「归属 route 持久」 admits owners from the whole catalog. This change's 「路由入口单独分组」 (L14) forbids routing entries on their owner route and changes the key rule (`routing` → `other`) but is an ADDED requirement, not a MODIFIED of those. After both are archived the main spec will contain two normative statements that disagree (e.g. "`group/ds` with `owned_by: opencode-go` SHALL be listed by `-opencode-go`" vs "SHALL NOT"). Because those requirements do not yet exist in `openspec/specs/`, they cannot be MODIFIED today; either rebase after owner-routes archives with explicit MODIFIED blocks for 「按网关归属注册 route」 and 「归属 route 持久」, or state the override relation in a way validation can check. The MODIFIED blocks present (「模型目录字段映射」, 「按 provider 分组…」, 「侧边栏常驻额度卡」) otherwise do copy the full prior text correctly.

**M8. Rollback and consumer interplay (design Migration Plan #4, Risks).** "回滚：manifest pin 回上一版本；`visibleModels.routing` 被旧版忽略，无需清理" ignores that sessions saved on `dsh-magpie-connector-routing` become `NO_ADAPTER` under the previous version (the owner-routes rollback note covers 0.2.0 settings, not this). Also unaddressed: the sidebar session icon capability (`dsh-sidebar-session-provider-icon`, `dsh.yaml` L140) identifies Magpie by route name and brands the upstream from the model id segment — for `group/…`/`auto/…` the "upstream segment" is `group`/`auto`; owner-routes flagged "侧边栏品牌识别" as a dependent capability, this change omits it.

**M9. Host/client implementation surface is understated and duplicates the classifier.** Proposal Impact lists `catalog.ts`, `runtime.ts`, `adapter.ts`, `SettingsPage.ts`, `view-model.ts`, sidebar. It omits the host settings response (`routes.ts:46`, `runtime.ts:563`) which must now emit the routing partition and the type (自定义/自动), and the client check (`SpeedSelect.ts:13` already duplicates a host regex, with a comment that it "must match"). If the client re-derives the type from the id prefix, D1 lives in two places (the PR #10/#11 divergence the maintainer complained about). Have the host emit the kind and the client render it. Also unspecified: a vendor partition left with no models after routing entries move out (PR #10 "omit empty provider panels unless they have usage cards"), and first-toggle semantics in follow mode for the routing partition (PR #10 "seed from the full catalog"); the scenario 「只有路由组时仍能恢复跟随网关」 only covers the explicit-allowlist state.

**M10. Scope creep / splitting.** (i) The default-effort copy change applies to **all** partitions (D5, spec 「默认 effort 下拉文案」) and its premise "不再出现「默认强度：」前缀" does not match the current code (`locales.ts:98,293`: `Default effort: not set` / `默认 effort：不设置`; no such prefix exists — it comes from PR #10's copy). The THEN "渲染文本中该行不含「默认」" collides with the existing `defaultEffortAria` ("…默认 effort") unless attribute text is excluded; it also fixes only the zh string. (ii) The sidebar multi-account work (D6) is independent of routing entries (separate capability requirement, separate files, no shared decision). Bundling it ties a low-risk presentation change to the high-risk route-identity change in C1/C2 and in rollback (M8). Splitting is cheaper to review, ship and revert.

### 📌 Suggestions

- **S1 Record the rejected "label-only" alternative.** The maintainer's PR #11 comment says a "smaller label/presentation change that preserves existing routes" is being compared. D2 only rejects "append `routing` to `knownOwners`". Add one paragraph explaining why a presentation-only change (keeping routes, no identity break, no Q1 migration) was rejected, so the BREAKING cost has an explicit justification.
- **S2 `group/auto-` heuristic (D1).** A user may name a custom group "auto-cheap" (`group/auto-cheap`), which would be typed 自动 and eligible for the ` · auto` suffix. The design itself notes legacy `group/auto-*` only as "仍可用". Either drop the legacy rule or accept and document the mis-typing.
- **S3 Assumption to state:** no real upstream provider is named `group` or `auto` (D1 classifies by id prefix only, ignoring `owned_by`). Cite the Magpie source or add a scenario `{id:"auto/x", owned_by:"auto"}` so the decision is explicit.
- **S4 Q1-A regression test.** Q1 is "decided", but a scenario like owner-routes' 「旧 route 选择不再可用」 for `(dsh-magpie-connector-opencode-go, group/ds)` (host `modelAvailable` false, `prepareCall` on the old route still resolves) would pin the documented behaviour and catch the PR #11 P2 mistake; `entryFor` is route-independent (`adapter.ts:106`) so the old pair still *prepares*.
- **S5 Test-plan hooks.** For tasks/test-plan: real-host (`buildModelCatalog`) test for the Routing group, routing-held `replace` failure, initial-registration failure, cap-full, `knownOwners` containing `routing`, duplicate sidebar identity.
- **S6 Archive order guard.** The change correctly states it must archive after `magpie-owner-routes`; add a check item so `openspec validate --strict` is re-run after that archive since M7 touches requirements that do not yet exist in `openspec/specs/`.
