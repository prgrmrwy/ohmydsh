## Context

- 插件关键词路径：`src/tools/index.ts` 的 `kernelQuery()` 对查询做汉字二字分段（`query-segment.ts`），`searchArgs()` 构造参数后 spawn 内核 CLI（`src/run/kernel.ts`）。两个函数都是文件私有，不是现在可以调用的公共 helper。
- 插件已有语义入口：`memex_search` 暴露 `semantic` 参数，`searchArgs()` 遇到它就追加 `--semantic`（`index.ts:318-323`），没有任何来源检查。工具描述按「工具描述经脚本同步」要求，从内核逐字提取。内核在库没有显式配置来源时，会按环境变量自动选择 OpenAI 或 Azure，并把未缓存卡片的全文送去向量化。现行「不引入向量检索」与实现早已不一致，且存在一条可以走通的外发路径。
- 两轮对抗 review 都判了 REVISE，而且主要阻断项都来自「本地向量后端」：判定之后内核会再读一次配置、模型下载时会读取 `HF_TOKEN_PATH`、缓存会混用不同权重、冷热计时口径不清。用户在 2026-11-03 决定：本期只交付关键词基线，插件语义请求一律拒绝，向量后端留给后续 change。
- 固定自检的程序证据只保存检索返回的摘要，不含 slug。采集阶段另把成功的工具返回全文冻结在 `collected-tool-results`（`collection.ts`、`evidence-text.ts`）。带 query 的 recall 没有结果时，插件返回 `{mode, content: "No cards found."}`（`index.ts:577`）。
- 可复用的安全文件操作：`fixtures.ts`（逐级 lstat、拒绝硬链接、独占创建，目录 0700、文件 0600）和 `freeze.ts`（`O_EXCL|O_NOFOLLOW` 写入、`readRegular`）。
- 私有材料：`~/.dsh-memex-eval/retrieval-goldset/` 下有 20 题种子、`probe.mjs`、`sem.mjs`。

## Goals / Non-Goals

**Goals:**
- 一条可回归、可离线重放的关键词检索基线：安全快照、冻结观测、零 LLM、含误选率。
- 堵住插件现有的语义外发路径。
- 把规范里的手段禁令换成目的约束，为以后启用向量留出有条件的口子。
- 把自检的 fail 拆成「没找到」和「找到没用」。

**Non-Goals:**
- 本地语义与混合后端、向量来源的启用。
- 改插件默认检索路径、wikilink 扩展、改内核、改工具描述文本。
- 防范能在运行期间改动本机目录或环境的人。
- 扩题、写封存集、LLM 裁判。

## Decisions

**D1 评测经内核 CLI，参数构造与插件共用一个纯函数。** 把关键词部分的 `kernelQuery` 与 `searchArgs` 抽到 `src/tools/search-args.ts`，插件和评测都调用它；遥测仍由工具层负责。parity 有两层验证：一层用替身内核，比较真实注册的 `memex_search` 和评测两侧的参数数组；另一层用真实内核，在 nestedSlugs 夹具上比较返回的 slug。备选方案「复用内核内部函数」被拒绝，因为内核不导出稳定的 API。

**D2 写入域固定在评测根下，并在创建前做祖先库检查。** 快照、报告和冻结观测都写在 `~/.dsh-memex-eval/retrieval/<run-id>/` 下，不接受自定义路径。创建前，从最近一个已存在祖先的真实路径开始，逐级往上查，遇到某一级含 `cards/`，或与输入库的真实路径相等，就拒绝。另外，从 `$HOME` 到运行目录的每一级都必须是真实目录而不是软链接，这样评测根不可能经别名指向其他位置，包括尚未初始化的库。新建的空目录里不可能有库，所以这项检查覆盖了「写进某个库」的所有情形，不需要库清单。被否决的备选方案：经鉴权向运行中的 Host 枚举 scope 列表（第 3 轮 review RC1）。那样会让离线工具依赖 Host 在线和认证，而祖先检查已经覆盖同一种失败。

**D3 读取用「lstat 链 + 不跟随软链接打开 + fstat 复核」。** 这样可以在打开之前拒绝软链接，打开之后再确认是普通文件且链接数为 1。目录被替换造成的竞态窗口属于威胁模型之外（见 D7），不引入目录句柄式的安全遍历。

**D4 不可变输入清单。** 清单是排除元卡、加入干扰卡之后的 `cards/`，加上只含白名单字段的 `.memexrc`。运行前后各核验一次：清单中每个文件的哈希不变，快照里也没有清单之外的文件。本期没有任何会写快照的后端，所以不需要区分哪些是可变缓存。

**D5 gold set 单文件、先全量校验、再显式选集。** `targets` 是 OR 集合，没有主目标，调换顺序不影响结论。`type` 只是标签。错误分两级定位：文件级报 `$`，题级报 id 和字段。

**D6 插件语义请求在参数层整体拒绝。** 拒绝发生在 `scope` 选库之前，因此对 `scope: "all"` 也是零调用，不进入「单库失败返回其余库结果」的语义，因为这不是某个库失败。我们考虑过三个备选，都被拒绝：
- 保留本地来源判定：两轮 review 说明要可靠实现，需要冻结配置、清理 HF 相关环境变量、禁止自动下载、校验缓存与权重的身份，成本与本期目标不相称；
- 删除 `semantic` 参数：会违反工具描述和参数逐字沿用内核的约定；
- 逐库判定：所有库的结果都一样是拒绝，逐库判定只会多一层失败语义。

拒绝时的提示写明「语义检索当前未启用」。

**D7 威胁模型写进规范。** 本期防范配置失误和环境中残留的远端凭据，不防范能改本机文件或环境变量的人，因为这样的人本来就能直接读卡。理由是要让以后的评审有一个确定的标准，避免每一轮都在加固范围上来回拉锯。

**D8 冻结观测覆盖所有可以重算的量。** 冻结内容包括：
- 逐题的有序 slug、按 `chars-v1` 计算的字符数（每个 hit 取 `title + "\n" + summary` 的码点数，不声称只计首段）、状态、错误类别、耗时；
- 干扰卡的身份、清单哈希、完整性核验结果与最终状态；
- 安装大小、快照大小，以及分位数算法和字符计数的协议版本。离线重算只读这些冻结数据。基础设施错误保留在分母里，这一轮标为 `incomplete`。

**D9 自检名次诊断走按版本区分的包装层。** 先校验 JSON 和 `current` 的 scope 与 home，再按模式解析：search 取本库的 hits；recall 只解析检索模式，`No cards found.` 还原为空列表。聚合规则是：任一次命中即为「已召回」；全部已知且都未命中为「未召回」；未命中且有无法解析的记录为 unknown。不修改 `program-evidence` 的冻结格式和夹具。上一版写的理由「改夹具会让旧轮次无法重算」不准确：报告模式本来就不比对资源哈希。真正的理由是改夹具会改变运行输入，而诊断并不需要新输入。

**D10 成本列不设门禁。** 只报端到端耗时的 p50 和 p95（每题都含进程启动，不区分冷热）、字符数中位数和体积，缺失的记 unknown。

**D11 默认排除规则从窄。** 默认只排除 `handoff`、`eval` 两个类别和三个前缀；`research`、`decision` 需要时显式追加。报告注明结果是在排除之后的背景上得出的。

**D12 叠加未归档 change，并锁定底文本的哈希。** proposal 记录了底文件的 sha256。归档前比对主 spec 中的该要求，发现变化就停下来，重新生成 delta。

**D13 规范改法用 REMOVED 加 ADDED。** 旧要求的名字本身就是手段禁令，保留名字再改内容会产生误导。另外用 MODIFIED 同步两条受影响的现行要求：`scope` 参数要求里的原生一致性条款，以及分段要求中关于语义的场景。

## Risks / Trade-offs

- [残余风险，用户 2026-11-03 裁定接受：库的 home 被配置在 `~/.dsh-memex-eval/retrieval/` 之内，或经祖先软链接指向那里，且该库尚未初始化（没有 `cards/`）。这种情况下，写入检查无法识别，快照可能写进该库的真实目录] → 风险要成立，必须特意把一个空库配进评测专用目录。要彻底防住，需要离线读取 Host 的 scope 配置，会让评测工具依赖 Host 的配置格式，留给后续 change 评估。
- [依赖 `semantic: true` 的会话会收到错误] → 提示写明当前未启用；默认的关键词路径不受影响。模型被工具描述引导去尝试语义检索时，会多一次失败的调用，这是保持描述逐字沿用的代价。
- [本期拿不到关键词与向量的对比数字] → 仓库外已有手动脚本 `sem.mjs`，可以作参考；正式对比放到下一个 change。
- [20 题种子偏乐观] → 题数少于 30 时强制标注「样本不足」，本期不据此做任何默认路径决策。
- [排除规则漏掉新形态的元卡] → 规则可以在运行时追加，排除列表写入报告。
- [`parseSearch` 的格式与内核版本绑定] → 在包装层按版本区分，解析失败记 unknown。
- [底文本被另外两个 change 修改] → 见 D12。

## Migration Plan

1. 在 `packages/dsh-memex` 内完成实现和单测，`npm test` 与 typecheck 通过。仓库根目录的 `npm test` 先跑通，再单独提交。
2. 在主 checkout 执行 `dsh build` 两次，第二次应输出 `no changes`。核对部署后的 `lifecycle/index.js` 含新句子，工具层含语义拒绝。
3. 用 20 题种子对 personal 快照跑一次，报告写到 `~/.dsh-memex-eval/retrieval/<run-id>/`，作为基线的第一个数据点。
4. 是否重启日常 Host 由用户决定；不重启时，现有的外发路径仍然存在，交付时会提醒。
5. 回滚：撤销提交，再执行一次 `dsh build`。
