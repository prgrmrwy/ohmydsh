## Why

存储内核的关键词检索**对连续汉字不分词**。`@touchskyer/memex@0.4.1` 的 `extractTokenSegments`
用 `CJK_RE = /\p{Unified_Ideograph}+/gu` 取词，一整串连续汉字因此成为**一个字面 token**，
按 substring 参与匹配；ASCII 侧靠 `ASCII_TOKEN_RE` 与空格天然分词，不受影响。

后果是中文自然语言提问在本仓的真实记忆库上**大面积 0 命中**。实测（`personal` 库，116 卡）：

| 查询 | 结果 |
|---|---|
| `子进程 代理`（带空格） | 5 命中 |
| `子进程代理`（无空格） | **0 命中** |
| `子进程能不能用上代理` | **0 命中**（10 字一个 token，全库无此连续子串） |

用 34 条「按症状提问」的 gold set 量化：**top1 仅 44%，17/34 返回空结果**。同一批查询若把
汉字串切成 2-gram 再送入内核，**top1 升到 65%、top3 升到 76%、空结果降到 8 条**。

归因已做过：对全部未命中逐条检查「卡片本身有没有可被检索到的锚点」，结果是
**19/19 条卡片都有有效锚点，0 条是卡片写得不好**——即这是纯粹的查询侧缺陷，不是内容质量问题。
在该缺陷存在时，任何「记忆质量」度量都缺乏分辨力：好卡与坏卡的中文召回率同为 0。

对照实验进一步排除了「改卡片就能解决」：挑 5 张未命中卡各追加一行症状关键词，其余不动，
**top1 纹丝不动（44% → 44%）**——因为整串汉字匹配不上，卡里写什么都无效。

本仓是该缺陷的**可修点**：`packages/dsh-memex` 今天把 `args.query` **原样透传**给内核。
上游不接受外部 PR（见 `pet-compat-minimization` 中记录的同类结论），且改上游取词逻辑会影响
其索引侧语义；在调用方做查询预处理则既不改内核、也不改卡片格式。

## What Changes

- **新增查询预处理**：在 dsh-memex 调用内核 `search` 之前，把查询中的**连续汉字串**切分为
  重叠 2-gram 并以空格连接，ASCII/数字/代码 token **原样保留**。
- **覆盖全部检索入口**：`memex_search` 与 `memex_recall` 今天是两条独立的 `search` 调用路径，
  预处理 MUST 同时覆盖，否则两个工具对同一问题给出不同结果。
- **语义检索不做预处理**：`--semantic` 走 embedding，切分反而破坏语义；预处理仅作用于关键词路径。
- **不做**：不改存储内核、不 patch 上游、不改卡片格式或 frontmatter、不改多库检索与守门语义、
  不引入分词词典或第三方分词依赖（词典是需要长期跟随的资产，2-gram 无状态且零依赖）。

## Capabilities

### Modified Capabilities

- `dsh-memex-integration`: 新增「关键词检索前对查询做 CJK 分段」的要求，明确其作用范围
  （仅关键词路径、全部检索入口）、不变量（ASCII 字节级不变、不改写卡片与内核）与降级行为。

## Impact

- **代码**：`packages/dsh-memex/src/tools/index.ts` 的 `searchArgs()` 与 `memex_recall` 分支；
  新增一个纯函数模块与单测。无新增运行时依赖。
- **行为**：中文查询召回显著提升（实测 +21 个百分点 top1）；**纯 ASCII 查询逐字节不变**
  （6/6 回归用例证实结果集完全一致）。
- **已知代价**：2-gram 会让更多卡进入候选（返回结果数中位数 4 → 8），属召回换精度的预期取舍；
  gold set 中出现 1 例名次下降（`插件 RPC 调用返回 405 但没有日志` 由 1 → 2），净收益为 +7 条命中。
- **不影响**：卡片文件、同步、scope 路由、settings UI、守门规则。
