# 设计：关键词检索的 CJK 查询分段

## 1. 缺陷定位（已实测，非推断）

读 `@touchskyer/memex@0.4.1` 的 `dist/cli.js`，取词与打分的相关常量：

```js
CJK_RE         = /\p{Unified_Ideograph}+/gu        // 连续汉字 → 一个 token
ASCII_TOKEN_RE = /[a-zA-Z0-9_\-./]+/g
FIELD_WEIGHTS  = { slug:5, title:5, tags:4, category:3, headings:3, wikilinks:2, body:1 }
MIN_SCORE      = 0.08
```

`extractTokenSegments` 对两条正则各自 `matchAll`，**汉字串不再二次切分**；`matchTokenInField`
对 CJK token 走 `line.toLowerCase().includes(token)` 的 substring 判定。于是「一串汉字」要命中，
库里必须存在**完全相同的连续子串**。

实测（`~/.dsh-memex/personal`，116 卡）：

| 查询 | 命中数 |
|---|---|
| `子进程 代理` | 5 |
| `子进程代理` | **0** |
| `会话 归档` | 5 |
| `会话归档` | 1 |
| `子进程能不能用上代理` | **0** |

## 2. 为什么修点在调用方，而不是内核或卡片

排除了三条路，每条都有证据：

**(a) 改卡片** — 做过对照实验。取 5 张未命中卡各追加一行症状关键词，其余不动：

```
对照组（原库）      top1 = 44%
实验组（+5 行症状） top1 = 44%      ← +0
```

因为整串汉字匹配不上，**卡里写什么都无效**。同一个实验组库，只把查询切成 2-gram，这 5 条
里 4 条立刻回到 rank 1。这直接证明瓶颈在查询侧。

**(b) 改内核** — 上游不接受外部 PR（与 `pet-compat-minimization` 中记录的结论同源），
且改取词逻辑会同时影响索引侧语义，属于比本变更大得多的风险面。

**(c) patch 上游产物** — `dsh-memex-integration` 现行 spec 已确立「不复制、不改写内核」的原则，
且本仓 `pet-compat-minimization` 的经验是 overlay 会长期绑定退役条件。为一个查询字符串变换
引入 patch 不成比例。

调用方预处理既不碰内核、也不碰卡片，且可随时撤除——这是本变更选它的原因。

## 3. 为什么是 2-gram，而不是分词词典

| 方案 | 取舍 |
|---|---|
| **重叠 2-gram**（选定） | 零依赖、无状态、对未登录词（产品名/缩写/代码混写）不失效；代价是召回换精度 |
| 分词词典（jieba 等） | 切得更准，但引入需长期跟随的词典资产与体积；对本库大量出现的 `dsh`/`Pet`/`locus` 等未登录词反而更差 |
| 单字切分（1-gram） | 召回最高，但单字在 `body` 权重下噪声极大，且会大量触碰 `MIN_SCORE` 以上的无关卡 |

2-gram 与内核的既有机制正好咬合：切出的 token 落入 `title`/`slug`（权重 5）时得分高，
落入 `body`（权重 1）时得分低，排序天然把「标题层面相关」的卡排前。

## 4. 不变量与边界

- **ASCII 字节级不变**：分段按「汉字串 / 非汉字串」交替扫描，非汉字段原样 `trim` 后保留。
  已用 6 条纯 ASCII / 代码查询回归验证，**结果集 6/6 完全一致**（含 `SettingsScope.mutate`、
  `connection.rpc.handle 405`、`node:sqlite NUL`、`memex sync --init`）。
- **只作用于关键词路径**：`--semantic` 走 embedding，切碎输入会破坏语义，故不处理。
  另注：本机当前**无任何 embedding provider**，`--semantic` 会挂起而非报错，因此关键词
  是唯一可用路径——这使本变更的收益是全量的，不会被语义路径稀释。
- **不写库**：预处理是纯函数，不触碰任何落盘数据。

## 5. 两个调用点必须共用一个实现

今天存在两条**各自独立**拼接 `search` 参数的路径：

```
src/tools/index.ts:152  searchArgs()        → memex_search
src/tools/index.ts:376  内联 ['search', …]  → memex_recall
```

只改其一会让同一问题经两个工具得到不同结果，而这种分叉在工具返回与日志里都不可见——
模型无法区分「库里没有」与「走错入口」。故 spec 把「单一实现 + 无旁路调用点」写成可验证条件。

## 6. 已知代价（不掩饰）

以 34 条症状式 gold set 度量：

| | top1 | top3 | 空结果 | 返回数中位 |
|---|---|---|---|---|
| 原样透传 | 44% | 47% | 17 | 4 |
| 2-gram | **65%** | **76%** | **8** | 8 |

- **候选变多**（中位 4 → 8）是 2-gram 的固有代价：更多卡越过 `MIN_SCORE`。因此评估应以
  **top1/top3** 为准，而不是「返回了多少条」。
- **一例名次下降**：`插件 RPC 调用返回 405 但没有日志` 由 rank 1 → 2。净效果是 +7 条命中、
  −9 条空结果，故接受；该用例写入测试以便后续回归时能看见这个已知取舍。

## 7. 实测结果（实施后复核，用已部署产物）

把 gold set 经**部署副本**的 `segmentQuery` 变换后再打内核，`personal` 库 34 条有效用例：

| | before | after |
|---|---|---|
| top1 | 44% | **65%** |
| top3 | 47% | **76%** |
| top10 | 50% | **76%** |
| 空结果 | 13 | **0** |
| MRR | 0.45 | **0.69** |
| 返回数中位 | 4 | 9 |

净效果：**+8 条升到 rank 1，−1 条下降**（`插件 RPC 调用返回 405 但没有日志` 由 1 → 2，
与设计阶段预测一致，已固化为已知取舍）。空结果归零是最有价值的一项：原先 13 次「查了等于没查」
现在全部返回候选。

## 8. 验收口径

单测覆盖纯函数的不变量（ASCII 恒等、代码 token 完整、汉字切分正确、空与边界输入）。
端到端收益用仓外的 gold set 复核（`~/.dsh-memex/.eval/`），**不把私有卡片内容引入仓库**——
库内容属于用户私有数据，不应进版本控制；仓内测试只用自造的最小夹具。
