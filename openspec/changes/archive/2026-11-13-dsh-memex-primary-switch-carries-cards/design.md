# Design — dsh-memex-primary-switch-carries-cards

## D1 触发点：配置生效路径，而不是页面保存动作

主入口改变只能通过配置声明表达（`scopes[].primary` 与 `workspaces[].primary`），所以迁移的实现位置
选择「配置生效路径」：`createMemexRuntime` 里已有的 `loader/volatile-update` 处理器。

这个窗口的属性正好是需要的顺序：

1. loader 已经 `updateVolatile` 把新值写进 Config 引用，并抛出 `loader/volatile-update`；
2. 处理器里 `effective()` 读到的是**新配置**；
3. 但 `scopes.replace()` 还没跑，所以 resolver 仍在服务**旧路由**。

于是「先合并、再设置主入口」就在这一个同步块里成立：合并发生在任何会话按新主入口解析之前。

被否掉的替代方案：

- **在页面保存流程里调一个新端点做合并（先在客户端合并、再写配置）**。顺序也正确，但只覆盖页面编辑；
  直接改配置、或另一份 page bundle 保存时都不会迁移；而且新库可能是本次编辑才创建/命名的，客户端在
  保存前拿不到最终库名。
- **在 `internal/config` 校验钩子里合并**。这个钩子还会被「候选校验」调用（设置页预检、loader 的
  volatile 提交都会走），在里面做文件副作用等于让一次纯校验悄悄写盘，挂载期的配置解析也会被波及。

## D2 冲突：目标副本赢，绝不覆盖

同一 slug 在两侧都存在时保留目标的副本，把来源记为 `skipped`。理由：两份可能已经分叉（这正是两个库
长期并存时会发生的），任何自动择一都会静默丢掉另一边；「跳过并报告」至少是可解释、可人工复核的结果。

实现上用 `COPYFILE_EXCL`：不先 `existsSync` 再拷，避免检查与拷贝之间的竞态把目标覆盖掉。

## D3 失败：保留旧路由（fail closed），下一次编辑重试

合并可能因为权限、磁盘或路径嵌套失败。此时处理器**不**调用 `scopes.replace()`，工作区继续按旧主入口
服务，日志告警一次；下一次 `loader/volatile-update`（任何编辑）会重新计算并重试，且合并幂等，只会补
缺失的部分。

已知边界（写进 delta spec 与 README）：这一时刻 Config 引用已经是新值，页面会显示新配置，而运行中的
路由仍是旧的；Host 重启后新配置会直接生效，卡片留在旧库（日志里有这次失败）。这是「不丢卡片」优先于
「配置与路由永远一致」的取舍：卡片在旧库仍是普通文件，可以人工再并一次。

## D4 迁移范围：两个目录、只增不改、不碰远端

- 只处理 `cards/` 与 `archive/` 下的 `*.md`；
- 源库只读：不删、不改、不移动；
- 不调用任何 `memex sync`，两库各自的远端与历史不受影响；
- 不触碰守门与发布方向：这是本机迁移，不是一次新的写入，因此不会被 internal → external 的
  deny-term 规则挡下（与人工 `cp` 的语义一致）；
- 忽略大小写以外的文件（非 `.md`、点文件）与子目录。

## D5 去重与判定

- 工作区单位 = 一个被声明的路径前缀；主入口按 resolver 的同一优先级判定：路径声明点名且该 scope 确实是
  认领者 → 唯一带 `primary: true` 的条目 → 唯一认领者。
- 旧、新两侧都必须能判定出主入口，且名字不同，才产生迁移；认领关系刚建立（原本没有认领者）不迁移。
- 同一对库在本次编辑里只合并一次：多个工作区共用两个库时，重复合并全是冲突跳过，没有意义。

## D6 页面表现

不新增控件，只让保存按钮在提交期间显示迁移状态文本（`saveBusy`）。提交本身是同步合并，`scope.mutate`
返回即代表两者都完成，所以按钮文案就是这个等待的进度提示。

## 风险

- 大库同步复制会短暂阻塞 Host 事件循环（几千张小文件量级在百毫秒级）；不为此引入异步队列，避免出现
  「路由已换、卡片还在拷」的中间态。
- 冲突不覆盖意味着分叉的卡需要人工处理；日志与 README 都点明这一点。
