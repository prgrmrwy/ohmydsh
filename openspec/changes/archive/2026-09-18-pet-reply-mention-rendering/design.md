## Context

Pet 的统一 locus 业务正文由 child 通过 `pet_locus_finish` 提交，Host 用 `im +messages-reply --as bot --message-id <触发的 om_*> --text <正文>` 发出（`channel/lark.ts` 的 `replyToTarget`）。这条链路上没有任何 @ 处理，而平台的 @ 语法只在 lark-cli 文档里：

- `text`：`<at user_id="ou_xxx">名字</at>`（名字可省），@all 用 `user_id="all"`；`post` 同法或 `{"tag":"at","user_id":…}`（`lark-im` → `references/lark-im-messages-reply.md` §@Mention Format）。
- 入站正文则相反：`event consume` 把 mention **预渲染成显示名**，所以 Agent 看到的样例天然是「@名字」，照抄即失败。

实测事实：`--text` 不会转义标记（dry-run 打印 `{"text":"\u003cat user_id=…"}`），因此**问题只在正文内容**，发送通道不需要改。旧部署里真实提醒之所以偶尔出现，是 child 绕过 `pet_locus_finish`、用 lark-im-live 的脚本手写标记发出去的（同一条 skill 记录里写着「刚才 @ 没生效」）——即系统对这条通道并无保证。

## Goals / Non-Goals

**Goals:**
- Agent 写出 `@显示名` 即得到真实提醒，不再依赖模型记得写平台标记。
- 改写范围可判定、可测试：整词、唯一命中、成员表内、非标记形式。
- 任何渲染失败都不影响发送与 Delivery 终态。
- 注入里补齐平台契约，让模型在别名的场合也能自己写对。

**Non-Goals:**
- 不跨群/跨租户模糊解析姓名（只读当前 chat 成员表）。
- 不改写卡片/富文本路径（本部署只用文本回复）。
- 不把渲染做成「内容创作」：只把 Agent 已写出的 @ 引用翻成平台标记。
- 不因此新增常驻订阅或额外出站信任面（复用既有 `+chat-members-list` 与 bot 身份）。

## Decisions

### 1. 渲染放在出站通道（`replyToTarget`），不放在工具层

**理由**：出站通道是唯一把正文变成飞书消息的地方，也是唯一能同时覆盖「业务回复」与未来其它回复调用方的位置；放在工具层则会与「Host 不参与正文」的既有分工混淆。渲染器本身是纯函数，通道只负责取成员表与失败降级。

**替代方案（否决）**：只在工具描述里教模型写标记（概率性，模型漏写就回到纯文本，且没有任何兜底）；让 child 自己用 lark-cli 发（绕过 Delivery 结算与表情状态机，规格明确禁止第二条出站路径）。

### 2. 映射来源：当前 chat 的成员列表，按 chat 缓存

`im +chat-members-list --as bot --chat-id <chat> --member-types user` 返回 `users[].name` 与 `users[].member_id`（实测：答疑群 4 人，姓名 + open_id 齐备）。与既有 `memberCount` 同一命令、同一身份，因此不扩大信任面。

按 chat 缓存（短 TTL）避免每条回复都发一次调用；缓存失败不影响正确性（下次重试）。

**替代方案（否决）**：用 `contact +search-user`（要求 user 身份，规格禁止出站用 user 身份，且是全租户搜索）；用入站事件的 `mentions[]`（只覆盖「触发消息里被 @ 过的人」，本例 bot @ 的赵鸿珂并不在其中）。

### 3. 只改写整词、唯一、非标记的引用

规则（全部可单测）：
1. 正文含 `<at ` → 整体不改写（信任 Agent 的显式标记，避免重复包装）。
2. 扫描 `@` 后紧跟的成员显示名，取**最长匹配**；匹配后必须是空白、标点或串尾。
3. `@` 前一字符必须是串首或非词内字符（排除 `a@b.com` 这类邮箱与 `foo@bar`）。
4. 显示名在该 chat 有多个成员命中 → 不改写（不猜）。
5. 单条正文改写次数设上限；超出部分保持原文。

**理由**：这些边界正是「渲染」与「改写内容」的分界：能唯一确定指向谁才渲染，否则一律保持原文。

### 4. 失败一律 fail-soft

成员表读取失败、字段形状不对、渲染抛错：按原文发送 + 一条低基数诊断（分类 + 改写次数，不含姓名/open_id/正文）。发送结果与 Delivery 终态不受影响——渲染是增强，不是发送的前置条件。

## Risks / Trade-offs

- [本意不是提醒的 `@某人` 被渲染成提醒] → 只改写整词且唯一命中的显示名；IM 语境里行首 `@显示名` 本就是「对某人说话」，与提醒语义一致。歧义一律不改写。
- [同名成员导致提醒错人] → 同名歧义不渲染（宁可纯文本也不通知错人）。
- [每条回复多一次成员表调用] → 只在正文出现可渲染候选时调用，并按 chat 缓存；命中缓存时零额外调用。
- [诊断泄漏群成员身份] → 只记录分类与计数；姓名与 open_id 永不进入日志（与 `pet-lark-channel` 既有诊断口径一致）。
- [模型看到「Host 会渲染」后完全不写标记，而成员表恰好不可读] → 注入保留显式标记写法作为别名/降级路径；渲染失败是 fail-soft，正文仍能发出。

## Migration Plan

1. 纯渲染器 + 通道接线 + 注入文案在 `packages/dsh-pet` 内完成并测试。
2. 经主仓 `dsh build` 物化、重启 `dsh web` 生效；无持久 schema 变更，回滚只需回退代码重新构建。
3. 实机验收：群里让 bot @ 一位成员，确认对方收到提醒、正文可点击；并确认同名/非成员场景保持纯文本。

## Open Questions

- 缓存 TTL 取值：先用与既有 knownNames 展示缓存一致的量级（分钟级）。若出现「刚进群的人 @ 不到」，再评估事件驱动失效，而不是把 TTL 调到近似不过期。
