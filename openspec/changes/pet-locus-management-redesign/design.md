## Context

Pet 的设置面板有六个页签，`Locus 管理` 是其中之一（`packages/dsh-pet/src/client/settings.tsx` 的 `LocusTab`）。当前实现把 `PetLocusManagementView.loci` 里**每一条记录**渲染成一张等权大卡。

本机真实快照（4 条 locus / 2 个父会话 / 3 个飞书入口）实测该页签：

| 指标 | 实测 |
|---|---|
| 面板总高 | 3444px（内容区 814px → 4.2 屏） |
| 等权事实行 | 47 行 `.dshpet-fact`（统一 132px 标签列） |
| 原始 ID | 17 处等宽展示，卡片标题本身即 `oc_a27b5de7e6a9a57462060eb289ec70ab` |
| 按钮 | 面板内 39 个，单卡一行 8 个 |
| 单卡高度 | 486–562px |

约束与既有事实：

- **本轮范围由所有者限定为纯面板调整：不新增任何 Host / wire 能力。** 因此群名、话题名与 `chatType` 的获取/持久化不在本设计内（实测这三者在系统中都不存在：入站事件不带群名、`projectGroupRecord()` 不设置 `chatName`、持久层含 `chatName` 的行数为 0）。
- **数据已经齐了。** `PetLocusManagementView` 随快照一并下发 `discovery.byEndpoint[].history`、`discovery.byParent`、`discovery.byChild` 与 `defaultQa`（`src/host/locus/management.ts:631-673`），且 `loci` 是**全部代次**（含已停止/已退役）。旧界面把这些索引闲置，反而让用户手输 `oc_…` 去查出来。
- `parentLocusId`（话题所属群级 locus）在旧 UI 中**从未渲染**，只出现在 rebuild 请求体里。
- 设置面板内容列宽实测 **568px**（DSH Settings 弹窗内），所有布局必须在此宽度成立。
- 设置 IA 规范 `openspec/specs/dsh-pet/spec.md` 现写「固定五个页签」且未列 Locus，与实现（六个页签）存在既存漂移，本 change 一并修正规范表述。
- **建树时机已改为按需（主干 `pet-locus-on-demand-tree`，已归档）**：拉 bot 入群不再产生任何 session 或 locus，整棵树只由**首条合格消息**建立；`/bind` 在尚无 locus 的入口一次建对且不发上下文变更警告。对管理面的直接后果有两条：① 管理面只会出现**已建树**的入口，未 @ 过的群不在列表中——这是模型的正确结果，不是缺失；② `provisioning` 从"几乎见不到"变成**真实存在的瞬时态**（首个 @ 正在建树时），面板必须如实呈现它，不能把它显示成空白或直接跳过。

## Goals / Non-Goals

**Goals:**

- 让所有者在**不滚屏**的情况下回答三个问题：这条入口**通不通**、**通到哪份工作**、**能不能写**。
- 把 `session 1—N locus 1—1 子会话` 这条不变量变成**可见结构**，而不是散落在各卡片里的重复行。
- 让每个标识**可读、可区分、可复制、可核对**，且不引入任何猜测的名称。
- 双向可达：从入口能到会话与飞书，从父会话能看到它全部的入口。
- 消除设置页中**不可逆外部副作用**的误触入口（创建答疑群、手输 id 绑定）。

**Non-Goals:**

- 不新增 Host 路由、不改 `wire.ts`、不改持久化 schema。
- 不做群名 / 话题名 / `chatType` 的获取、持久化或刷新（已确认不做，见 proposal）。
- 不改动 locus 领域语义、权限模型、Delivery 模型与轮盘行为。
- 不修子会话标题的生成（`childLabel` 在群名缺失时写入裸 `oc_…`）；本轮只在呈现层用角色词 + 截断缓解。
- 不引入任何自定义颜色或字体：全部沿用 DSH 主题变量。

## Decisions

### D1 · 行 = 入口（endpoint）= 一个 locus 家族，用已下发的索引聚合

以 `endpointKey` 聚合 `loci`，当前代取 `discovery.byEndpoint[].current`，历史代取同一项的 `history`；父会话分组取 `discovery.byParent`。

*为什么不自己按 `generation` 排序推断：* 当前代的判定（`currentFor` / `isCurrentLocusState`）是 Host 侧规则（`invalid|stopped|retired` 不再是当前代），前端重推一遍就会与 Host 产生第二套真相。

*被否方案：* 保留卡片但默认折叠 —— 折叠只减少高度，不解决「同一父会话被重复 5 遍」和「原始 ID 当标题」。

### D2 · 短码是显示别名，由真 ID 确定性派生，永不作为入参

每类对象一条明确规则：`oc_`/`omt_` 前缀后前 4 位；`session-` 后第一段前 4 位；`locus-…-<seg>` 取**末段**前 4 位（时间戳段无区分度）；workspace uuid 第一段前 4 位。同页冲突只在显示层延长到 6/8 位。

*为什么不在 Host 生成：* 那会引入一个新的持久身份，与「不以新身份替代既有标识」冲突；短码一旦能被当作输入，就必须解决碰撞与生命周期，成本远超收益。

*被否方案：* 直接显示 ID 前 8 位 —— 仍然像 ID，且无法一眼区分类型。

### D3 · 两个读法共用同一份 discovery，不新增查询

`按工作` 与 `按入口` 是对同一批行的两种分组（换根），数据都来自快照里已有的索引。旧 UI 的「发现关联」三选择器表单降级为折叠的手工查询入口，仅用于快照中不存在的 id（粘贴而非手输）。

*为什么保留手工查询：* Host 契约「只返回所选索引、不因共享 parent 枚举兄弟」必须继续可达；但把日常反查交给两个读法。

### D4 · 关系轨是唯一的"用力点"，其余保持安静

用 1px 竖轨 + 7px 节点把父会话—入口—会话连起来，**节点即状态**（颜色 + 文字双通道，不新增状态胶囊）。颜色全部取 DSH 主题变量，不新增自定义色值。

*被否方案：* 卡片式保留视觉重量；或大数字统计块 —— 后者是模板化答案，且没有对应数据支撑。

### D5 · 默认只显示可用父会话与仍被服务的入口，条件由筛选控件自述

默认筛选条件 = 父会话 `availability === 'available'` **且** 入口状态 ∈ {`active`, `provisioning`, `switching`}。披露只由筛选控件承担：按钮在收起状态就写明两个维度（`父会话：可用 · 入口：在服务`），浮层按桶给出**全量快照**的计数（含未勾选的桶），勾选即显示。列表里 MUST NOT 再有第二处"隐藏出口"行。

*为什么入口状态维度默认隐藏：* `stopped` / `invalid` / `retired` 是 Host 明确不再服务的入口 —— 该 endpoint 之后的入站消息会被拒（`repository.ts`：*explicitly rebuild it before accepting work*），默认把它与仍在服务的入口平铺在一起，会让"能用的"与"门牌"混为一谈。

*为什么列表内不留出口行（曾被设计为必需，现已撤销）：* 早期判断是"静默隐藏比滚动更糟"，据此加了一行「显示全部 · 已隐藏 N 个入口（按状态：…）」。实测下来它有两个问题：一是**重复**——筛选控件本来就写着条件、浮层里每个桶都带全量计数，再单起一行只是把同一件事说两遍；二是**占位**——它把入口整体下推，而这次迭代的目标正是让默认视图不滚屏看完。撤销后，唯一需要补的不是"再显示一次数量"，而是**恢复路径不能被埋**：终止态入口的重建按钮因此移到行本身（见 D6/任务 4.2），空列表的空态文案直接点名该勾哪个桶。

*代价（已知并接受）：* 归档父会话下的入口在默认视图里没有任何就地提示，只能从筛选按钮的当前条件看出"有条件在生效"。所有者第一次遇到时可能先找一下；换来的是列表干净、控件不重复，且浮层里「已归档」带回计数。

*为什么父会话维度仍要默认隐藏：* 实测存在「父会话已归档但其下 locus 仍为 `active`」的真实状态（归档不改写 locus 记录，它只挡住将来的绑定与父子补问）；默认展开会让已归档的工作混进当前视图。

筛选控件带 `aria-pressed`；筛选不落盘、不改数据。头部计数按**快照全量**给出（「关联 N 个入口」），不随筛选与搜索缩小 —— 否则一个只有终止态入口的快照会显示「关联 0 个入口」，读起来就是"没了"。

*头部布局（三轮收敛后的结果）：* 第一行是标题 `关联` + 右端的筛选控件（**改读法的控件跟着标题**）；第二行是计数描述（`N 个入口 · … · 状态更新 …`），单独成行、可自由换行；第三行是「按工作/按入口」+ 搜索框。标题 MUST NOT 参与收缩或换行 —— 此前三者挤在一行，标题被压成一列一个字（「关」压「联」）；控件与标题同行、放不下时整块换行，而不是压缩标题。

### D6 · 设置页不提供新建外部资源的入口（移除）

移除绑定 endpoint 表单与默认 Q&A 的两组创建按钮。理由：绑定需要手输 chat/thread/session/workspace 裸 id（实测无人会这样用），而创建答疑群是**真实建群并指定群主**的不可逆动作，且旧界面把多个「创建/打开」按钮按裸 session id 并排渲染。替代路径：关联由飞书消息建立，答疑群由 Pet 轮盘建立（上下文自明）。生命周期动作（解绑/归档/停止/重建/权限/确认执行根）全部保留。

### D7 · 逻辑抽到 `src/client/locus-view.ts` 纯函数模块

短码派生、家族聚合、两读法分组、筛选、可用性→文案映射全部做成纯函数，组件只负责渲染。

*为什么：* 旧 `settings.tsx` 已 3182 行，且现有测试几乎全是 `readFileSync` + `toContain` 的源码文本断言 —— 它们能证明"写了这句话"，不能证明"聚合正确"。纯函数可以真正断言行为（含同名入口、跨父会话代次、归档父会话等真实边界）。

### D8 · 首行不得以原始 ID 开头（可测约束）

名称可用 → 显示名称 + 短码；不可用 → 兜底名（有 `threadId` → `话题 · 19cd`，否则 → `入口 · a27b`）。**不写「群」**，因为 `chatType` 未持久化，写了就是猜。

*理由：* 与既有要求「不以不稳定名称替代真实标识」一致的方向上再进一步：宁可显式说明是兜底显示，也不猜一个看起来更像人话的名字。此条写成测试断言，防止回归。

### D9 · 名称与短码成对出现

实测同一父会话下会出现两个平台名同为「答疑 · DSH」的入口。因此名称永远与短码成对渲染，名称单独不构成身份。本轮因为用兜底名，同名问题不出现；但规则现在就固定，避免日后引入名称时退化。

## Risks / Trade-offs

- **移除设置页创建入口会改变既有使用习惯** → 替代路径明确（飞书消息 / 轮盘），且空态就地说明出处；BACKLOG B033 已就此定为 P1（理由是不可逆副作用）。
- **默认筛选可能让所有者以为入口丢失** → 列表内固定出口 + 数量 + 原因；筛选控件本身显示当前条件。
- **`settings.tsx` 现有大量源码文本断言会在重写时失效** → 属预期成本，随重写更新；同时把可行为断言的部分转移到 `locus-view.ts` 的纯函数测试，净减少文本断言的比重。
- **570px 内容列宽下信息密度高** → 行内两行式布局（身份/状态 + 会话），右侧固定动作列；身份列不参与收缩，让元信息先截断；长标题截断 + `title` 属性保留全文。
- **兜底名不如真名好看** → 这是"不新增能力"约束下的必然结果，已在 name 边界说明中如实呈现；日后若引入群名同步，必须同时解决同名，规则已在 D9 固定。
- **话题跳转依赖 `applink` 的 thread 形态** → 仓库内已有生产先例（`docs/notes/pet-locus-spike-findings.md:38` 指向 `dev-infra-server/service/ux-issue-group-dispatch.ts:127-144`），但本仓库没有调用点，参数形态需在实现时按该处确认；证明不了就退化为所属群，不伪造目标。
- **`provisioning` 是瞬时态且可能长期卡住**（主干 B040 已记录：provisioning 失败后运行期永久阻塞同一 endpoint，需重启 Host） → 面板按只读如实呈现「准备中」，不提供会破坏在建过程的动作；本轮不解决阻塞问题（B040 的范围），但 MUST NOT 把该状态显示成空白、跳过或伪装成活跃。

## Migration Plan

无数据迁移、无协议变更、无部署顺序要求：改动集中在 Web 客户端产物，随 `dsh build` 物化后刷新页面生效。

回滚策略：还原 `packages/dsh-pet/src/client/` 下相关文件（并重建客户端 bundle）即可，无持久化残留。

## Open Questions

- 筛选条件（父会话可用性、入口状态）是否需要跨会话记忆？本设计按"不落盘、每次打开都是默认"实现；若后续要求记忆，只影响客户端本地状态，不涉及 Host。
- 入口状态筛选（活跃 / 已停止·已失效 / 已退役）是否保留？规范只要求"按父会话状态筛选且不静默隐藏"，入口状态那一组是设计增量（对应 BACKLOG B030 要点 4 的折叠诉求），默认全勾等于不过滤。
