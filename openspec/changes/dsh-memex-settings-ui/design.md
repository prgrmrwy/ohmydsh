# 设计：DSH 记忆设置页

## Context

动机见 `proposal.md`「Why」。这里只记本设计所依赖的、已实测的现状与约束。

### 目标模型（已与用户确认）

```
一个远端仓库  ←→  一个记忆库（多个本地 workspace 可共用；personal 吃 ohmydsh + dsh-cockpit 是有意的）
其它仓库       →  各自自动派生
无仓库目录     →  fallback：按本地路径派生出各自的库，且不配置远端同步
```

## Goals / Non-Goals

**Goals:**

- 让「工作区 ↔ 记忆库 ↔ 远端存储」这条对应关系可见、可编辑、可复制。
- 让派生出来的库、以及已存在但未声明的库**可见且可声明**。
- 让 fallback 不再落进一个已配置远端的共享库。
- 用最小的新增授权面实现以上：只新增一条**只读** Host 通道，写入仍走官方 settings 通道。

**Non-Goals:**

- 不做卡片浏览与编辑（内核自带 `memex serve`）。归档 design 的「不做 GUI 面板」指的正是这一项，
  本设计只做配置面，不与其冲突。
- 不在页面上编辑 `bindings`、`autoDerive`、`publish`（见 D8）。
- 不自动发现工作区（不从会话历史或最近目录推断映射）——映射只由用户显式声明或由解析规则派生。
- 不新增比内核更严的卡片 slug 校验，不改卡片格式。
- 不改多库检索的并发/归并语义，不改守门规则本身。
- 不改 DSH core，不引 patch。

## Decisions

### D1. 页面落点是独立的 `settings.section`，不是 Plugins 里的配置卡

新增 `settings.section`（`id: dsh-memex`，`order` 取 25 左右——官方 `general 0 / models 10 / plugins 15 /
agent-presets 20`，本仓第三方 `egress-guard 290 / system-clock 300`）。

**备选**：`settings.plugins.tab` + `settings.plugin.item`（"插件配置"卡）。否决理由：那个位置的语义是
「宿主面插件的配置项」，而本页表达的是**工作区与库的对应关系**（含文件系统与 git 事实），不是插件参数；
且卡片 chrome 由别人拥有，呈现一张表格会与其形态冲突。

### D2. 导航图标用有界 DOM 适配，自绘 16px 线性 book

`label` 用「记忆」；图标按下述方式实现：MutationObserver 扫 `[role="dialog"] nav button`，按**可见文案**
匹配到本行 → 打上 `data-dsh-memex-settings-nav` 属性 → 配对 CSS 隐藏官方齿轮、用**自绘 16px 线性 SVG
作为 mask**（`background-color: currentColor`）绘制 book。

**为什么用 mask + currentColor 而不是 pet 的 emoji**：官方导航图标是单色线性风格，emoji 的彩色字形在
rail 态与深浅主题下都不协调；mask 自动跟随主题色与尺寸。不引入任何图片资产或运行时网络访问。

**为什么不用声明式契约**：契约里没有 icon 字段（见 Context）。接受齿轮是零成本选项，但用户明确要求 book。

**边界**：只标记自己那一行；匹配不到就不做任何事（官方齿轮照常显示）；释放时移除所有标记。
页面本身 MUST NOT 依赖该适配生效。

### D3. 配置读写走官方 `settingsScope`，不新增 Host 写能力

编辑 `scopes`（路径前缀、库路径、增删条目）通过 `ctx.settingsScope.bind({ namespace: 'dsh-memex' })`
的 `mutate` 提交：整份 `scopes` 作为一个带 revision 围栏的操作，Host 侧的既有校验与 last-good 语义
原样生效。

**备选**：自建写通道直接改 `settings.yaml`。否决：会绕过 revision 围栏与 Host 校验，并复制一份 settings
写入逻辑。

**结果**：本变更新增的 Host 能力**只有只读事实通道**（D4），页面在通道不可达时仍可编辑（D9）。

### D4. Host 侧一条 `/dsh-memex` 通道：取事实的端点 + 一个远端动作端点

一条 connection RPC 通道，端点：

- `stores`：即时采样并返回每个已知 scope 的库事实——库是否存在、卡片数、远端地址、自动同步状态、
  最近同步时间、该 scope 的来源（配置 / remote 派生 / 本地派生 / 命名空间下发现），以及内核版本视图。
- `resolve`：给定路径 → 解析出的 scope 与库路径（**纯查询**）。
- `remote`：按用户显式请求执行一个远端动作（见 D7）。

**前两个端点是纯查询**：不创建、不移动、不删除任何东西，`resolve` 故意对尚不存在的目录作答。
**唯一会产生副作用的是 `remote`**，且它只执行枚举过的远端动作、只委托内核 CLI。通道整体 MUST NOT
提供任何创建/移动/删除库的能力——它拿到的 scope 服务是**去掉了 `ensure` 的窄接口**，
所以接线错误也不可能把「打开页面」变成一次文件系统写入。

**事实来源用内核自己的 `sync --status`**，而不是直接读库内 `.sync.json`：`--status` 是内核文档化的
接口，避免与内核私有持久化格式耦合。成本是每个库一次子进程：并发上限 4，只在页面打开与手动刷新时采样
一次，不做轮询。

**安全边界**：回环与认证由 connection 层对每个 channel 统一施加（0.1.2 已删除逐 channel 的
`authority: 'loopback'` 注册参数），本通道不额外声明，也不放宽任何既有边界。

### D5. fallback 改为本地路径派生，名字取路径末两段

无仓库目录 → 派生名 = 路径末两段以 `-` 连接并归一化（与 remote 派生**同一形状**），库位于
`~/.dsh-memex/<派生名>`。

**为什么取末两段而不是 basename**：与「不同组织的同名仓库不共库」是同一条理由——
`…/work/learning` 与 `…/Documents/learning` 只取 basename 会静默共用一个库。

**为什么不共用一个 `local` 库**：用户已明确「本地路径可以各自一个」；共享库会让互不相关的本地知识
互相污染，正是本方案要避免的「混库产生噪音」。

**去重保护复用现有机制**：把本地派生的归属标识表示为 `local/<绝对路径>`，与 remote 的 `host/path`
同构，于是现有那条「不同来源派生出同名就报错」的守卫自动覆盖本地派生与远端派生撞名的情况。

**兜底**：归一化后不满足 scope 名规则时（例如路径含非 ASCII 段）落到一个固定的本地兜底库名，
行为与其他库一致——保持解析是**全函数**，不引入临时目录特例。

**碎片库的缓解**：库只在首次写卡时创建（既有行为），创建时工具返回值已给出「已创建新记忆库且未配置同步」
提示；设置页把它们列为可见条目。

### D6. 完整性约束分静态与动态两级

「同一仓库被两个 scope 认领」**不能**在配置期静态判定（remote 模式是正则，重叠不可判定）。因此：

- **静态**（`validateMemexSettings` 扩展，注册与实时编辑都走）：同一 `home` 被两个 scope 共用；
  同一 remote 模式字面重复出现在两个 scope → 拒绝并指明两方。
- **动态**（解析层）：一个 remote 同时匹配多个 scope 的模式 → **报错并指明两方**，
  替换今天「按配置顺序第一个命中即生效」的静默行为。

**取舍**：动态报错会让原本能跑的会话变成硬错误。这是有意的——静默 shadow 会让一个知识域的记忆写进另一个，
比报错更糟；错误信息同时给出解法（加显式映射或删掉重叠模式）。

### D7. 远端写入按状态分流，全部委托内核 CLI

| 库状态 | 页面动作 | 实际命令 |
|---|---|---|
| 未配置远端 | 配置远端（用户输入 URL） | `memex sync --init <url>` |
| 已配置远端 | 立即同步 / 拉取 | `memex sync` / `memex sync push` / `memex sync pull` |
| 已配置远端 | 自动同步开关 | `memex sync on` / `memex sync off` |
| 已配置远端 | 更换远端（独立动作 + 确认） | `memex sync --init <新url>`（内核内部走 `remote set-url`） |

**「不重建」由内核语义 + 我们的调用方式共同保证**：内核在 `--init` 里先 `rev-parse --git-dir` 探测，
存在就不 `git init`；remote 已存在则走 `set-url`。我们**从不**直接写 `.sync.json` / `.gitignore`，
因此「库内不出现本系统生成的私有文件」这条既有不变量保持成立。

**必须以稳定的 C locale 调用内核 CLI**（诊断新增，见下）。内核判定「remote 已存在」靠的是
**英文错误串匹配**（`err.message.includes('already exists')`）。本机 `LANG=zh_CN.UTF-8` 时 git 输出
「远程 origin 已经存在。」，该判定失效 → **对已配置远端的库重跑 `--init` 直接失败**（实测，exit 1）。
因此所有内核调用 SHALL 注入 `LC_ALL=C` / `LANG=C`：这使内核里依赖英文串的分支在任何机器上行为一致，
也让我们上报的错误文本确定（可被解析与断言）。**不使用「我们自己执行 `git remote set-url`」这条退路**
——那会绕过内核语义，把库内 git 配置变成我们的责任。

**实测确认（0.6）**：

| 场景 | 结果 |
|---|---|
| 未配置库首次 `--init` | 成功：建 `.git`、`.gitignore`、`.sync.json`，提交并推送，`origin` 就位 |
| 已配置库在 zh_CN locale 下重跑 `--init` | **失败**（英文串判定失效）；`/.git` inode、卡片 inode 与哈希、提交数**全部未变** |
| 已配置库在 `LC_ALL=C` 下重跑 `--init` | 成功：走 `set-url` 分支，提交并推送待提交的卡片 |
| `LC_ALL=C` 下 `--init <另一个 URL>` | 成功：`origin` 与 `.sync.json.remote` 一并更新为新地址 |
| 与远端存在不可合并的历史（同路径不同内容） | exit 1，stderr 给出解法提示；内核自行 `merge --abort`，**卡片哈希不变、无残留合并状态** |

**副作用（须在页面上如实呈现）**：`--init` 会把 `.sync.json` 的 `auto` 写成 **true**，
即「配置远端后自动同步默认为开启」。页面读 `--status` 显示 `auto: on`，并允许用户关闭。

**失败语义**：内核退出码非 0 时把 stderr 摘要原样上报；库目录与卡片保持原状，
不做任何回滚或清理（内核在合并冲突时会自行 `merge --abort`）。

### D8. 页面不暴露守门输入

`publish`（发布方向）是写入守门的 fail-closed 输入。页面不提供切换它的控件：schema 默认是 `external`
（守门开启），放松守门只能靠显式编辑配置。这样「页面能改的东西」与「降低安全性的东西」不重叠。

同理不在页面上暴露 `bindings` 与 `autoDerive`：前者改变模型的可达范围，后者改变解析路径，
都会在本期把页面从「对应关系的展示与编辑」拖成「全部配置的编辑器」。

### D9. 页面数据流与降级

- **设置值**（工作区路径、库路径、条目列表）来自 `settingsScope` 快照，是编辑与显示的真源。
- **库事实**（存在性、卡片数、远端、同步状态、来源）来自只读通道，按 scope 名与设置值 join。
- **通道不可达时**：库事实列显示不可用，**编辑仍然可用**（编辑不依赖通道）；不显示任何推测值。
- **保存以回读为准**：保存成功后显示 Host 回读到的值；被拒时显示拒绝原因并保留保存前的有效值。

### D10. `personal` 的隐式可写目标保持不变

无绑定配置时 `accessFor` 仍返回 `write = [当前 scope, 'personal']`，即派生库会话里的模型仍可**显式**
传 `scope: "personal"` 把卡片写进那个会同步的库。保留该行为：它是显式动作、且守门对
`publish: external` 的目标照常生效；本变更只改变 **fallback 的默认落点**，不改变可达范围语义。
`list()` 对 `personal` 的强制包含同理保留。

## Risks / Trade-offs

- **[导航图标适配随运行体升级失效]** → 适配失败静默降级为官方齿轮，页面不受影响；把它列入 DSH 升级回归项
  （与 pet 的同类适配一起看）。
- **[每个库一次 `sync --status` 子进程]** → 并发上限 4、只在页面打开与手动刷新时采样、不轮询；
  库数量级是十几个，不构成压力。
- **[fallback 改变导致同一目录的历史卡片与新库分家]** → 库只在首次写卡时创建；工具返回值已带
  「已创建新记忆库」提示；迁移说明写明「想让某目录继续留在 `personal` 就把它显式声明为 `personal` 的路径前缀」。
- **[本地派生碎片库]** → 只在首次写卡时创建；设置页把未声明库列为可见条目并提供声明动作。
- **[动态重叠报错让原本能跑的会话变成硬错误]** → 见 D6 取舍；错误信息给出可执行的解法，且该状态今天本就是
  「静默写错库」。
- **[设置写入被 Host 拒绝]** → 保留 last-good（既有语义），页面以回读为准显示，不呈现未生效值。
- **[声明动作误把命名空间下的既有库变成配置条目]** → 声明是显式动作，并在过程中要求确定发布方向；
  默认取保守值。
- **[上游 `--init` 的 locale 敏感判定]** → 已由「所有内核调用注入 `LC_ALL=C`」消化（D7）；
  把它同时列入内核升级回归项：升级内核后需复核 `--init` 的「remote 已存在」分支是否仍靠英文串匹配，
  以及该分支在已配置库上的实际行为。

## Migration Plan

**部署（按序）：**

1. `packages/dsh-memex` 落地 Web 半区与只读通道，`dsh.yaml` 更新该条目的版本与 note。
2. `dsh build` 物化；重启必须**脱离调用方进程**（`setsid`），否则中断会留下停机空档。
3. settings **无需迁移**：已声明的 3 个 scope 路由不变。可选：若希望某些无仓库目录继续留在 `personal`，
   把它们显式加进 `personal` 的 `pathPrefixes`。
4. 幂等校验：`node scripts/sync.mjs` 连跑两次报 `no changes`。
5. 冒烟：设置页打开、三个部分的数据、试解析、保存即时生效、通道不可达时的降级。

**回滚：**

`dsh.yaml` 该条目置 `enabled: false` → `dsh build` → 重启。库与卡片不受影响
（本变更不迁移、不移动、不删除任何卡片）；本地派生出来的新库可直接用内核 CLI 或 Obsidian 继续访问。

### D11. 一个工作区 → 多个入口，主入口唯一（2026-09-20 追加）

路由从「一个工作区恰好一个入口」改为「一个工作区**关联一组**入口，其中恰好一个是主入口」。

**依据是归档 design 自己的 D3**：「库的划分依据是**发布目标与访问权限**，而不是概念域」。
反过来说：同一个项目/概念域在发布目标或访问权限不同时，本来就该拥有多个库——内部知识一个、
可外发知识一个。原来的实现把"库按发布目标划分"读成了"一个项目一个库"，于是同一路径前缀被两个
scope 声明时会**静默取声明顺序里的第一个**（实测：`proj-internal` 胜出、`proj-external` 永远
路由不到且无任何告警）。这不是"不支持"，是"静默吞掉"。

**声明形状**：不新增 `workspaces[]` 这类第二张表（会和 `scopes[].pathPrefixes` 形成两个真相源），
而是允许同一工作区被多个 scope 声明，并在 scope 上加 `primary: true`。

**主入口的含义**：它是该工作区的**当前 scope**——召回流（索引卡是单库策划物）、
`organize`/`links`/`archive` 这些图级操作、以及默认读取与默认写入，全部只作用于它。

### D12. 可达 ≠ 默认动作（2026-09-20 追加）

附加入口只是**在可达范围内**：默认读取与默认写入仍只作用于主入口，写入附加入口必须由工具参数
显式指名。否则「把项目知识同时留一份到外部库」会变成默认行为，每张卡都会自动复制一份进外部库，
守门会被高频触发，而用户只是想让那个库**可选**。

这一条同时决定了页面文案：主/附的差别必须在界面上说清楚（主入口=默认与图级操作，附加入口=显式写入目标）。

### D13. 唯一性按可判定性分级，并禁止隐式优先级（2026-09-20 追加）

- **配置期可判定**：同一路径前缀、字面相同的 remote 模式 → 校验拒绝「同级多个认领者却没有唯一
  主入口」（0 个或多个主入口都拒绝）。
- **解析期才可判定**：不同 remote 模式是否命中同一仓库 → 命中多个时同样要求唯一主入口，否则报错
  并列出命中者（不再沿用上一版「多命中即报错」的写法，因为多命中现在是合法的）。

同一路径前缀被多个 scope 声明时，除主入口唯一性之外 MUST NOT 再有隐含优先级：**命名顺序、声明
顺序、条目长度都不得成为判据**。这一条是这次修复的核心——静默顺序正是最初那版的行为。

### D14. 页面的主语：一组工作区（2026-09-20 追加）

页面行从「一个记忆入口」改为「**一组共享同一关联入口集合的工作区**」。分组键是关联入口集合而不是
单个入口：这样最常见的「一个入口 + 一组工作区」仍是一行（当前部署就是三行），而当一个项目真的挂了
两个入口时，两个入口出现在同一行里成组呈现，不会被拆到两处。

行内两块按用户要求上下排：**上面是关联仓库集合**（这些工作区），**下面是记忆入口**（一个或多个，
主入口在前并标注）。视觉上仍是书架 + 竖脊线：脊线表示"这些工作区进这些入口"。

### D15. 页面的主语改为**真实 DSH workspace**（2026-09-20 第二轮追加）

D14 的「一组工作区」仍然是页面骨架，但**工作区从哪来**换了来源：不再由「配置里声明过的路径」
反推，而是直接读 DSH 自己的 workspace 注册表（`ctx.workspaceRegistry.list()`，即 sidebar 里那些
工作区，条目形如 `{id, title, path}`）。

理由：用户的工作区本来就是 DSH 概念，配置里的 `pathPrefixes` 只是它的**副本**。以副本为骨架会出现
两个尴尬：(1) 没在内存里配过的工作区（本机 8 个工作区里有 4 个）在页面上根本不存在，用户无法给它
挂入口；(2) 配置里写错一个路径就凭空多出一个"工作区"，而真正的目录在别的分组里。

**降级**：`workspaceRegistry` 是可选注入——用 `ctx.get('workspaceRegistry')` 惰性读（cordis 的 `get`
不需要 inject）。服务不存在时端点回答 `known: false`，页面退回 D14 的「按声明路径分组」形态，
MUST NOT 因此白屏或假装拿到了工作区列表。

**不丢配置**：声明了路径但不属于任何 workspace 的条目（历史遗留或手工路径）单独列在
「未对应工作区的路径」一块，MUST NOT 因为没有工作区就对用户隐藏——那样等于配置不可见、不可改。

### D16. 主入口默认取「该工作区派生的库」，但派生只是**提议**，不是写入（2026-09-20 第二轮追加）

每个工作区都要有一个默认主入口，否则未配置的工作区在页面上是无主的。默认值取解析器对该路径的
**实际派生结果**（`resolve(path)`：先看仓库 remote，再看路径末两段），所以页面显示的就是运行时会
用到的那个库名（实测：`dev-infra-server` → `aiby-dev-infra-server`，来自远端 `aiby/…`；
`~/Documents/learning` → `documents-learning`，来自路径）。

**MUST NOT 因为"展示默认值"就写配置**：未声明的工作区保持未声明，页面只把它标成「派生」。
只有用户真的要对它做点什么（挂附加入口、关掉兜底）时才落一条配置，并且必须**同时**把派生入口落成
`primary: true`——因为解析器一旦发现任何声明命中该路径，就**不再走派生分支**
（`configuredPathMatch` 命中即返回），只声明一个附加入口会**静默抢走主入口**，把该工作区的记忆
路由到另一个库。这是 D13「禁止隐式优先级」在页面上的延续：任何会改变路由的写入都要在保存前说明。

### D17. 兜底入口是「默认授予」，由入口自己的 `fallback` 声明可否，绑定只做加法（2026-09-20 第二轮追加）

`personal` 的语义从「无绑定时只作为写入目标」改为**默认授予的兜底入口**：它默认可读可写，因此
一个新工作区不需要任何配置就能用；页面把它显示成每个工作区下的一条附加入口（主入口就是 `personal`
时不显示，因为那是它自己）。

**关闭**由入口自己的 `fallback: false` 表达（新增 schema 字段，缺省即开启；只有显式关才落盘）。
关闭后 `personal` **读写都不可达**——"不使用一个入口"在用户直觉里就是两个方向都不用，只在写入侧
生效会留下"能读不能写"的半开状态。

**绑定不取消兜底，只做加法**：`bindings` 仍然是显式的额外可达范围。今天 `accessOf` 在存在绑定时
无条件 `read.add('personal')`，这条要改成「兜底与绑定各自独立相加」，否则 `fallback: false` 会被
绑定悄悄推翻。反过来，若某个绑定**显式**列出 `personal`，那是人的显式决定，可以覆盖默认关闭。

**关闭未声明工作区的兜底需要落一条声明**：兜底值挂在入口上，未声明的工作区没有入口可挂。
取舍是「要么写不进配置，要么落一条声明」——选后者，并按 D16 同时落主入口标记，保存前说明。

### D18. 列表态只显示名称与卡片数，展开才是详情；入口由选择器添加（2026-09-20 第二轮追加）

用户实测反馈：一个入口摊开是 8 行事实（路径、远端、自动同步、最近同步、发布方向、动作），
三个工作区就是三屏，"看不清有几个入口、每个多少卡"。改为：列表态一行只放**角色 + 名称 + 卡片数**，
点击该行展开成现在的详情；展开态是**临时状态**，不进配置。

**入口用选择器添加，从构造上消除重名**：实测点「+ 入口」得到的是一个空名字输入框，随手填一个已存在
的名字就会撞出 `每个条目的名称必须唯一`——这是页面把校验当交互用。改为从**候选列表**里选
（已声明但不在本组的库、命名空间下未声明的库、以及"新建库…"才出现的名字输入框），候选里不可能
出现重名，名称字段也就不再需要"事后报错"。

同一轮修掉的呈现缺陷：动作按钮被压成两行（`已复\n制`）、远端地址在窄列里断行、"关联仓库"
实际指的是路径（`partWorkspaces` 文案），以及 `.dshmx-*` 里缺少的 `min-width: 0` / `nowrap`。

### D19. `memex serve` 卡片浏览入口不在本 change（2026-09-20 第二轮追加）

用户要的"用 memex server 看卡片的入口"是**新的进程能力**：要按需 spawn 一个长驻子进程、占端口、
管理生命周期，且上游默认会重定向到托管站点（必须 `--local`，内部库尤其不能走托管）。它与"设置页
展示与配置对应关系"的风险面不同，按项目约定另立 change（`BACKLOG.md` 的 B045）。

本 change 只做到"把每个库的路径与远端可复制"，卡片明细留给那个 change。
