# Design — dsh-memex-delete-undeclared-library

## D1 只有宿主能删，且只删「发现型库」

删除是页面唯一的不可逆动作，因此判定放在宿主：`delete` 端点只接受一个 scope 名，然后按四道证明检查，
任何一道不过就拒绝并说明原因：

1. 该名字**不在**当前配置的 `scopes[]` 里（配置声明过的库要用「移除条目」，不是删目录）；
2. 解析结果的 `source` 必须是 `discovered` —— 命名空间下、有 `cards/`、无人声明；
3. 解析出的 home 必须**恰好等于** `<namespace>/<名字>`（防跨目录误删）；
4. 没有其它 scope 当前解析到同一目录（防删掉正在用的库）。

页面永远不传路径，只传名字，因此它不可能成为「任意目录删除」的入口。

## D2 确认态显示绝对路径与卡片数

用户要求「如果里面有内容可以给个绝对路径」。确认行显示 `将删除该目录及其中的全部卡片：<绝对路径> — N 张卡片`，
用户看到的就是宿主将要删的那个路径（来自 `stores` 端点的 `home`，与实际删除目标同源，不是页面自己拼的）。

## D3 不做回收站

被删的库如果配了远端，卡片仍在远端仓库里，可以从远端重新拉回；本地没有第二份时就是没了——这与用户
「确认就删掉」的要求一致。页面不在删除后自动建同名空目录，也不写入任何配置。

## 风险

- 误删一个「看起来没用」但某工作区其实还在派生的库：由 D1 第 4 道证明挡住（列表里出现的 discovered
  库若被某工作区解析，会出现在 `list()` 中）。派生名与已声明条目同名的情形（见另一处修复）不受影响：
  那种条目在配置里，第 1 道证明直接拒绝。
