## Context

动机见 proposal.md。与设计相关的现状（均为实测或读代码确认）：

- **认领**（哪些库挂在一个工作区上）由 `scopes[].pathPrefixes` / `remotePatterns` 表达。解析器取**最深**的匹配前缀，
  同一深度的所有认领者属于该工作区（`resolver.ts` `configuredPathMatch`）；没有路径命中时依次尝试 remote 模式
  （`configuredRemoteMatch`）、按 remote 自动派生、按本地路径派生。这一层本 change 不动。
- **工作区级决定**（主入口、记忆开关、兜底开关）却写在**库条目**上：`scopes[].primary / memory / fallback`。
  `personal` 同时认领 ohmydsh 与 dsh-cockpit，所以在 ohmydsh 关闭记忆会把 dsh-cockpit 一起关掉
  （`setMemory()` 实测，见 proposal）。条目级布尔值也表达不出「一个库在 A 是主、在 B 是附」。
- 页面模型里有几处以 `homeDir = ''` 调用 `claimersOf()` / `expandPath()`，包括 `setPrimary`、`detachEntry`、
  `routeOwnerOf`、`stageAssumedPrimary`、`attachEntry`。配置里的前缀常写成 `~/…`（本机 `personal` 就是），
  空 homeDir 会把 `~/x` 展开成 `/x`，这些前缀因此**匹配不到**：「移除」对 `~/` 写法静默无效，「设为主入口」漏掉
  以 `~/` 写法认领的兄弟入口。
- 对经 remote 模式命中的工作区，`workspaceViews()` 按路径找不到认领者，于是把**已声明的**库当成派生主入口展示。
  这时「增加附加入口」会再落一条同名条目，然后被重名校验拒绝。
- 设置经官方 `SettingsScope.mutate(ops)` 提交，一次调用就是一次原子的 namespace 变更。
- schemastery `Schema.object` 默认非严格，未知键透传（实测；审查 round 1 S1 也在源码里确认了这一点）。

**审查史**：round 1 指出按 cwd 前缀匹配的声明管不到 remote 路由；round 2 指出改成「按路由键精确匹配」后，路由一变声明
就失效，开关会从关变成开（fail-open）。两轮都判 REVISE 后按规则上报，用户选择**收窄 + 关闭优先**（2026-09-28），
也就是下面的 D1、D2。

## Goals / Non-Goals

**Goals:**
- 记忆、兜底开关成为**目录**自己的声明，不随库的其它工作区联动；主入口成为**路径认领组**自己的声明。
- 任何声明都**只能关、不能开**，且与路由无关：改认领、切换主入口都不会让**由声明关闭**的地方悄悄打开。
- 页面上的任何操作都不会悄悄打开一个关闭的注册表工作区（D3 通用守门，round 3 C1）。
- 经路径认领、派生或本地派生的工作区能在页面上把主入口换成另一个库（替换语义），切换不会让关闭的开关打开。
- 旧配置零迁移继续生效。

**Non-Goals:**
- 不改认领模型（库仍通过自己的 `pathPrefixes` / `remotePatterns` 挂到工作区）。
- **经 remote 模式认领**的工作区：主入口仍由条目级标记决定；页面不提供切换主入口或挂附加入口（见 D4）。
  一个条目的 `primary: true` 跨多个仓库生效的问题早于本 change 就存在，这里不解决（round 2 C2）。
- 路径声明管的是**目录**，不管仓库：同一仓库在别处的外部 worktree 或另一个 clone 不受某条路径声明影响，仍按条目级
  标记与默认值判定。这与现状一致（round 1 C1 在这个收窄范围内不再适用，见 review.md Rebuttals）。
- 不自动改写既有的条目级 `primary / memory / fallback`（页面在用户显式「打开」时除外，见 D3，保存前逐项说明）。
- 不改变名称维度的 `accessFor(scope)` / `resolveByName(scope)`，它们没有目录上下文，只读条目级。
- 不在配置期拦截**手改配置**造成的「条目级关闭不再作用于某目录」：这与 0.2.0 一致，用户在 2026-09-28 裁定（round 3 C1 的
  手改部分）。
- 浏览不按发起工作区做 Host 侧授权：Host 无法证明请求来源，用户在 2026-09-28 选择收窄（round 3 C2），见 D6。

## Decisions

### D1：`workspaces[]` 按路径声明，覆盖该路径下的所有目录

```yaml
dsh-memex:
  scopes: [...]            # 不变
  workspaces:              # 新增
    - path: ~/mydir/opensource/ohmydsh
      memory: false        # 只能写 false
    - path: ~/w/proj
      primary: proj-internal
      fallback: false      # 只能写 false
```

- `path` 必填，按 `pathPrefixes` 的规则规范化（展开 `~`、绝对化、去尾斜杠），规范化后 MUST 唯一。
- **`memory` / `fallback` 只接受 `false`**（schema 层面就是常量）。声明只能收紧，不能放开。「打开」的做法是删除关闭的来源，
  不存在「子目录写 true 盖掉祖先的 false」这种写法。
- 一条声明**作用于**所有按路径段落在 `path` 之下（含自身）的会话 cwd，**与该会话怎么被路由无关**：路径认领、remote
  认领、派生、本地派生一律适用。路由变了，声明照样生效。
- `primary` 是例外。它是**路径认领组**的属性，只在会话的路由为路径认领、且命中的最深前缀**等于**该 `path` 时参与
  主入口判定。
- **备选**（round 2）：按路由键精确匹配。否决：路由一变声明就失效，关闭的开关会打开（round 2 C1），相关的搬运规则
  也会覆盖共享键上的取值（round 2 M1）。

### D2：取值规则：关闭优先；主入口有声明则用声明，陈旧即拒绝

对一个会话（cwd、路由、认领者集合 C、主入口 X）：

| 决定 | 规则 |
|---|---|
| 主入口（仅路径认领） | 最深前缀 A 的声明给出 `primary` → 用它 → 否则 C 中唯一的条目级 `primary: true` → 否则 C 唯一成员 → 否则报错 |
| 主入口（其它路由） | 与现状相同（条目级标记 / 派生结果） |
| 记忆 | **关**，当且仅当：任一覆盖 cwd 的声明写了 `memory: false`，**或** X 的条目写了 `memory: false`；否则开 |
| 兜底 | **关**，当且仅当：任一覆盖 cwd 的声明写了 `fallback: false`，**或** X 的条目写了 `fallback: false`；否则开（绑定显式列出 `personal` 仍可覆盖，与现状相同） |

- **配置期校验**（`validateMemexSettings`）增加以下拒绝项：
  - `path` 缺失，或规范化后重复。
  - `primary` 不是已声明的 scope。
  - `primary` 不是该 `path` 的**精确**认领者（某个库的 `pathPrefixes` 规范化后等于该路径）。
  - `memory` / `fallback` 写成非 `false` 的值（schema 已拒绝）。
- 「同一前缀多认领者须有唯一主入口」放宽为：该前缀的声明给出了 `primary`（上一条已保证它是精确认领者），或（兼容）
  认领者中恰好一个条目级 `primary: true`。
- **解析时防御**：声明的 `primary` 不在 C 中时，解析 SHALL 报错并拒绝该路由，不忽略、不回落。配置期校验通过即保证不会
  出现这种情况，这条是给未经校验载入的配置兜底（round 1 M2）。
- 声明是路由无关的，所以只有删除声明才能打开由声明关闭的目录。**条目级**兼容字段不是：它跟着「谁是主入口」走，改认领、
  改路径、换主入口都可能让它不再作用于某个目录，round 3 C1 指出了这一点，0.2.0 就有这个问题。页面用 D3 的通用守门挡住；
  手改配置属于显式决定，不在配置期拦截，理由见 review.md 的 Rebuttals。

### D3：页面写操作

**关闭**记忆或兜底（工作区块路径 P）：写 `workspaces[P].memory|fallback = false`，不动 `scopes`，不落派生主入口。声明也覆盖 P 下的
子目录，所以提示行 SHALL 列出落在 P 之下的其它注册表工作区。

**打开**记忆或兜底：页面计算让 P 关闭的来源，逐个处理：

1. P 自己的声明：删除该字段；字段删空时删除整条声明。
2. 主入口 X 的条目级 `false`：删除该字段。同时，打开前以 X 为主入口、也是关闭状态的**其它注册表工作区**各写一条关闭声明。
3. **祖先路径 Q 的声明**：**拒绝**，并指向 Q。声明覆盖 Q 下所有目录，「Q 关、P 开」无法表达。
4. X 带 `remotePatterns` 时**拒绝**，并说明需要手改配置。页面无法逐个保持那些 remote 路由的关闭状态。

处理完后，页面在草稿上用 D2 重算，校验两件事：P 变为开启，其它注册表工作区的取值都不变。任一不满足就拒绝，并指出阻止保存的
来源。这是兜底判定，不管上面的规则是否漏了某种情形，都不会出现「打开一处、连带打开别处」。提示行列出每个被删除的来源，以及
「未登记在 DSH 中、原本也受它关闭的目录会恢复」这一后果。

**通用守门：不得悄悄打开。** 这是 round 3 C1 的修正，适用于页面的**每一次**保存，包括挂入口、移除、改路径、切换主入口、
「打开」，以及今后新增的任何改认领的动作。比较的对象按项分开（round 4 C1）：

- **记忆**：会话的 `memory` 布尔值。
- **兜底**：`personal` 在该工作区的**实际可达性**，读、写两个方向分开，**计入绑定覆盖**。兜底决定本身（默认授予）只是它的一个
  输入：绑定显式列出 `personal` 时，即使兜底关闭，它仍可达（`resolver.ts` `accessOf`）。只比较兜底决定的话，会把「条目写了
  `fallback:false`、但绑定保持可达」误判成关闭，再补一条声明把它真的关掉。

对每个注册表工作区 W 取两个值：

- **before**：取自 Host 的试解析结果。D5 新增 `personal: { read, write }`，由 Host 用真实解析结果计算，含绑定。
- **after**：在草稿上**保守地**重算，与 Host 用同一套纯函数，包括兜底决定、绑定（页面从同一份 settings 快照读取 `bindings`，不编辑它）
  和 `accessOf`。
  - 记忆：只要 W 被草稿中的某条声明覆盖就是关；W 在草稿里仍有路径认领时，它的主入口条目写了 `false` 也是关。
  - 兜底：同理先判定兜底决定，再按草稿主入口的绑定加回 `personal`。
  - W 在草稿里落出了所有路径认领（改由 remote 或派生路由，页面算不准）时，条目与绑定那一半按**开**、**可达**算。这个方向是保守的，
    只会触发补声明或拒绝。

对每一项（记忆；兜底的读；兜底的写），若 `before = 关/不可达`、`after = 开/可达`，而用户在这次编辑里没有对 W 的这一项做「打开」：

1. 在草稿里补 `workspaces[W].memory|fallback = false`，在提示里说明，然后再算一遍。
2. 补完仍是 `after = 可达`（草稿主入口的**绑定**显式列出了 `personal`，声明盖不过它）时，**拒绝保存**并指出那条绑定。
3. 某个 `before = 开/可达` 的注册表工作区因补声明而变关（它落在 W 之下）时，**拒绝保存**并指出冲突：既不为了保持一处关闭而关掉
   另一处，也不放任打开。
4. 其它由开变关的工作区在提示里列出。

守门针对的是**注册表中**的工作区。未登记的目录无法枚举：用户显式「打开」时的影响在提示行明说；其余情形下，D1 的声明或既有
条目字段都不会因页面操作而被删除。

**切换主入口**（旧 O → 新 N，块路径 P，当前认领者 C）只改认领与 `primary`：

1. **最深前缀 A = P**：从 O 的条目里去掉 P（O 在其它路径、祖先前缀上的认领不变；P 仍有更深的认领者，所以 O 不再属于 P）。
   N 精确认领 P：已认领则不变；已声明的库给自己的条目加 P；未声明的库或新建库落一条新条目。
2. **A 是 P 的祖先**（P 继承 A）：把 P **分出来**，C 中除 O 以外的每个认领者和 N 都精确认领 P；A 的认领不变。
3. **派生或本地派生**（O 没有条目）：N 精确认领 P。
4. **remote 认领**：不提供（D4）。
5. P 的精确认领者 ≥ 2 时写 `workspaces[P].primary = N`，否则清掉该字段。

切换**不会**打开任何开关。声明与路由无关，所以原有声明继续生效。原来的关闭若来自 O 的条目级 `false`，切换后它不再作用于 P，
由通用守门给 P 补一条关闭声明。N 的条目带 `false` 时，切换后 P 会变关，提示行 SHALL 说明。

规范性示例（均在 `/w` 下，O=`a`，N=`c`）：

| 切换前 | 切换后 |
|---|---|
| a:`[/w/p]`，b:`[/w/p]`，ws `/w/p` primary a | a:`[]`，b:`[/w/p]`，c:`[/w/p]`，ws `/w/p` primary c |
| a:`[/w]`，b:`[/w]`（块 `/w/p` 继承 `/w`，a 为主） | a:`[/w]`，b:`[/w, /w/p]`，c:`[/w/p]`，ws `/w/p` primary c；`/w` 的认领不变 |
| a:`[/w/p, /w]`（单认领者） | a:`[/w]`，c:`[/w/p]`；ws `/w/p` 无 primary |
| c:`[/w]`，a:`[/w/p]` | a:`[]`，c:`[/w, /w/p]` |
| a:`[/w/p]` memory:false（条目级） | a:`[]`，c:`[/w/p]`，ws `/w/p` memory:false |
| 派生库 d，无条目，ws `/w/p` memory:false | c:`[/w/p]`，ws `/w/p` memory:false（不变） |

提示行 SHALL 点名 O；情形 2 还要说明「P 从 A 分出来单独认领」。

- **备选**：切换只改角色，O 降为附加入口。用户明确选择了替换（2026-09-25）。

### D4：页面入口的动作分布

- 非主入口（已声明的附加入口、兜底行 `personal`）：展开区提供「设为主入口」，走 D3。
- 主入口（已声明或派生）：展开区提供「更换主入口」，候选清单与「增加附加入口」同源（排除已挂在该工作区的库，含「新建库」），
  选中后走 D3。
- **remote 认领的块**：不提供「设为主入口」「更换主入口」「增加附加入口」「移除」，并说明「这个工作区由仓库地址认领，在对应库的
  仓库字段里修改」。页面 MUST NOT 为它落派生主入口，因为它的主入口是已声明的库。记忆和兜底的「关闭」照常可用（写该块的路径
  声明）；「打开」遵循 D3。
- 所有行始终带角色徽标，取消「只有一行时不标注」的规则。
- **开关只在注册表工作区块上可点**（实现期决定，2026-09-29）：配置块（路径不在注册表中、未认领路径的库、注册表不可用时的退化块）
  只呈现记忆与兜底的状态并说明原因。声明需要一个工作区路径，守门也只比较注册表工作区；给配置块逐路径写声明会多一套规则。
- **在继承祖先路由的工作区上挂入口**（实现期决定，2026-09-29）：新入口成为 P 唯一的精确认领者，也就成了主入口；继承来的库不再
  出现在块下。不把 P 分出来让原库继续做主入口，这是挂入口，不是切换。提示行说明这件事，被关闭的项由通用守门补声明保持。
  「新增第二个入口时让原入口成为声明主入口」只适用于原入口精确认领 P 的情形（继承的库不是 P 的精确认领者，声明它为主入口
  过不了 D2 校验）。代价（round 6 M3）：原主入口条目上的关闭不再作用于 P，守门要为 P 补声明；新入口的绑定列出 `personal`，
  或 P 下有开启的注册表子工作区时，挂入口会被拒绝，拒绝说明指出新入口会成为主入口。
- **注册表不可用时不能改认领**（round 6 C1）：守门的比较对象为空，改认领可能悄悄打开真实工作区，所以页面拒绝保存
  改认领的编辑（比较草稿与已保存条目的 `pathPrefixes`），其它编辑照常。
- **`personal` 成为入口的显式性**（round 6 M5）：声明盖不过入口（`accessOf` 总是包含当前 scope 与同组认领者）。只有用户在
  工作区 W 自己的块上把 `personal` 挂上、设为主入口或选为替换时，W 上 `personal` 的可达才算显式决定；其它任何使 `personal`
  成为某注册表工作区入口、从而由不可达变可达的编辑都拒绝。
- **折叠分组只收注册表工作区**（round 6 M4）：配置块没有开关，收进「可以再打开」的分组会自相矛盾。
- `personal` 本身是该工作区的认领者（主或附）时不显示兜底行（round 1 S2）。

### D5：契约与页面模型

- `MemexResolveResult` 增加 `claim`：`'path'`（附最深前缀）、`'remote'` 或 `'none'`。页面据此判断块是否 remote 认领，以及是否继承祖先前缀。
  另增 `offBy`：记忆、兜底**决定**各自关闭的来源清单，每项是 `{ kind: 'workspace', path }` 或 `{ kind: 'entry', scope }`，供 D3 的
  「打开」使用。
  另增 `fallback`（兜底决定本身，布尔值）与 `personal: { read, write }`（`personal` 在该路由的实际可达性，计入绑定；当前 scope 就是
  `personal` 时两者都为真）。通用守门只用后者比较；页面的兜底开关显示前者，两者不一致时标注「经绑定 X 仍可读/写」。
  两项都只报告配置里已有的信息，不报告原始 remote URL（可能含凭据）。
- 草稿为 `{ rows, workspaces }`。保存在同一次 `mutate` 里分别 `set ['scopes']` 和 `set ['workspaces']`；旧页面 bundle 只 `set ['scopes']`，
  不会抹掉新声明。页面在草稿上用与 Host 同构的纯函数重算 D2，用来预览和生成提示；保存后以 Host 回读为准。
- 所有按路径比较的模型函数改用 Host 回报的 `homeDir`，不再传 `''`。

### D6：卡片浏览：页面按工作区收起入口，Host 不信任自报的工作区

round 3 C2 指出，调用方自报的 `workspace` 证明不了请求真的来自那个工作区。用户在 2026-09-28 选择收窄，所以：

- **不**给 `browse` 请求加 `workspace`，契约保持 `{ scope }`。Host 的判定不变：`resolveByName(scope).memory` 为关就拒绝，
  而且在启动服务进程之前拒绝。附带的未知字段一律忽略，不作放行依据。
- 页面按工作区决定呈现：工作区的实际记忆为关（Host 回报的 `memory`）时，它下面的入口不呈现「打开」。同一个库挂在记忆开启的
  工作区下时照常呈现。
- 只被路径声明关闭的目录，其库仍可被直接请求浏览。浏览是本机用户的只读查看，记忆关闭约束的是 agent 在该工作区的注入与工具。
  这一点在 spec 里写明。
- round 1 M1 随之失去对象：请求里不再有可伪造的工作区。

## Risks / Trade-offs

- [手改配置仍可能让条目级关闭不再作用于某目录] → 这是 0.2.0 的既有行为。手改是显式决定；配置期拦截需要拿到上一份生效配置，
  还要定义什么算「显式打开」，用户选择不做（2026-09-28）。CHANGELOG 建议：需要稳定关闭的目录改用路径声明，因为它与路由无关。
- [工具与注入的生效时机不同] → 如实写进 spec（round 3 M1），用测试锁定；不改代码。
- [绑定可以让兜底关闭后仍可达] → 守门比较实际可达性而非兜底决定（round 4 C1）；声明盖不过绑定时拒绝保存，不放任打开。页面不编辑
  `bindings`。
- [两处都能写关闭] → 关闭优先使两处永远不冲突，任何一处关就是关。页面只写声明；CHANGELOG 与 dsh.yaml note 写明规则。
- [声明覆盖子目录，关一个父工作区会连带关掉登记在其下的子工作区] → 这是「关闭优先」的保守方向。保存前列出受影响的工作区。
- [「打开」会删掉条目级关闭] → 页面为其它注册表工作区写声明保持关闭，并在草稿上重算校验；未登记目录的影响在提示行明说。被祖先声明关闭、或 X 带 remote 模式时，页面拒绝打开。
- [替换会让 O 从该工作区消失] → 保存前提示点名 O；保存前可「放弃」；库本身与卡片不受影响。
- [remote 认领的工作区不能在页面上切换] → 显式说明且不提供动作（fail closed）；本机当前没有 remote 认领。

## Migration Plan

- 无需迁移：未出现 `workspaces` 时，行为与 0.2.0 完全一致（关闭来源只有条目级字段）。
- 部署：`node scripts/sync.mjs`，二次运行无变化。Host 半区有变化，需要重启 DSH，重启必须脱离调用方进程（`setsid`）。
- 回滚：`dsh.yaml` 回退版本或设 `enabled: false` → sync → 重启。0.2.0 的 schema 透传未知键，`workspaces` 会被**忽略**，于是：
  - 靠声明关掉的记忆和兜底会重新打开；
  - 只靠声明决定主入口、且精确认领者 ≥ 2 的路径会被 0.2.0 校验拒绝（保留 last-good）。

  CHANGELOG 的回滚说明因此要求：回滚前把需要保持关闭的开关写回条目级，并为这些路径补条目级 `primary: true` 或删除多余认领。
  回归测试锁定「旧 schema 透传未知键」这一前提（round 1/2/3 S1）：把 0.2.0 的 `MemexSettingsSchema` 定义原样冻结成测试夹具，
  用它解析一份带 `workspaces` 的分节，断言解析不报错、`workspaces` 原样保留、`scopes` 的解析结果与不带 `workspaces` 时相同；
  再用新 schema 解析同一份结果，断言声明完整恢复。
