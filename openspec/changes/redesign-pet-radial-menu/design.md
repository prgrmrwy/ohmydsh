## Context

Pet 的快捷能力入口在 `add-dsh-pet` 中最初就写的是「轮盘」，但一期实现落地为矩形悬浮列表。矩形列表带来两个实际问题：它与桌宠形态不符；更重要的是，矩形菜单与桌宠之间存在物理间隙，指针在移动途中会触发 `mouseleave`，菜单随即消失——当时的缓解手段是加悬停桥接与延迟，属于对症下药。

本设计的几何、时序与交互边界已在可交互静态原型中逐条验证：`design-notes/wheel-mockup.html`。原型迭代过程中暴露了三个非显然的缺陷，均已在下方 Decisions 记录成因与结论，避免实现时重蹈。

约束：

- 轮盘必须留在 `shell.overlay` 层内以绝对定位渲染。挂到 `document.body` 会使 React 18 的事件委托失效——这一点在 `add-dsh-pet` 中已经踩过。
- 所有 CSS 选择器必须以 `dshpet-` 开头，不得触及 DSH 自身类名。
- 桌宠尺寸可配置（56/72/88px），几何必须随之缩放。

## Goals / Non-Goals

**Goals:**

- 用同心圆环替换矩形列表，使指针从桌宠到能力的移动路径连续无间隙。
- 交互边界与视觉边界严格一致：看得见的才响应，看不见的不响应。
- 移除入口处的通用二次确认，把安全判断交还给掌握上下文的 Skill。
- 简化任务面板，只保留唯一有明确用途的操作。

**Non-Goals:**

- 不改动 Host 侧的任务/调用模型、可信上下文、Skill 授权边界与投影机制。
- 不引入动画库或 canvas；用 SVG 与 CSS 过渡即可。
- 不处理超过 24 个能力的分页或滚动——超出即不渲染。
- 不改变 Skill 的启用/禁用语义，容量上限只是呈现约束。

## Decisions

### 几何：环宽 38px、呼吸间隙 20px、容量 6/8/10

以 72px 桌宠为基准。三个参数中，**间隙比环宽更关键**，这与直觉相反。

内圈每块的可用弧长为 `2πr/n`。加宽环宽只增大 `r` 的上界，而文字位于环带中线，`r` 变化有限：环宽从 38px 加到 48px，内圈仍只能容纳 4 个字。真正起作用的是把第一圈整体外推：

| 间隙 | 内圈中线半径 | 弧长 | 可容纳 |
|---|---|---|---|
| 4px | 59px | 62px | 4 字 |
| **20px** | **75px** | **79px** | **5 字** |
| 40px | 95px | 99px | 7 字 |

取 20px：内圈 5 字够用，最外直径 344px 仍可接受。40px 虽更宽裕，但会让轮盘在窄侧栏下大面积溢出。

容量 6/8/10 来自「每圈比内层多 2 个」，三圈合计 24。这是硬上限，超出不渲染。

**替代方案**：让外圈无限增长。否决——第四圈直径将超过 400px，在多数视口下大半不可见，且每块角度过小无法容纳文字。

### 可保持区域按实际渲染圈数计算

指针是否仍在轮盘上，判定为「到桌宠中心的距离 ≤ 已渲染最外圈半径」。

**这里有一个已在原型中复现的缺陷**：最初实现用固定三圈半径判定，导致只渲染一圈时，第二、三圈本应所在的空白区域仍被认为「在轮盘上」——轮盘不会收起。视觉边界与交互边界必须一致，因此半径取实际圈数：

| 能力数 | 渲染圈数 | 保持半径 |
|---|---|---|
| 6 | 1 | 94px |
| 7 | 2 | 132px |
| 15 | 3 | 170px |

**替代方案**：用 DOM 元素的 `mouseleave`。否决——扇区之间的接缝会触发假的「离开」，这正是矩形列表当初需要延迟兜底的原因。

### 唤起只绑桌宠本体，收起不设延迟

唤起绑在桌宠元素上。**最初绑在 344px 的容器上，使收起状态下桌宠周围一大片空白都成为热区**，轮盘会从很远的位置弹出。

容器同时需要 `pointer-events: none`，只让桌宠与扇区可交互，否则那个方形会遮挡底层页面。

收起不需要宽限期：圆盘从中心到最外圈**连续无断点**——呼吸间隙、扇区接缝都在半径之内。指针要离开必然连续穿过整个圆盘，因此「离开圆盘」即真的离开。这与矩形列表形成对照：那里需要延迟，正是因为元素之间存在真实空隙。

### 文字沿弧线切向排布，倒立则翻转 180°

规则：先按扇区中角切向对齐（`mid + 90`），归一化后若落在 90°–270° 区间（会上下颠倒），再加 180°。

**最初的 `mid ± 90` 判断是错的**。实测每一块都在倒转，不只是底部扇区：

```
扇区中角  -90° -> 归一 180°  倒转
扇区中角  -30° -> 归一 240°  倒转
扇区中角   30° -> 归一 120°  倒转
```

修正后，底部扇区（中角 90°）旋转为 0°——完全正立向上，符合预期。

标签按弧长截断，各圈约 5/6/7 字。优先使用 Skill 声明的 `petLabel`，未声明则用能力名，仍超限则截断加省略号。

**替代方案**：`textPath` 沿弧线弯曲排字。否决——小字号下弯曲文字可读性反而下降，且实现复杂度显著上升，收益仅为多容纳 1–2 个字。

### 逐圈渐入，第一圈立即出现

第一圈在展开瞬间可见，其后每圈延迟 0.08s。层次可被感知，但不推迟可操作时间——用户最常用的能力在内圈，不应为动画等待。

**替代方案**：0.3s 间隔。否决——三圈全部展开需 0.6s，实际使用中明显迟滞。

### 移除 `petConfirm`

入口处的通用二次确认无法区分破坏性与无害操作：它对每个能力都加一次点击，却把安全判断交给了不掌握上下文的 Pet 入口。

安全性应由 Skill 在其 Pet Task 内负责。`clean-worktree` 本就依赖 `wsClean` 既有的 dirty/merge/active 门禁——那才是能真正拒绝危险操作的位置，而 Pet 的确认框只能问「你确定吗」。

字段移除后，`SKILL.md` 中的残留声明被忽略而非报错，既有 Skill 无需修改即可加载。

### 任务面板只保留「进入执行会话」

现有三个按钮逐一处置：

- `Open full process` → 保留，并让整行可点。这是面板唯一明确有用的操作。
- `Open source` → 移除。它跳回发起任务的原会话，与 Pet 的任务管理无关。
- `Archive` / `Cancel` → 移除。归档属于高危操作，不应放在悬浮层这种易误触的位置。

移除归档不丢能力：归档可在 executor session 中完成，`reconcileArchives` 已经实时观察归档变化——终态任务自动归档，非终态任务保留并给出诊断，不把外部归档误判为「工作已取消」。这条链路在本变更前即已存在并生效。

## Risks / Trade-offs

**[轮盘在靠边时被裁切]** → 接受。已确认中心圆与桌宠始终完整可见，被裁的只是外圈。定位逻辑优先保证中心区域在视口内。

**[小尺寸桌宠下内圈文字更挤]** → 56px 桌宠的内圈弧长小于 72px 基准。缓解：几何参数随桌宠尺寸缩放，且截断逻辑按实际弧长计算而非固定字数。

**[归档入口消失后任务列表增长]** → 现有规则限制「每来源 scope 至多一个未归档任务」，不会无限堆积，但已完成任务会留在列表中。若后续确认碍事，合适的位置是设置页的诊断标签，而非悬浮面板。

**[破坏性能力单击即执行]** → 这是本变更的显式取舍。风险由 Skill 自身的门禁承担；若某个 Skill 缺乏门禁，问题在该 Skill，而非 Pet 应当补一道通用确认。

**[SVG 扇环路径在整环时退化]** → 只有一个能力时扇区跨越 360°，标准圆弧路径会退化为一个点。需用双圆弧构造完整圆环，原型中已验证该分支。

## Migration Plan

1. 先移除 `petConfirm`（Host 侧字段与解析、客户端两段式流程、示例 Skill 声明）——它与轮盘渲染无耦合，可独立验证。
2. 实现轮盘几何与渲染，替换矩形列表；同时移除 `SourceChip`。
3. 简化任务面板。
4. 设置页加入容量上限。

每一步均可独立回滚。字段移除对既有数据无破坏性影响：残留的 `petConfirm` 声明被忽略，不影响 Skill 加载。
