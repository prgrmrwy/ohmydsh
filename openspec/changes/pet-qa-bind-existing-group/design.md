# pet-qa-bind-existing-group Design

## Context

`pet-qa-group` 的入口是出站的：点 Q&A → Host 建群 → 绑定。它的信任模型完全建立在
「群是 Host 亲手创建的、初始只有本人与 bot、其余成员由本人拉入」之上——这就是那条
豁免全局 allowlist 的 Requirement 的全部依据。

本 change 把入口反过来：群早已存在，成员不是本人拉的，Pet 也不是群主。绑定链路可以
复用，**信任模型不能**。

既有约束（均已在主规范中）：

- qa 绑定豁免 sender allowlist，豁免严格限于该 chat，不外溢。
- 每个源会话至多一个活跃答疑群；作用域键以源会话构成，不以 chat 构成。
- 绑定失效走 fail closed，群内明示一次后静默；child 与历史保留。
- qa child 的目录约束是 prompt 级：Pet 在 seed 与每条提问中注入受管执行根。
- 未通过防线的入站消息静默丢弃，不向会话暴露 bot 背后有 agent。

## Goals / Non-Goals

**Goals:**

- 在既有群内 `@bot /bind <前缀>` 建立与 `pet-qa-group` 同形态的绑定。
- 绑定后该群的提问、投递、表情、失效、目录约束与 Q&A 建群完全同路。
- 群与会话严格 1:1，双向占用即失败。
- 前缀解析 fail closed 且不泄露任何未命中会话的存在。

**Non-Goals:**

- 解绑命令（归档 Task 即解绑，已是既有语义）。
- 跨群迁移、重新绑定到另一个会话（先归档再 `/bind`）。
- `/bind` 之外的任何斜杠命令——留口不实现的原则沿用二期1。
- 让非 allowlist 成员发起绑定。
- 任何群管理能力（改名/踢人/解散）：Pet 在既有群里只是普通成员，本能力也不需要。

## Decisions

### D1 `/bind` 只认 allowlist，绑定后全群继承提问权

`pet-qa-group` 豁免 allowlist 的理由是「群由 Host 创建，成员只能被本人信任链拉入」。
既有群不满足该前提：成员可能有几十人，且都不是本人为此目的拉入的。

因此拆成两段信任：

```
/bind 命令本身        → 仅 allowlist（= 机器所有者本人）
绑定成功之后的提问     → 全群成员（继承 qa 既有豁免）
```

后半段的依据从「本人亲手拉人」换成「**本人亲手把这个群绑上了**」——一次显式的、
针对这个具体群的授权动作，与 Q&A 里「本人亲手建群」等价。

替代方案（否决）：（a）`/bind` 的群不豁免 allowlist，只有名单内的人能问——安全但
废掉了「让群里其他人问」这个诉求，绑定就失去意义；（b）任何群成员都能 `/bind`——
等于任何人可以把 bot 接到任意会话上，直接越过所有者。

**用户已确认取此方案**，并明知其代价：在一个 N 人群里 `/bind`，等于一次性给 N 个人
开了触发权，而 child 持有源会话的全量工具面。spec 如实声明，不制造虚假边界。

### D2 群与会话严格 1:1，双向校验

`pet-qa-group` 只约束了会话侧（一个会话至多一个群）。`/bind` 引入群侧的对称问题：
一个群被绑到两个会话，或一个会话被两个群绑。两者都会让「这个群的提问该给谁」
失去唯一答案。

判据统一为**对应 scope 存在未归档 Task**（用户明确指定）：

```
群侧   chat_bindings 存在该 chatId 的 qa 行，且其 activeTaskId 指向未归档 Task
会话侧 findActiveTaskByScope(qa:<sessionId>) 命中
```

任一命中即固定失败并回执说明。归档是唯一的解绑手段——这与 `pet-qa-group` 已确立的
「归档 qa Task = 结束答疑群」一致，不引入第二种解绑概念。

绑定行已失效（`qaInvalidatedAt` 存在）时视为未占用：那是个无法应答的死绑定，`/bind`
SHALL 归档其 Task 后继续，与 Q&A 动作面对同样情形时的处理一致。

### D3 前缀解析：fail closed 且不泄露

`<前缀>` 是**用户在群里打出的字**，这是本 change 唯一的新输入面。约束三条：

1. 前缀只用于**查找**，不作为任何其它操作的输入；
2. 匹配范围是全部未归档 session（已归档的 fork 不出来）；
3. **无匹配与多匹配返回同一句回执**，不透露匹配数量，也不透露任何未命中会话的存在。

第三条是用户显式要求的加严版本。理由：回执一旦区分「没找到」与「找到 3 个」，就成了
一个可枚举信道——尽管 `/bind` 仅限 allowlist、暴露面很小，但既然要写进 spec，就没有
理由留这个区分。前缀下限 6 位与 UI 短 id 徽章一致，且接受更长前缀以化解撞号。

### D4 复用建群事务的后两步，跳过建群

`createQaGroup` 现有三步：fork → 建群 → 写绑定。`/bind` 的群已存在，因此是：

```
Q&A:    fork child → im +chat-create（指定本人为群主）→ 写 kind:qa 绑定
/bind:  fork child → （群已存在，跳过）              → 写 kind:qa 绑定
```

失败回收沿用同一逻辑：fork 成功而写绑定失败时释放 child。比 Q&A 更简单——没有
「群已建好但收不了场」这个窗口（那正是 D2 把 fork 排在建群之前的原因），因为这里
根本不建群。

绑定行新增一个来源标记区分两者。**它不改变任何下游行为**，只用于诚实展示：`/bind`
的群 Pet 不是创建者也不是群主，设置页与诊断应如实呈现，避免用户以为 Pet 能管理它。

### D5 命令识别发生在「未绑定群」这一格

二期1 的入站防线对未绑定的群是静默丢弃。`/bind` 必须在那之前被识别，否则命令永远
到不了。识别点因此放在路由判定之后、丢弃之前：

```
mention 命中 → 去重 → 水位 → 消息类型
  → 该 chat 有 qa 绑定？ → 是：既有 qa 投递路径（不变）
                          → 否：是 /bind 命令且发送者在 allowlist？
                                → 是：进绑定流程
                                → 否：按既有规则处理（静默丢弃 / workspace 路由）
```

非 allowlist 发送者的 `/bind` **静默丢弃**，与其它未通过防线的消息一致：回一句
「你无权绑定」等于向未授权者确认了 bot 背后有 agent，违反既有 Requirement。

### D6 回执发在群内

绑定成功的回执发到群里而非私聊所有者：群成员有权知道本群接入了一个能看到某段工作
上下文、并能在真实工作区里执行命令的 agent。悄悄接入更省事，但不诚实。

回执内容：已绑定、child 以源会话**最近一个完成 turn** 为准（in-flight turn 不进种子，
沿用 fork provider 的既有行为）、以及此后群成员 @bot 即可提问。

失败回执（1:1 冲突、前缀不唯一/无匹配、源会话不可 fork）同样发在群里，因为发起者
就在群里且已通过 allowlist——此时 bot 是 agent 已不是秘密。

## Risks / Trade-offs

- [在 N 人群 `/bind` 等于一次性给 N 人开触发权] → 信任前移到「本人显式绑定这个群」；
  spec 如实声明不承诺能力边界；建议实现时在回执中报出当前群成员数，让所有者当场
  看见自己授权了多大范围（不阻断，仅告知）。
- [既有群的历史消息与成员构成不可控，提示注入面大于 Q&A 群] → 与上一条同口径；
  child prompt 的「修改先确认」条款原样适用（真机已验证其完整闭环）。
- [`/bind` 是模型不可见但用户可见的新命令面] → 仅此一个命令，显式动词，且只在未绑定
  群生效；绑定后同一串文本不再被解释为命令。
- [前缀撞号] → 接受任意长度 ≥6 位前缀；回执不泄露数量，用户自行补长。
- [用户误把群绑到错误会话] → 1:1 + 归档解绑提供退路；回执报出源会话标题供当场核对。
- [Pet 在既有群里不是群主，无法自我清理] → 本能力不需要任何群管理权限；绑定失效
  只停止投递，群本身归用户处置（与 `pet-qa-group` 存量群的处理口径一致）。

## Migration Plan

1. `chat_bindings` 加一个可选来源标记字段，加性变更，存量行读作「Pet 建群」。
2. 无行为回滚风险：`/bind` 不可用时既有群的消息仍按原规则处理（静默丢弃）。
3. 回滚 = 移除命令识别分支；已建立的绑定仍可正常服务，因为它们与 Q&A 绑定同形态。

## Open Questions

- 回执是否报出群成员数（D1 风险项的缓解）——实现时定，倾向报，成本极低。
- 前缀是否允许匹配 executor / child 会话本身（而非普通用户会话）——倾向只允许普通
  会话，避免把一个 qa child 再 fork 一层；实现时确认 session 类型可判定。
