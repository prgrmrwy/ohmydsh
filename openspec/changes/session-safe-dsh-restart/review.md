### 🟡 Moderate

#### R3-M1. The handshake guarantees "Host not yet stopped when the command returns", but nothing in the design delays `stop` until the launcher/result is out; `DSH_RESTART_GRACE_MS` is passed but unused, so two normative scenarios are untestable as written

**Evidence**
- Sequence: orchestrator writes `orchestrator-ready`+`ready` (`design.md:62`), *then runs the normal preparation stage*, then waits for `go` before stop (`design.md:62`); the launcher, upon seeing `ready`, writes `scheduled`→`go`→prints→returns (`design.md:61`, `spec.md:66`). The preparation stage (`main.mjs:112-122`, spawned `dsh-server-bin.mjs`) is the only thing between `go` and `doStop()` (`main.mjs:123`); there is no fixed delay or launcher-done marker anywhere.
- Therefore, if preparation is fast (autoUpdate disabled/no-update, prerequisite skipped, runtime already resolved/cached — exactly the normal plugin-restart case), the orchestrator can reach `doStop` within milliseconds of `go` being written, i.e. before the launcher's print/return and before the bash-tool result reaches the Host.
- Two normative scenarios assert the opposite as a THEN: `spec.md:20-24` ("旧 Host 在命令返回时仍为 `owned`") and `spec.md:74-78` ("命令返回时旧 Host 尚未收到停止信号，orchestrator 在独立 scope 中继续"); `design.md:133` (a) repeats it as a real-systemd assertion ("launcher 在 ready 后返回且早于 Host stop"). None follows from the SHALLs in `spec.md:64,66` or D2/D3.
- `DSH_RESTART_GRACE_MS` is defined in the internal env protocol (`design.md:60`) and listed as a calibratable constant `GRACE 3s` (`design.md:166`) but is never referenced by D2 step 4/5, D3, or any spec requirement; grep of the design shows only those two occurrences.
- Consequence: test authors cannot write the three assertions deterministically (they would either inject a grace the design does not authorize or observe flakiness); and the user-visible promise "返回 0 只表示已排程" loses its delivery step — the agent may see a killed tool call even though the restart proceeds. This is the exact, still-open residue of round-1 S1/round-2 S1; it is now a testability contradiction rather than only a suggestion.

**Fix (Required Change RC1)**: add the missing deterministic step. #### R3-M2. The ready/go/abort marker protocol is under-specified: nonce generation/transport/validation, marker file content schema, `go`-write failure, abort-write failure, and abort/go precedence are undefined, though `spec.md:70` makes them normative

**Evidence**

#### R3-M4. Concurrent restarts remain only partially protected: two orchestrators that both pass the pre-stop re-probe can stop each other's Hosts, and history has no rule for the resulting concurrent terminal runs (carry-over of R2-M11)

B then starts D. Both receipts can be `ready`, with PIDs that are already dead.

#### R3-M7. Timing constants are simultaneously normative in the spec and "calibratable without contract change", and the 5 s handoff budget is not reconciled with the Host's own 5 s shutdown grace plus provider quiescence

**Evidence**
- `spec.md:66` pins `READY` (5 s) and `GO` (30 s) as fixed SHALL bounds; `spec.md:68` pins the capability-probe bound (5 s); `spec.md:120` pins the handoff wait ("固定上限 5s"). `design.md:166` says "常量取值需真机校准 … 实施时在 WSL 记录测量，仅调整常量不动契约". - `HANDOFF 5s` vs the Host's own shutdown budget: `$COMPAT/dsh/lib/profile-boot-BZ2ZjNWi.js:12` sets `PROCESS_SHUTDOWN_TIMEOUT_MS = 5e3` (grace *before* the app is forced to exit), and the provider "terminates every running managed range and terminal session and **awaits quiescence**" (`dsh-subprocess-local/README.md:66`) with "Linux direct exit has no independent deadline … can keep disposal pending indefinitely" (`:149`). `stopServer` returning "port empty" (`process.mjs:199-200`) can therefore precede actual process exit by up to the Host grace plus provider quiescence, which may legitimately exceed 5 s. #### R3-M8. The central systemd mechanism is only partially pinned: the cited measurement covers launcher exit, not the Host-dispose kill of the `systemd-run` client that the design itself says will be killed; the real-systemd row must name that kill explicitly

**Evidence**
- `design.md:9` reports: launcher uses `spawn(systemd-run,…,{stdio:'ignore'})`+`unref()`; the outer process returns in ~21 ms; the scoped process keeps running after outer exit and the scope is collected at the end. That is the *launcher-exit* case.
- The actual event that matters is different: `design.md:60` says "systemd-run 客户端留在旧 Host managed range（Host 停止时会被清理），内部 orchestrator 位于新 scope（实测存活）". The Host's disposal kills the client as part of the old managed range (`dsh-subprocess-local/README.md:66`), whereas the scoped orchestrator is the client's **child** in a different scope. The reviewer confirmed the man-page model (scope command executes with systemd-run as parent and inherits the caller's environment; scope lifetime is cgroup-based) and it is plausible that killing the client leaves the child untouched — but no cited measurement or test proves it, and `man systemd-run` does not specify what happens to the scoped command when the client is terminated.
- `design.md:133` (b) says "orchestrator 在父 range 清理后存活并完成 stop→fake start", but a test author can satisfy that by killing only the launcher process/its shell, never the `systemd-run` client; the row must say which processes are killed (client SIGTERM then SIGKILL, mimicking provider disposal) and assert the scope/orchestrator survive.
- Additional properties worth pinning in the same row: the scope unit name `dsh-restart-*` must not match the provider regex `/dsh-(?:subprocess|terminal)-\d+-[0-9a-f]+\.scope/` (so a nested/accidental relabel cannot misclassify a managed range), and the replacement Host (child of the orchestrator) keeps the scope active after the orchestrator exits until the Host stops, then the scope is collected (`design.md:133` (d) covers activity/collection but not the "client killed" precondition).
- The transient-service rejection rationale in `design.md:65` ("主进程退出会清掉同 cgroup 残留") cites no systemd documentation; `systemd.kill(5)`'s default `KillMode=control-group` is the citable reason, and the scope-vs-service distinction is exactly what the test must protect.

**Fix (Required Change RC8)**: extend the D2/D3 measurement statement and the real-systemd row: explicitly SIGTERM then SIGKILL the `systemd-run` client while the orchestrator runs, assert orchestrator survival + `stop→fake start` + receipt, assert the scope-name non-match, and keep the manual WSL E2E as the final gate. Cite `systemd.kill(5)` in the transient-service rejection.
