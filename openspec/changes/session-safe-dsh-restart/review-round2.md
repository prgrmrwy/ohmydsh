### 🔴 Critical

#### R2-C1. `scheduled` vs `go` ordering contradicts itself across the normative requirement, the design, and the fail-closed requirement; following one text breaks the core safety guarantee

**Evidence**
- `spec.md:55` (R2): "launcher 收到 `ready` 后才写 `go`、写 `scheduled` receipt、打印并返回" — go first, then scheduled, then print/return.
- `design.md:65` (D2 step 3): "收到 ready 后写 `<id>.go`、追加 `scheduled` receipt、打印…，返回 0" — same order.
- `spec.md:141` (R4): "首个 `scheduled` 事件必须在写 `go` 与任何 stop/UI 清理之前落盘；该写入失败时不得写 `go`" — scheduled strictly before go.
- `design.md:105` (D6): "launcher 预检可写 → 排程握手 → 写 `scheduled` → 写 `go` → 返回" — scheduled strictly before go.
- These are the four places that implementers and test authors must read, and they specify opposite orders for the single safety-critical handoff step.

**Consequence**
The whole point of the preflight + scheduled-before-go rule is that no Host stop may happen without a persisted `scheduled` record. If the implementation follows R2/D2 (go first), a normal failure mode — disk full / `$DSH_HOME` remount / quota hit between the two writes — has already released the orchestrator to stop the Host; the launcher then fails to persist `scheduled`, the caller may never see its result, and the exact "unrecorded/unverifiable restart" class returns. It also makes R4's mandated failure scenario unwritable: the test cannot simultaneously assert go-before-scheduled and scheduled-before-go.

**Fix (required)**
Pick one canonical order and use it everywhere: `ready` → append `scheduled` (fsync as needed) → write `go` → print → return. Rewrite `spec.md:55` and `design.md:65` accordingly; keep `spec.md:141`/`design.md:105` as-is. Add the missing scenario: "GIVEN ready received, WHEN the `scheduled` append fails, THEN no `go` is written, Host is not stopped, non-zero exit with actionable error." D10/receipt tests must pin the exact append order.

#### R2-C2. The scheduled child's process-handle and stdio lifecycle is undefined: without `unref()` the launcher cannot return; after the launcher exits, the orchestrator's inherited stdout/stderr pipes are broken, and a write after `stop` crashes it with an unhandled EPIPE (typically between stop and start)

**Evidence**
- `design.md:56-64` (D2 step 2) says "以 argv 数组 spawn（不等待、不拼接 shell）" but says nothing about `unref()`/`detached`/`stdio`. `design.md:65` requires the launcher to "返回 0" after the ack; `design.md:91` requires the orchestrator to call the same `performRestart`; `design.md:89` keeps "UI 策略与 plugin 列表输出沿用现有实现", i.e. the orchestrator logs to its stdout/stderr (plugin-list output can be several KiB).
- Verified Node semantics in this environment:
  - a spawned child with default/pipe or `stdio:'ignore'` keeps the launcher's event loop alive until it exits (measured 1.02 s vs 0.01 s after `child.unref()`), so a naive `spawn(systemd-run, …)` means `runLauncher` returns but the process — and therefore the DSH bash tool call — hangs past the ack, until the Host dispose kills the whole range; the promised "打印并返回 0" never reaches the caller;
  - after the launcher exits, its pipe read ends close. A child that inherited the pipes (default `pipe` or `inherit`) dies on its first write after the Host/launcher side is gone: reproduced `Unhandled 'error' event … Error: write EPIPE`, exit code 1. The orchestrator's first guaranteed post-handshake write is the `doStop` log (`main.mjs:58-63`, line 62 logs after stop; D4 keeps this via `design.md:89`), i.e. **after the Host has been stopped and before the replacement Host is spawned**.
- This is the same failure class the change exists to eliminate: a Host that is stopped with no replacement, now with a receipt ending at `stopped`/`process-exited`. The artifacts do not mention stdio redirection, EPIPE handling, or `unref` anywhere, and `proposal.md:36`'s module list has no "stdio/log sink" responsibility.

**Fix (required)**
Make the scheduler's process/stdio contract explicit in D2/D4 and the spec/test plan:
1. spawn `systemd-run` with `stdio: 'ignore'` (or file-backed stdio, e.g. `$DSH_HOME/dsh.log` fds) and `child.unref()`; keep the `'exit'` listener only for the bounded ready wait;
2. the orchestrator must not write to inherited stdout/stderr: install `process.stdout/stderr` error handlers and route all progress/plugin-list output to a file-backed sink (`dsh.log`/`dsh-startup.log`) while the receipt stays JSONL;
3. add tests that would have caught both defects: (a) real-systemd row asserts the launcher returns within ready+ε while the orchestrator keeps running after the launcher's pipes are gone; (b) a harness row closes the launcher side, then asserts the orchestrator completes stop→start and appends `ready`; (c) unit row proves no non-unref'd child handle remains after `runLauncher` returns.

- `design.md:40-42` treats a readable non-matching cgroup with no markers as external; `proposal.md:7`/`design.md:48` describe the residual risk of stripped markers only as "非 Linux".
- But the provider falls back to a warned PGID mode when the user manager is unreadable or `systemd-run --expand-environment=no` is unavailable (`$COMPAT/dsh-subprocess-local/README.md:150`); in that mode the Host's shell calls do **not** run in `dsh-subprocess-*` scopes, so cgroup evidence does not exist on Linux either. A session call with markers stripped would fall through to the external sync path and reproduce the original half-restart on such a Linux host.
- The capability probe (`design.md:74-76`) only proves that `systemd-run --scope` accepts the flag set, not that the provider is in native ownership mode, so a passing P0 probe does not make the cgroup substrate true.

**Fix:** declare the cgroup substrate prerequisite (native provider ownership) in R1/D1, add "Linux without provider-native scopes" to the recorded residual risk and upgrade checklist, and decide whether the launcher can/should detect provider mode (e.g. by refusing when it cannot prove the substrate on a session call, or by documenting the fail-open direction explicitly). Add a scenario for the old-systemd Linux residual.

#### R2-M3. `dsh history`'s "latest run = latest event time" is polluted by orphaned orchestrators, and the incomplete/abandoned rule mislabels live restarts and ignores the "non-terminal but Host still owned" case

- `spec.md:143`: "以 restartId 分组、按最后事件时间选最新 run … 非终端且端口无 owned Host 时显示 incomplete/abandoned." `design.md:98,107` repeat it.
- Race 1 (orphan event): if a launcher times out or dies before `go`, its orchestrator keeps waiting up to 30 s (`design.md:66,68`). Meanwhile the user retries and a newer run completes successfully. The abandoned orchestrator then appends `failed(go-timeout)` with a **later** timestamp than the newer run's `ready`, so "latest by last event time" selects the older, abandoned run and shows a failure as the most recent restart — the opposite of the requirement's intent. (Round 1 M4 asked for run identity; the id exists, but selection is still time-of-event rather than time-of-run.)
- Race 2 (live restart): another session running `dsh history` while a restart is between `stopping` and `starting` sees a non-terminal tail and an empty port and gets "incomplete/abandoned" although the orchestrator is alive and working. There is no liveness/age guard.
- Gap 3: an orchestrator that dies after `go` but before `stop` leaves a non-terminal tail, the Host still `owned`, and the caller still connected (`design.md:95-99` only covers death after stop). No display rule exists for that state (it is the most common pre-stop failure shape).
- The staleness scenario (`spec.md:163-167`) only covers "old `ready` + later external startup", not any of these.

**Fix:** select the latest run by run creation time (embedded in `restartId` / first event) and define precedence for late events of superseded runs; define liveness/age for in-flight runs (e.g. non-terminal + orchestrator PID/scope alive ⇒ "in progress", not abandoned); add a display rule for "non-terminal + Host still owned" (`scheduled/ready` + caller still connected ⇒ "orchestrator stopped before Host stop; Host untouched"); add scenarios for the orphan-event and in-progress cases.

#### R2-M4. Handshake failure leaves two terminal `failed` events for one run; the normalized terminal state is nondeterministic, so the no-ack scenario's expected receipt will flip after up to 30 s

- Launcher no-ack path writes `failed(schedule, no-ack)` and kills the client (`design.md:66`); if the orchestrator did start, it writes `failed(schedule, go-timeout)` on its own timeout (`design.md:68`). Both belong to the same `restartId`, and `spec.md:143` has no rule for choosing between multiple terminal events of one run, nor for "last event wins" vs "first failure wins".
- Scenario `spec.md:67-71` asserts the no-ack receipt shape; a test run at T+3 s sees `no-ack`, a run at T+35 s sees `go-timeout` — the same command produces different machine-readable outcomes depending on when history is read. The kill of the systemd-run client is explicitly "尽力而为" and, for `--scope`, killing the client is not a defined scope stop (the man page describes systemd-run as the command's parent; no contract says the scoped command receives a signal or that the scope is stopped), so the orchestrator can survive to write the second event.
- Related: there is no cancellation/abort protocol between launcher and orchestrator (design:68's "go 在 grace 前被移除/不存在时不停止 Host" has no defined actor — R2-S7).

**Fix:** define a single terminal event per run and precedence (e.g. launcher writes `failed(schedule, no-ack)` and an `<id>.abort` marker; orchestrator polls the marker, exits without its own event or with `reason=aborted` and history prefers the launcher's event); add a scenario that asserts the final state after the full 30 s window, not only at launcher-return time.

#### R2-M5. The state directory (ready/go/scheduled coordination) has no location, mode, ownership, validation or cleanup contract; it is a local-trust boundary and an unbounded leftover surface

- `spec.md:55` mentions "状态目录" only once, inside the orchestrator's pre-ready check; `design.md:55` preflights the receipt file but not the state dir; `design.md:61-68` passes `--state-dir <dir>` and defines `<id>.ready`/`<id>.go`; `design.md:108` says the orchestrator cleans markers at the end, and calls leftover markers harmless because ids are unique.
- Undefined: where the directory lives (under `$DSH_HOME`? `/tmp`?), who creates it with what mode/owner, symlink/TOCTOU handling, what the launcher does if the dir is pre-created by another user or is world-writable, what happens to markers when the launcher dies after ready and the orchestrator times out, when orphaned state dirs are swept, and how the orchestrator validates that the `ready`/`go` pair belongs to its own run rather than a replayed/stale file. A predictable directory in a shared location lets a local user delete/replace `go` (cancelling restarts) or pre-create `ready` (making the launcher claim a schedule that does not exist) — on a multi-user Linux host this is a real trust boundary; accepted unique ids do not fix permissions.
- Cleanup is only "orchestrator at the end" (`design.md:108`); a launcher crash before go plus an orchestrator timeout is covered, but a scope kill/OOM of the orchestrator leaves the directory forever, and there is no bounded sweep or `dsh history` view of stale coordination state.

**Fix:** add a requirement/scenario: state dir = `$DSH_HOME/dsh-restart-state/<restartId>/`, created by the launcher with 0700 (under the 0700 home), never reused, validated (owner/mode/expected restartId in the file content), and swept by the launcher at the next restart or by a bounded cleanup step; test leftover/wrong-mode/pre-created dir fail-closed and cleanup after success/failure/orphan.

#### R2-M6. D8 misstates `-b/--build` and the unified orchestration omits the current build-before-restart stage; R3 also conflicts with the current base requirement's ordering

- `design.md:124`: "`restart -b/--build` | 保持现状：`buildOnly` 在 restart 前返回，不进入排程." This conflates two different flags: `args.mjs:8` maps the **command** `build` to `buildOnly`, while `args.mjs:9` maps the **option** `-b`/`--build` to `flags.build`. `main.mjs:78-85` runs autoUpdate/prereq and, for `flags.build`, the `sync.mjs` build before falling into the restart at `:98`; only `flags.buildOnly` returns at `:86`. The existing contract row that matches the D8 sentence is `['build','-b','restart']` (`tests/launcher-contract.test.mjs:104`), not `restart -b`.
- `design.md:81-90` (D4) omits the conditional `sync.mjs` build stage from `performRestart`, so "序列与现状一致" is false for `dsh restart --build`: the external path would stop building before restart, or the build would have to move to a place the design does not specify (launcher before scheduling vs orchestrator after disconnect). `proposal.md:13` just says "restart 与 build-only 组合保持现有行为", which does not disambiguate.
- Also `R3` (`spec.md:93`) mandates "autoUpdate → prerequisites → prepare → then stop", while the *current* `openspec/specs/startup-autoupdate/spec.md:46` mandates "stop server → close UI → confirm port release → resolve runtime → start". The `cross-platform-launcher` delta already rewrites that requirement to prepare-before-stop, but this change deliberately does not modify it and does not state an archive-order precondition (design:175 only discusses implementation order); archived out of order, two live requirements would mandate opposite orders and `spec.md:3`'s "stricter wins" cannot resolve an ordering contradiction.

**Fix:** correct the matrix row (and add rows for `--check`/`--dry-run`/`--yes`); put the build stage into D4 explicitly with its session-context placement; add a normative archive-order note ("this change must not archive before cross-platform-launcher merges its MODIFIED requirement") or reference the pending base text instead of restating the order; add a parity scenario for `dsh restart --build` in both contexts.

#### R2-M7. External restart must write a receipt (R4) but must not change output/exit codes (R6); the failure behavior for an unwritable `$DSH_HOME` on the external path is unspecified and contradictory

- `spec.md:139` makes every restart — "外部与会话语境、成功与失败、含 fail-closed 拒绝" — append JSONL events. `spec.md:141` defines the writability preflight and fail-closed behavior only for "排程前" (session scheduling), not for the external path. `spec.md:193`/`proposal.md:17`/`design.md:106` require the external path to keep its CLI contract unchanged (stdout/stderr/exit code) while also writing receipts.
- If `$DSH_HOME` is unwritable/read-only on an external restart, the implementation cannot both satisfy R4 ("must append", and M9's "no unrecorded continue" spirit) and R6 ("exit code/output must not change"). Today an external restart with an unwritable home succeeds; after this change it must either silently skip the record (violating R4's universal wording) or fail (violating R6). The design has no third option and no test.
- Same ambiguity for the 0700 directory clause (`spec.md:139`, `design.md:103`): if `$DSH_HOME` already exists as 0755 (common for a shared/user-created home; the test fixtures create it with default mkdir mode 755 — `tests/helpers/launcher-fixture.mjs:62`, measured), does the preflight fail-closed, chmod a user-owned home, or ignore the existing mode? No requirement says.

**Fix:** state the external-path receipt policy explicitly (recommended: best-effort append, never change output/exit code, and record the degraded condition on stderr only if it does not change contract; or explicitly make external receipt best-effort and scope R4's fail-closed clause to session scheduling). Define directory mode as "create-if-absent 0700; never loosen an existing home; file always 0600; do not fail merely because an existing home has other bits". Add scenarios for both.

#### R2-M8. D7's allowlist strips legitimate launch-time/plugin `DSH_*` configuration, creating an environment-fidelity difference between cold start and session-initiated restart; it has no requirement/scenario traceability

- `design.md:113`: keep only `DSH_HOME`, `DSH_PROFILE`, `DSH_PROFILE_DIR`, `DSH_BIN` plus `.env.local` explicit values; `design.md:116` tests that a representative plugin `DSH_*` does not appear. The direction fixes round-1 S5's leak concern, but it also removes values the Host is documented to read from `process.env`:
  - `DSH_TELEMETRY_DISABLED` is a documented launch-time Host env read at `$COMPAT/dsh/lib/profile-boot-BZ2ZjNWi.js:269` (`telemetryDisabledEnv`) and described as "Launch-time DSH_TELEMETRY_DISABLED value; any non-empty value opts out" in the runtime API catalog (`dsh-app-boot` also has `resolveTelemetryPatch(disabledEnv, …)` at `dsh-app-boot/lib/index.js:1006-1010`). A user who exports it (or a caller environment that carries it) loses the telemetry opt-out only on session-initiated restarts.
  - `DSH_AGENTS_HOME` and `DSH_BUNDLED_SKILL_DIR` are fallbacks read by the Host skill provider (`$COMPAT/dsh-skill-filesystem/lib/index.js:78,84`).
- The current launcher's `hostEnv` only filters `npm_*` (`scripts/launcher/environment.mjs:44`), so external cold starts pass these through; the replacement Host after an in-session restart would not. This is a silent config-drift bug, not a security improvement, and the design has no requirement or scenario for replacement-Host env fidelity (D7 is design-only).
- `.env.local` declared `DSH_*` values are kept (`design.md:113`), which is the workaround only if the user put the value there; external-environment-only settings are not.

**Fix:** keep the allowlist principle but add the documented Host launch env (`DSH_TELEMETRY_DISABLED`, and any other documented launch/plugin config keys found by scanning the pinned runtime) to the allowlist, strip only session-identity keys (`DSH_SHELL`, `DSH_SESSION_ID`, `DSH_PTY_SESSION_ID`, `DSH_WEB_URL`, `DSH_RESTART_*`), and test both directions: session markers absent AND representative config present. Add a spec requirement or at least an explicit D7 test row + traceability to R3.

#### R2-M9. Instruction/recovery contract misses the most likely safe-failure path: orchestrator fails *before* stopping the Host, so the caller is still connected and the launcher already returned success

- `spec.md:177`/`design.md:134` cover "执行前告知会断开 / 不得当次宣称成功 / 重连后按 history 验证 / Host 未恢复时外部 `dsh` 恢复".
- But `design.md:95-99`: autoUpdate/prerequisite/prepare failure and stop-stage failure leave the old Host running; the launcher has already returned 0 after the handshake. The agent session therefore **does not disconnect** and the "reconnect then verify" instruction never triggers; the agent may believe the restart is in progress, report the scheduled message to the user, and never notice `failed(preparing)`/`failed(stop)` in the receipt. There is no instruction bullet for "session did not drop ⇒ query `dsh history` now; a failed(preparing/stop) means the Host was never stopped — report failure, do not ask the user to recover externally."
- Scenario `spec.md:101-105` only asserts Host state, not caller-facing behavior; R5's materialization test only checks tokens, so nothing forces this bullet.

**Fix:** add the non-disconnect verification bullet to R5/D9 and to the required tokens; add a receipt/history assertion for the pre-stop failure case (Host owned, caller connected, `failed(preparing|stop)` displayed), and state that the launcher's 0 means "scheduled", not "restarted".

**Fix:** replace the quoted phrase with byte-exact anchors from the real files (or better: assert absence of both `由用户执行` *and* `等于自断` in the step-4 block, and presence of the new consent/disconnect/verification phrases), and restate R5/spec:189 as "old directive removed/rewritten" rather than "not sole guidance". Cross-check both skills and README (the current directive also says "请用户自己执行 `dsh restart`" — README:84/92 and the skill's "必须问" need reconciling with the new consent rule).

#### R2-M11. Concurrent restarts (session+session, session+external) have no mutual exclusion, epoch check or truthful receipt labeling, so two orchestrators can stop each other's Hosts

- `design.md:93-99` performs stop → handoff → start with per-run validation only (port ownership/identity at the moment of stop); nothing prevents a second orchestrator (another agent session, or an external synchronous restart) from stopping/starting in the gap. A concrete sequence: session A's orchestrator wakes after grace; meanwhile the user runs an external `dsh restart`, which stops the old Host and starts Host B; A then sees B on the port, stops B (identity is "valid DSH", so stopServer accepts it), and starts Host C. Both runs write `ready` receipts with different PIDs; the external command reported success for a Host that was stopped moments later by A; if B's caller reports success and A's start then fails, both receipts disagree.
- Round 1 M4 raised the concurrency-receipt aspect (`design.md:118` in round 1); the revised artifacts dropped it from the risk list and only added history selection (`spec.md:143,163-167`), not behavior. In this repository (multi-session / Team agents) this is a realistic case, not a theoretical one.
- No requirement defines whether concurrent restarts are serialized, rejected, or explicitly accepted as churn; no epoch/lock file; no receipt label such as "superseded by restartId …".

**Fix:** add a serialization/epoch rule (e.g. single-writer lock/epoch file under `$DSH_HOME`, orchestrator re-checks the epoch before `stop` and aborts with `failed(stop, superseded)`; external and session paths both participate) or explicitly accept the churn as a P0 non-goal with rationale and a receipt "superseded" marker; add a concurrency scenario and reconcile the history selection rule (R2-M3).

## Verdict

The round-1 blocking analysis was correct and the revision genuinely closes most of it: the terminal-prefix detection gap (C1), the non-Linux evidence source and R1/R2 platform contradiction (C2), the shared orchestration boundary (M1), the ack handshake (M2), the failure tail (M3), argv-only scheduling (M5), the systemd support boundary (M7), persistence/bounded tail (M9) and most Suggestions are now supported by concrete normative text and scenarios. The root-cause citations remain accurate at this HEAD.

However, the revision introduced and/or left two **blocking** problems on the exact critical path it is meant to protect:

1. **R2-C1** — the fail-closed ordering of `scheduled` versus `go` is stated in opposite orders in R2/D2 vs R4/D6. Implementing the R2/D2 order can release the orchestrator to stop the Host before the mandatory receipt record exists, which is precisely the unverifiable-restart class the change exists to prevent, and makes R4's own failure requirement untestable.
2. **R2-C2** — the scheduled child's process handle and stdio are undefined. A normal implementation either cannot return from the launcher (child handle keeps the event loop alive) or, once the launcher exits, the orchestrator crashes with an unhandled EPIPE on its first `doStop` log write — after the Host has been stopped and before the replacement Host is spawned. Both mechanisms were reproduced locally with the pinned Node; neither is mentioned anywhere in the artifacts.

In addition, five round-1 items are only partially fixed (M4 receipt vocabulary/ordering, M6 cross-change oracle coordination, M8 mechanical instruction assertion, S1 grace/result delivery, S8 flag matrix), and the new review found nine further Moderates on detection ambiguity (R2-M1), the cgroup substrate (R2-M2), history selection/incomplete-state rules (R2-M3), handshake-failure double events (R2-M4), state-dir trust/cleanup (R2-M5), `-b/--build` and base-requirement ordering (R2-M6), external receipt vs zero-change (R2-M7), replacement-Host env fidelity (R2-M8), instruction recovery for pre-stop failure (R2-M9), exact-phrase testability (R2-M10) and concurrent restarts (R2-M11).
