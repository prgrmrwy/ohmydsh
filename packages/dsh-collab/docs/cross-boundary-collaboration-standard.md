# 跨边界协作标准

- **状态：** 方向已于 2026-10-22 与用户讨论确定，作为 dsh-collab、collab-kernel 后续 change 的依据。本文不是 OpenSpec 规范，可执行要求以 `openspec/specs/` 为准。
- **适用范围：** 跨 session 协作（本机）、Pet Locus 主会话与飞书入口的协作、将来的跨机协作。
- **参照：** DSH 官方 Agent Teams（`@deepseek-ai/dsh-experimental-agent-team@0.2.0-rc.2`，MIT）；调研纪要见分支 `ws/collab-pet-locus-collab` 的 `packages/dsh-collab/docs/2026-10-22-locus-unified-collaboration-exploration.md`。

## 1. 定位：Agent Teams 管边界之内，我们管跨边界

| | 边界之内（Agent Teams） | 跨边界（本标准） |
|---|---|---|
| 一句话 | 一个需求、一个负责人，按职能拆给多个 agent 去做，最后统合 | 多个各自负责一块的现场之间，共享上下文、协商公共部分 |
| 关系 | 上下级：Lead 指派、打断、统合 | 平级：各自对自己那块负责，只能协商 |
| 现场 | 同一个 checkout，同一份权限 | 不同仓库、不同平台（飞书）、将来不同机器 |
| 成员来源 | Lead 为这件事临时派生，事毕即散 | 已有会话，或长期存在的外部入口 |

**判断标准**：是否有一个负责人对整件事全权负责，且所有成员都在他的控制范围内。满足就属于边界之内，直接用 Agent Teams；不满足就属于跨边界，用本标准。

- **跨仓库需求**：A 负责仓库 a，B 负责仓库 b，公共部分要共同完成。这是平级，属于跨边界。
- **Pet Locus**：子会话服务飞书里的另一群人，有自己的受众和回复权；它的现场是群和话题，生命周期跟着入口走。这是派驻关系，属于跨边界。只有当主会话为做完一个需求临时开子会话分工时，才属于边界之内。
- **每个现场内部**需要分工时，照常使用 Agent Teams。本标准不实现团队内的任务板，避免和官方重复。

## 2. 与 Agent Teams 对齐的是原则，不复刻功能

1. **改状态不顺带唤醒。** 条目修改、ack、共识达成、请求的中间进度、自记进度、Leader 转交，都只写进台账，不唤醒任何人。
2. **结束通知请求方。** 请求进入终态（done 或 rejected）时，唤醒请求的作者。这对应 DSH 主子结构里"子会话一轮结束，运行时自动通知父会话"：Agent Teams 的任务板之所以能只登记、不唤醒，是因为下面有这层结束通知托底；跨边界没有父子关系，所以由协作层自己提供。每个请求最多通知一次（终态不可逆），不会成环。
3. **要对方动手，就显式发消息。** 发一条需要回复（`needsReply`）的消息。送达不等于处理：消息持久、可追溯，"已投递"只说明对方持有这条消息；inactive 不等于完成。
4. **台账是唯一真源，管理事实可查、不广播。** 修改带版本号，用 CAS 防止覆盖；状态由日志重放推导；成员、空间、进度通过工具按需读取，不推送给每个人。

Agent Teams 或 DSH 主子语义调整时，先核对这四条原则是否变化，再按需跟进。概念对照：

| 我们 | Agent Teams | 差异 |
|---|---|---|
| 协作空间（jsonl 台账） | Team（Lead 会话日志） | 我们独立于会话，可以有多个 root |
| 成员（邀请加入 / 宿主管理） | teammate（Lead spawn） | 我们接纳已有会话和外部入口 |
| 请求、自记进度 | task（claim / complete） | 我们按平级礼节表达："向对方提请求"与"记录自己的进度" |
| 共识（charter + ack） | 无 | 平级没有裁判，需要共识；Agent Teams 有 Lead 拍板，不需要 |
| 消息 + `ref` | mailbox | 我们有幂等收据和话题计数；投递排到下一回合，而不是 steer |
| 话题唤醒上限 | 无 | 平级 agent 互相唤醒会成环，需要上限 |

## 3. 空间组织

- **按协作的事情划分空间**，不按会话拓扑。例如"需求 X"一个空间，"A 的 Locus"一个空间。
- **成员与空间是多对多**。一个会话可以同时在多个空间里，它就是这些空间之间的桥。
- **不做树状结构**，没有空间嵌套和权限继承。底下通不通由成员关系决定：默认由桥成员转述；需要直通时，把子会话邀请进对应空间。
- **`ref` 只在同一个空间内有效**。跨空间提及一件事时，在正文写明空间和条目，不跨空间计数。
- **空间有用途说明**（创建时填写），`collab_status` 里会显示，用于判断往哪个空间写。

### 多空间的读写路由
- **回应别人**：写进唤醒指针所在的空间，并 `ref` 被回应的那条记录。
- **主动发起**：按用途说明，选与"这件事和谁有关"匹配的空间。
- **一件事涉及两个空间**：写进主要相关的空间；另一边需要知道时，由桥成员在那边发一条摘要并注明出处。不做跨空间自动同步。
- **读取入口只有一个**：`collab_status` 汇总本会话所在的所有空间及待办；需要细看时再对具体空间调用 `collab_read`。

## 4. 可见范围与写入纪律

- **同一个空间内显式登记的内容对所有成员可见**：共识、请求、进度、消息。
- **原始对话历史不进入空间**：群聊原文、会话历史、其它入口的信息，不原样搬进来；写入的应是提炼后的结论、请求、进度。这条是写入纪律，接入方可以在登记工具上加结构约束。
- **接入方可以用不透明成员名隐藏入口身份**。例如 Locus 子会话叫 `locus-7f3a`，只有主会话和管理面知道它对应哪个群。这样可以满足 Locus "不枚举兄弟入口"的承诺。
- 协作层不按成员控制可见范围。

## 5. 防循环

- 会唤醒他人的只有三种：需要回复的消息、邀请、请求进入终态时的结束通知。
- **按话题计数**：话题是 `ref` 一路追溯到的起点（一条没有 `ref` 的消息，或一个条目）。一个话题里会唤醒他人的消息达到上限（20）后，再发会被 `COLLAB_THREAD_LIMIT` 拒绝，不会被静默吞掉。
- 收到 `COLLAB_THREAD_LIMIT`：停止这段往返，向本会话的用户报告；不要为了继续同一件事而另开新话题。
- 不写 `ref` 就是新话题，从 0 开始计数。这是用户接受的口子。
- 结束通知不计入话题上限（每个请求至多一次，不会成环），但归属该请求的话题，便于追溯。
- 不设全局兜底，也不提供重置入口。

## 6. 人类的位置

- 人类不作为台账成员。每个 root 是背后那个人的代理：需要人拍板时，root 在自己的会话里问自己的人类，再把结论带回台账，并注明"已与用户确认"。
- **同机前提**：各 root 背后通常是同一个人，所以"root 对自己人类的转述"视为可信，"邀请即加入"也成立。**跨机后这个前提不成立**，成员信任和邀请规则要重新设计。
- Leader 是发起空间的 root（即人类的代理），只管空间本身：邀请、关闭。Leader 不对其它成员做业务指派。

## 7. 场景映射

### 7.1 跨仓库需求
- 空间"需求 X"，成员 A、B。
- 公共部分（接口、文件归属）写成共识，双方各自 ack。
- 需要对方做某件事时提请求，再发一条需要回复的消息请对方处理；各自的进度自己登记，不唤醒别人。
- A、B 内部的拆分各自使用 Agent Teams。

### 7.2 Pet Locus
- 空间"A 的 Locus"，成员是主会话 A 与它的群、话题子会话。子会话由 Pet 管理成员，使用不透明的名字。

| Locus 现有能力 | 对应 | 接入时的改动 |
|---|---|---|
| 共享事实台账（主会话与其子会话共享） | 协作空间 | 存储迁到协作层 |
| 待办（固定来源、回复去向、证据快照） | 请求或自记进度，飞书来源放进结构化附加数据，用 `ref` 指向来源消息 | 中等 |
| 受理即开工 | 请求被接受，再发一条需要回复的消息唤醒主会话 | 小：正好就是"登记 + 发消息"两步 |
| 子会话询问主会话（`pet_inquire`） | 一条 `ref` 消息问答，Pet 在派发和续进时加自己的守卫 | 大：询问存储、派发、恢复要接到协作层 |
| 只读查阅主会话历史 | 宿主读取能力，不属于协作层 | 不动 |
| Delivery、受管 finish、飞书回复权、代际、管理面 | 入口与生命周期，不属于协作层 | 不动 |

- 子会话需要更多上下文时，依次：
  1. 到飞书拉自己入口的消息；
  2. 读协作空间；
  3. 问主会话，或只读查阅主会话历史。
- Locus 接入要单独开 change，并先确认它与 ADR-0006（Locus 留在 Pet 内）的边界：ADR 不禁止消费独立协作内核，需要写清楚 Pet 保留什么。

### 7.3 跨机（预留，不实现）

| 约束 | 现状 | 要求 |
|---|---|---|
| 单一落盘方 | 每个空间一把排他锁；创建时记录 `serviceId` | 跨机时由一个 hub 串行执行命令，或用带条件写（ETag/If-Match）的存储做乐观并发；不能让 git 或云盘多点直接写 |
| 所有成员都能提交 | 授权表按操作检查 | 逻辑写入权不变，只是经 hub 排队 |
| 唤醒由目标机器发起 | 由 provider 的 `deliver` 执行 followup | 跨机时由中继通知目标机器上的插件执行；MCP 只能拉取，叫不醒空闲会话 |
| 成员地址 | `{channel, address: sessionId}`，只在本机有意义 | 以后加上机器身份；现在就不能假定 sessionId 全局唯一 |
| 有序日志 | 单写入方保证 seq 全局有序 | `ref` 与话题计数依赖它，跨机后仍由 hub 保证 |
| 内容不依赖本机 | — | 附加数据、约定里的路径只用于展示，不作为有意义的内容 |
| 信任 | 同机时视为同一个人 | 跨机要重新设计成员信任与邀请 |

## 8. 协作层为 Locus 预留的扩展点

只做加法。三项已由 change `collab-locus-extension-points` 在协作层实现（2026-10-23）；Locus 真正接入另开 change：
1. **宿主管理的成员**：接入方按自己的绑定加入、换代、退役成员，不形成第二份授权真相。
2. **结构化附加数据**：条目和消息可以携带接入方定义的数据，协作层只存储、不解读。
3. **可插拔投递策略**：普通唤醒排到下一回合；接入方可以要求独立轮次（例如 Pet 的询问）。
