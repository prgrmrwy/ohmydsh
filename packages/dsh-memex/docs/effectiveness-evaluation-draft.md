# Memex 效果评估规则（讨论稿）

状态：讨论稿，2026-10-12。尚未进入 OpenSpec，不是验收标准。定稿后再拆成 change。

> 2026-10-27：评估方法论基线已移到 [evaluation-methodology.md](evaluation-methodology.md)，与本稿冲突时以新文件为准。本稿 4.1 被动记录与 4.2 意图参数已在 dsh-memex 0.4.0 实现。历史审计发现：意图标签不能直接当作召回目的的真值，很多 `gap` 实为背景确认或解决后查重。

## 1. 目标

一句话验收标准：**同类问题再次出现时，Agent 能正确复用以前学到的知识，在任务质量不下降的前提下，减少重新调查、推导和搜索的成本。**

推论：

- 不必出现新方向才算有效。原本要重查的旧结论，这次靠记忆加一次必要核验就解决了，也是核心收益。
- 读了卡、引用了卡，却没有减少工作或改善结果，不算有效。
- 成本要算全：召回、读卡、写卡、核验都计入，不能只算省掉的搜索。

## 2. 为什么不再沿用 v3

v3（2026-10-10 冻结）的单位是“一次召回”，问题是“返回的卡有没有被用上”，用先验 0.40 乘一组凭直觉设定的似然比。

| 核心要求 | v3 能否衡量 | 缺口 |
|---|---|---|
| 写入：该记的记下来了吗，写得能直接用吗 | 不能 | 只看召回；不评卡片质量；看不到漏记 |
| 检索：需要时找得到吗 | 部分 | 看不到“该召回没召回”；“没拿到”混合了“库里没有”和“有但没找到” |
| 消费：用对了吗，省事了吗 | 部分 | “读了卡仍把调查重做一遍”也算用上；不衡量成本 |

另外：似然比未经数据估计，信号互相重复计数；留出检验中 v3 的概率不如恒定基线；v6 预检中双评一致可判定只有 2/6。根因是历史记录缺少关键事实（查询时的库内容、卡的版本、召回前已知什么），旁观者无法分清贡献来源。

v3 的类别结果保留为历史参考，不作为新规则的标签来源，也不与新规则的数字直接比较。

## 3. 三个问题，各用自己的单位

每个问题用可程序判定或可核对的分类，不再连乘似然比。

### 3.1 写入（单位：一张新写或被覆盖的卡）

问题：卡片第一段能否在不读全文的情况下直接使用？

背景：内核检索结果每张卡只展示标题、第一段和匹配行（`formatSearchResult` 的 `firstParagraph`），基线评估中 Agent 大多不读全文。

判定项（第一段内）：

- 触发情境：什么问题出现时应想到它；
- 结论或做法；
- 适用边界：项目、版本、环境或前提；
- 使用前最低核验。

程序先判定（长度、是否只是铺垫、是否以冒号结尾等形态），LLM 抽样复核四项是否齐全。指标：新卡达标率；对比现有卡（2026-10-12 时 personal 库 417 张，46 张第一段只是铺垫）。

### 3.2 检索（单位：一次声明为“有具体缺口”的召回）

问题：召回那一刻，库里有没有适用的卡？有的话返回了吗？

分类：

- `hit-top`：库里有适用卡，并排在前 3；
- `hit-low`：有，返回了但排在后面；
- `miss-retrievable`：库里有，但没返回（检索问题）；
- `miss-absent`：库里没有（捕获问题，或确属新问题）；
- `n/a`：不是有具体缺口的召回（见 4.2）。

判定方法：用召回时记录的库版本还原当时的卡集合，由 LLM 在“当时存在的卡”中判断有无适用卡。旧数据可按卡库的每日自动提交近似还原。

### 3.3 消费（单位：一次返回了适用卡的召回）

问题：适用的卡是怎么被用的？

分类：

- `direct`：直接据此行动，没有重新调查同一问题；
- `verified`：做了有界核验后据此行动；
- `redo`：读了卡，仍把同一调查重做了一遍（关键负例）；
- `ignored`：没有用；
- `misled`：用了过期或不适用的卡，导致错误或返工。

`redo` 与 `direct`/`verified` 的区分以程序可观察行为为主：读卡后是否对同一主题继续反复搜索、读源码直至得到卡上已有的结论。

### 3.4 成本（附在消费单位上）

从召回到形成该问题结论所用的步数、工具调用数、token，按消费类别比较。抽样案例用 5.3 的拿掉重放给出因果差值。

## 4. 数据怎么拿：三层

社区依据（检索范围有限，见文末）：模型的自我报告系统性偏向少报使用；判断贡献的通行办法是去掉该内容看输出是否变化；记忆效果评测普遍采用有/无记忆的成本与成功率对比。

### 4.1 被动记录（全量，程序）

在现有召回遥测上补 5 项，全部只记判据，不记查询原文和卡片正文：

1. 库快照：每个被查库当时的 git commit 及是否有未提交改动；
2. 命中卡的版本：每条命中的内容 hash 和 `modified`；
3. 关联键：session id 的 hash、turn、toolCallId；
4. 写卡事件：slug、新建或覆盖、时间、关联键；写入时的 DSH 与模型版本（来源只记在遥测，不进卡片 frontmatter）；
5. 命中解释：每条命中的名次、得分，以及由第几个查询词在哪个字段（slug / title / tags / category / headings / wikilinks / body）命中。记查询词的序号和字段名，不记词本身。

读卡、后续工具调用、步数、token 已在会话记录中，不重复记录，分析时按关联键对齐。

第 5 项借鉴 TrustGraph 的查询期可解释记录（每次查询分步记录命中依据与分数，见 `docs/query-time-explainability.md`、`trustgraph-base/trustgraph/provenance/triples.py`）。现有遥测只有一个近似的 `anchored` 布尔值，无法回答“这次召回靠什么命中、为什么排在这里”。未确认：内核输出不含分项得分，可能需要在集成层按内核权重复算；复算结果只用于记录，不改变返回内容与顺序。

### 4.2 召回时声明意图（当时的 Agent）

召回工具增加一个可选的结构化参数，Agent 在**看到结果之前**选择：

- `gap`：有具体缺口；
- `background`：任务开头的背景加载；
- `by-name`：按名取回已知的卡；
- `dedupe`：写卡前查重或找邻居；
- `verify`：写后验证或健康检查。

理由：只有当时的 Agent 知道召回目的，而此时它还没看到结果，不存在事后合理化。这也直接解决了旧评估中最难判的“排除项”。

不采用“事后自评有没有用”作为标签：研究显示模型实际用了某信息时，在推理中承认的比例常低于 20%，被追问时也会否认。事后自评只作参考。

### 4.3 拿掉重放（抽样，因果标准答案）

从一次 `gap` 召回的时刻分叉出两个会话：一个照常返回，一个去掉该适用卡，其余相同，各自运行到同一检查点。比较步数、token 和结论质量。

- 只用于只读调查片段；有副作用的步骤需隔离或 mock。
- 每月抽 10–20 例；结论质量由人抽查。
- 同一案例必要时重复运行，避免把模型随机性当成收益。

## 5. 各方职责

| 角色 | 负责 | 不负责 |
|---|---|---|
| 程序 | 被动记录；核对 Agent 声称的动作在会话记录中真实存在；程序判定各分类的可观察部分 | 语义判断 |
| 当时的 Agent | 召回意图（4.2） | 有没有用的最终标签 |
| LLM 评审 | 适用卡判定（3.2）、卡片四项复核（3.1）、`redo` 边界案例 | 替代重放给出因果结论 |
| 重放 | 抽样案例的因果成本差 | 全量统计 |
| 人 | 定标准；抽查重放质量和 Agent 意图声明的可信度 | 逐条打标签 |

## 6. 指标

| 指标 | 定义 | 对应问题 |
|---|---|---|
| 新卡达标率 | 新卡中第一段四项齐全的比例 | 写入 |
| 可检索召回率 | `gap` 召回中，库里有适用卡时被返回的比例 | 检索 |
| 捕获缺口率 | `gap` 召回中 `miss-absent` 的比例（需人工抽查是否本应记下） | 写入 |
| 正确复用率 | 返回适用卡的召回中 `direct` + `verified` 的比例 | 消费 |
| 重做率 | 同上分母中 `redo` 的比例 | 消费 |
| 错误复用率 | 同上分母中 `misled` 的比例 | 消费 |
| 成本差 | 重放样本中有卡与去卡的步数、token 差 | 成本 |

所有比例按会话聚类给区间；会话数不足 15 个时只报描述，不下结论。

## 7. 与优化和上游的关系

> 进度（2026-10-13）：4.1 的 5 项被动记录、4.2 的意图参数与第 2 条 P0 已在 change `dsh-memex-reuse-evidence-and-card-lead`（dsh-memex 0.4.0）中实现，尚待部署。第 1 条基线重算、4.3 去卡重放、第 2 条下的“为什么命中”候选与第 4 条上游 issue 均未进入该 change。

1. 定稿本规则，并用它在 2026-09-24 至 2026-10-08 的历史数据上重算基线（4.2、4.3 无法回溯，基线只含 3.1–3.3 的可回溯部分）。
2. 唯一 P0：写卡要求第一段写清四项（改本仓库注入的写卡引导与环境级指令，不改上游 skill）；与 4.1、4.2 一起上线，观察窗起止事先写明。
   - P0 之后的候选（本轮不做）：召回结果中给每张卡标注“为什么命中”，例如“标题/标签命中”或“仅正文命中”，并标出本会话自写的卡，帮助 Agent 判断何时读全文。借鉴 TrustGraph 检索结果附带来源与解释的做法；它的 MCP 工具只返回合成文本、丢弃解释（`trustgraph-mcp/trustgraph/mcp_server/mcp.py`），正是要避免的反例。前提是 4.1 第 5 项先落地，并用数据确认“仅正文命中”确实更少被用上。
3. 上线 1 周看写入端（新卡达标率）；3–4 周看检索与消费端。
4. 上游：核心论据（召回只展示第一段，写卡指引未提）不依赖本规则，可先开 issue；复测数据作补充，并注明单用户、小样本。

## 8. 待确认事项的结论（2026-10-12 核对）

1. **会话记录保留：已确认，不会自动清理。** 在已安装的 DSH 0.2.0-rc.2 会话持久化与相关包中未找到按时间清理的逻辑；本机 `~/.dsh/sessions` 现存 1,625 个日志文件、约 1.7 GB，最早可追溯到 2026-08-14。4.1 可以依赖会话记录对齐，只需关联键。残余风险：人工删除或归档会话会丢失对齐，分析时需报告缺失。
2. **会话分叉：已确认可用，但不能直接替换工具结果。** DSH 提供 `session/fork`，可按精确事件序号 `atSeq` 复制前缀生成新会话，未完成的轮次由 `forked` 合成结果关闭（`dsh-api-session-controller` 的 `fork`，`dsh-session` 的 `buildForkSeed`）。没有“替换某次工具结果”的接口。因此 4.3 改为：
   - 在发起召回的那条 assistant 消息之前分叉，让模型在两个分支中重新发起召回；
   - 由 dsh-memex 提供仅用于重放的排除机制（按会话排除指定 slug），只作用于去卡分支；
   - 两个分支都必须把库固定到召回时的 commit（检出到临时目录），否则会混入之后新写的卡；
   - 分叉会使用**当前默认模型**而非原会话的模型，重放前需显式切回原模型；
   - 模型在重放中可能改写查询，应作为噪声记录，并对同一案例重复运行。
3. **意图参数对行为的影响：无法事先确认，改为上线后的验证项。** 参数设为可选；上线后比较加参数前后各两周的召回频率、每次召回后的步数与 token。若召回频率变化超过 30%，回到讨论。
4. **与现行规范的冲突：可以化解，需在 change 中新增要求。** `dsh-memex-memory` 规范约束的是**工具描述**只能沿用上游原文并追加 `scope` 说明；新增参数自带参数级说明，不改动工具描述。仍需新增一条要求，写明意图参数的取值、可选性、只用于遥测、不改变检索结果。
5. **适用卡判定的 LLM 可靠性：无法事先确认，改为试点验收项。** 重算基线时先抽 20 个 `gap` 召回，由 LLM 判定后人工复核；一致率达到 80% 以上才全量使用，否则只报人工复核的子集。

补充：内核搜索输出不含分项得分（只有 `--compact` 下的归一化总分），4.1 第 5 项需要在集成层按内核权重重新计算；现有 `anchored()` 已是同类近似实现，可在其基础上扩展。
