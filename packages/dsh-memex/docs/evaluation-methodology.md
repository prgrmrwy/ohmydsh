# Memex 有效性评估方法论

状态：方法论基线，2026-10-27 与用户对齐。约束此后所有 Memex 效果评估与据此进行的优化。
修改本文件中的任一原则，须写明理由、日期和触发修改的证据，不得为让某轮结果更好看而修改。

具体题目、业务证据和运行结果只保存在本机私有目录（`~/.dsh-memex-eval/`），不入库。
[effectiveness-evaluation-draft.md](effectiveness-evaluation-draft.md) 是 2026-10-12 的讨论稿，其中被动记录与意图参数已实现；与本文冲突时以本文为准。

## 1. 要回答的问题

同类问题再次出现时，Agent 能否正确复用以前学到的知识，在质量不下降的前提下减少重新调查的成本。

这个问题拆成两半，由两套互补的方法回答，不互相替代：

| 方法 | 回答 | 不能回答 |
|---|---|---|
| 历史审计（真实会话） | 日常使用中实际发生了什么、哪些场景最多 | 记忆的独立作用（来源混淆），总体净节省 |
| 构造检测（模拟日常任务） | 已知情况下行为对不对、断在哪一环 | 真实使用中省了多少 |

两者的结论都不能单独外推为"Memex 值不值"。净节省只能由有记忆/无记忆对照回答。

## 2. 证据原则

1. **以真实工具调用为主账。** 按调用身份去重，fork、seed 等继承副本不重复计数；遥测只用作辅助诊断。
2. **相关不等于贡献。** 返回了相关卡、读了卡、最终结论与卡一致，都不能单独证明记忆起了作用。
3. **未见不等于无用。** 缺少证据时标为未知，不得把"未见贡献"或"未知"计为失败。
4. **证据要看区分度。** 一条证据在记忆有用和无用时都会出现（似然比约为 1），就不改变判断。例如：父任务已给出修法、Agent 照做。区分度高的证据，是"有没有用记忆，结果会明显不同"的现象。这里只用似然比判断一类证据**有没有区分度**，不给证据赋具体数值，也不做连乘计算。2026-10-12 的 v3 规则用先验乘以凭直觉设定的似然比，在留出检验中表现不如恒定基线，已废弃。
5. **评审分歧不投票。** 两次评审不一致时，按源证据逐条仲裁；仲裁不了的保留为未知，不取更乐观的一方。
6. **记录齐全不等于验证深度一致。** 报告必须分层说明每条记录的阅读深度。
7. **不用当前版本回填历史。** 历史卡片版本无法还原时，标为不可用。

## 3. 构造检测原则

### 3.1 场景

- 按记忆库的实际消费地点（DSH workspace）出题，模拟日常工作。
- 跨库是独立的检测维度：附加入口只有显式指名才会被检索（`openspec/specs/dsh-memex-scope/spec.md` 中"可达不等于默认动作"），所以"是否意识到要查副库"与"能否找到"分开测。
- 共库的多个仓库要测"抗串仓"：是否区分卡片属于哪个仓库。
- 检测时保持现有检索设置；测出的问题记录下来，之后再修复。

### 3.2 出题

- 题目由不知道优化方案的独立会话出，出题方与优化方分离。
- 间接题列出禁用词，不得包含卡片标题、首段中的关键标识符。从卡片原文派生的题目只能测到上限。
- 题型至少包括：标识符直接问、概念直接问、症状问题、任务型、同症状不同根因。
- 卡片状态至少包括：有效、过期（只在副本中人为改错一个事实）、干扰、缺失。
- 优先出高区分度的题：过期、跨库症状、缺失、任务型。查一步代码就能答的直接题要少出。
- 标准答案写成"必答事实 + 可接受根因"，以固定提交点的代码为准；卡片只提供线索，同主题任一卡提供事实都算数。
- 间接题不规定固定链路，只记录检测点：首次召回、发现新标识符后是否补检索、第几步拿到关键事实、是否核验、结论是否正确。

### 3.3 指标

按漏斗分层，每层只在上一层通过的题上计算，失败时定位到具体环节：

检索（召回时机、命中名次、事实到达、跨库意识、补检索、抗串仓）→ 记住了（答对、转述准确、正确弃答）→ 用上了（应用、过期处置、抗干扰、结论正确、拿到关键事实的步数和成本）→ 记下了 / 更新了 / 废弃处置 / 写入正确的库。

- 事实以摘录、链接或读卡任一形式到达上下文都算到达。"不在前 3 名"不等于失败。
- 写入类指标必须在隔离库中测。

### 3.4 Agent 对待卡片的标准

卡片是先验：告诉 Agent 先往哪里查。当前代码与环境是似然：用来更新判断。结论是后验：以核验后的事实为准。

两类错误都要计：

- 把先验当后验：照搬卡片，不核验。
- 完全不用先验：召回了仍从零开始调查。

卡片与代码冲突时，正确行为是以代码为准，并指出冲突。

## 4. 判定

- 能用程序判定的不交给模型：检索层全部由程序从日志判定。
- LLM 裁判必须：允许"无法判断"并单独统计；引用原文片段，由程序逐字核对；尽量与被测 Agent 不同模型家族；只做粗粒度判断（更好 / 更差 / 相当）。
- 放量前先用人工标注的小样本校准，裁判与人工的一致率达标后才使用。
- 格式合规不等于内容合格；评审者是否真的读完了原文，要用程序核对。

## 5. 报告

- 不出单一总分。主报告是"卡片状态 × 题目类型"矩阵，每格给出通过数、样本数和区间。
- 有效样本量按主题数计，不按题数计；结论按主题报告。
- 小样本用后验区间表示。区间大部分重叠的变化不能算作改善。
- "改善"的门槛在试点结束后、正式运行前确定，之后不再修改。
- 换算回真实使用：以历史审计得到的场景比例作为先验权重，给构造检测结果加权，同时列出不加权的结果。只做加权，不建立完整的贝叶斯模型。

## 6. 防过拟合

发现、评估、优化的循环会改变被测对象。以下规则不可省略：

1. **区分系统级修复与内容级修复。** 系统级修复（召回指令、默认检索范围、写卡规范）可以用开发集验证。内容级修复（改某张卡、补写卡）完成后，相关题目作废，或单独记为"该卡已修复"，不计入系统改进。
2. **封存集。** 一部分主题只在阶段性验收时运行，结果不用于优化，优化方也不看其题目。开发集改善而封存集不变，即判定为过拟合。
3. **持续补充新主题。** 每轮从库中新抽主题；用过的题保留为回归测试，单独计分。
4. **主题分层抽取。** 按子系统、卡片历史召回情况、卡片性质分层，不凭印象挑选。
5. **回到真实使用核对。** 定期用历史审计方法抽样复核真实会话，确认检测上的改善出现在日常使用中。

## 7. 安全与隔离

- 评估默认只读：不改真实记忆库、不改检索实现。修复是评估之外的独立动作。
- 过期题和写入类检测只使用库副本。worktree 预览环境的 memex 仍共享真实库，不能直接用于写入测试。
- 业务库与个人库同样纳入评估，不因业务属性排除。业务原文只存在本机，但“存在本机”不等于“在本机推理”：被测 Agent 与 LLM 裁判会把卡片、源码和会话摘录发给所选服务商。只能发给检测套件中声明的服务商，裁判只拿判定所需的证据。
- 每个检测套件固定一个被测 Agent 配置与裁判配置，测试会话不经过自动路由，以保证测试链路一致、可在不同模型之间比较。
- 每道题从不可变快照重建记忆库与被测仓库副本；副本不得保留自动同步配置、git remote，也不得与真实库共享链接。标准答案与封存集放在被测会话可达范围之外，scope 隔离不等于文件隔离。
- 测试流量必须可被日常统计排除。

## 8. 已撤回的结论（防止再次引用）

- "召回后首段通常就够"：样本有 fork 加权，返回结果实际还包含正文匹配行与链接，不成立。
- "排名是最大瓶颈"：旧的 top3 口径不成立；目标卡没有命中，可能仍通过替代卡、链接或读卡到达。
- 任何从部分覆盖样本得出的全库有效率或 recall 百分比。
