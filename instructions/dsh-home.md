# DSH 工作环境指引

- 默认省略 `sandbox_permissions`。
- 只有工具真实返回 `[sandbox: file access denied ...]`，且更宽权限能解决时，才原样重试一次；请求最窄权限并提供 `justification`。
- 若返回 `not strictly wider`，移除权限参数再试，不重复升级。
- runtime 显示 approval disabled 时不请求升级；始终遵循最新 runtime context。
- 同类参数错误连续出现时停止重试并报告。
- 读取不确定是否存在的路径前，先用 `glob` 确认；`read` 失败后先查明原因（路径是否正确、是否为目录、权限），再换方式，不原样重试。
- 当记忆工具可用时，在完成涉及代码修改、架构决策、调试或非平凡问题求解的任务后，主动判断「未来遇到类似情况时，这条会不会改变做法」；若会，调用 `memex_retro` 写一张原子卡片。检索结果只展示标题和第一段，所以第一段要能脱离全文直接使用：依次写清什么时候适用、结论或做法、适用边界（项目、版本、环境）、复用前最低需要核验什么，背景和来历放在后面。不要记录常规命令输出、显而易见的事实、临时聊天上下文或任何密钥/凭据；关联已有卡片时在正文中用 `[[slug]]` 并说明关系为何成立。
- 对照当前代码或环境核验召回的卡片时，若发现它有误或已过期，在同一回合内修订：先读卡，再用 `memex_write` 改写，保留原标题和创建日期（`memex_retro` 会把创建日期改成当天）；把第一段改为当前事实，并在末尾追加带日期的修订说明，写明改了什么、依据哪个文件和行号。结论已完全不适用时，在卡内写明，不要删卡。只修订本回合实际核对过的事实。

## Worktree 内的预览验收

- 只有需要验收时，才在 worktree 内依次执行 `dsh build` → `ws prepare-preview` → `dsh`。若当前 Host 尚未注册新动作，可使用当前 worktree 构建后的 `dsh-ws prepare-preview <worktree绝对路径>`。
- 隔离 build 不更新日常 GUI。预览的实际地址以 `DSH_PREVIEW` 输出为准，首选端口占用时会自动退避。不要操作日常 3080。
- prepare-preview 按白名单复制运行配置快照（含订阅 refresh token），不复制 Session/history；codex 在预览中刷新后可能需要在日常 GUI 重新登录。memex 仍共享真实记忆库。
- 验收通过后再提交并获准合入；生产部署必须从主 checkout 执行 `dsh build`，连续第二次应无变更，最后由用户决定是否重启日常 Host（见下节）。不要把生产部署指向临时 worktree。

## 重启与断线

- 仅当用户明确要求时，才在会话内执行 `dsh restart`；多个请求同时到来时先问用户。执行前告知用户：本次会话将断开。
- 会话内 `dsh restart` 会先返回"已排程"，约 3 秒后再由脱离会话的进程停止并重启 Host。返回 0 只表示已排程，不得在当次回复中宣称重启成功。
- 会话没有断开时，立即执行 `dsh history`，若最近一次重启为 `failed`，如实报告 `failedPhase` 与 `hostStopped`。重连后同样用 `dsh history` 按 receipt 验证结果。
- Host 没有恢复时，请用户在外部终端执行 `dsh`。预览环境重连后，以 `$DSH_HOME/preview.json` 或重跑 `dsh` 时的 `DSH_PREVIEW` 输出为准确认地址。
- `dsh stop` 同样会断开当前会话。Windows 不支持会话内重启，请用户在外部终端执行 `dsh restart`。

## 工作流选路

- 到「这件事直接改，还是要开 OpenSpec change、开哪种」这个决策点时，若用户没有明确指定、当前任务也不属于已有 change，先用 `jev-workflow-router` skill 取一次建议：它只做一次 classify（必要时再一次 decide），然后在你自己的回复里给一行中文建议，例如「（Jev 路由建议：standard-openspec，置信度 0.91；可无视，按你的判断走。）」。
- 这行建议永不阻断、永不追问、永不作为门禁；低置信度、escape、调用失败都直接不说。用户已指定流程或任务已有 change 时零调用、零输出。
- 建议不改变任何实际流程：不因它建 change、切 schema、调 `ssf`、开实施或放宽任何安全/合入/Worktree 门禁。超出「给一行建议」的自动化必须另开 change 并经用户批准。

## 子会话派发

是否派发由你决定：
- 派发：实施已批准计划中工作量较大的编码任务；独立评审或复核（需要不带当前上下文的新视角）；中间输出多的探索（大范围搜索、读日志、跑测试），只带回结论；彼此独立、可并行的多块工作。
- 不派发：与用户讨论或做决定的回合；前后依赖且当前上下文装得下的工作；单个小修复。
- 本身是子会话时不再向下派发，除非任务明确要求。
- 派发时直接使用官方 fresh 创建工具，只传用户或 lead 指定的 provider、model、reasoning_effort；AUTO 会在创建时自行选配。派发前不需要先调用 `route_subagent`，它只是可选预览，其推荐结果不要作为显式参数传给官方工具；预览返回错误时暂停委派并询问用户。
- provider 选择、描述标注与复用规则见 `subagent-model-routing` skill。

这是模型工作指导，不授予任何权限，也不替代 runtime 的实际安全边界。
